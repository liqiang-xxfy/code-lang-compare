## 1. 项目定位

### 1.1 目标用户与核心场景

| 项 | 内容 |
| --- | --- |
| 用户 | 有 JS/TS 基础的前端开发者，计划学 Kotlin / Swift / Dart / Python（TS 不熟） |
| 痛点 | 多语言语法并行学习时混淆、记不牢；官方文档按语言组织，不做跨语言对照 |
| 核心场景（按频次排序） | ① 忘了某语言怎么写某个东西 → 秒查；② 学一门新语言时按章节系统对照；③ 迁移过程中踩坑 → 按症状检索 |
| 使用姿势 | **桌面浏览器为主**，移动端为阅读降级场景（不是编辑场景） |

**术语约定（对齐既有决策）**：本文的"**基准语言**（baseline）"= 被选为参照系的那一门（默认 JavaScript）；"**目标语言**（target）"= 与基准对照的其余语言。二者都是运行时可变角色，不是固定的语言属性。

### 1.2 成功标准（可验收）

| # | 标准 | 验收方式 |
| --- | --- | --- |
| S1 | 打开任一 Feature 深链，能在一次滚动内看清"该特性在所选语言里各怎么写、差异在哪" | 人工走查 |
| S2 | 新增一门语言只改 `content/` 与 `content/registry.yaml`，CI 的 `verify-extensibility` 通过 | `npm run verify:ext` |
| S3 | 100% 已发布 snippet 有完整 provenance；许可台账可逐条核对到"义务 → 履行位置" | `attributions.json` 人工抽检 20 条 |
| S4 | 375px 宽视口下可完整阅读任一 Feature，无横向溢出 | 移动端走查 |
| S5 | 首期内容（JS+Python / M1 前 8 章）100% 达到 `reviewed` 或以上 | `content:report` |

### 1.3 非目标（明确不做）

在线运行代码、用户账号与云同步、内容协作编辑、社区评论、内容的多语言翻译、原生 App / 小程序、后端服务、搜索（首期）。

### 1.4 要超越的基线（保留 v1 结论）

对标 `hyperpolyglot.org/scripting`：语言列可勾选 / 可存预设、章节与长代码可折叠、可"只看有差异的项"、支持"以某语言为基准"的视角切换、有差异标记、移动端可用、有实战内容、有按症状检索的踩坑清单。

内容组织范式沿用《移动端直播接入：前端转 Android 原生新手指南》的骨架：**硬约束前置 → 心智模型对照表 → 目标语言速成 → 分步实操 → 按症状查的踩坑清单（带 ⭐ 必踩标注）→ 学习路线 → 官方资源**。

## 3. 架构总览

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ L4 呈现层   views/ + components/                              │
│             只依赖 ContentRepository 接口与生成的静态注册表        │
├──────────────────────────────────────────────────────────────┤
│ L3 应用层   stores/ + composables/                             │
│             用户设置、当前基准/语言集、派生视图态（含运行时 diff） │
├──────────────────────────────────────────────────────────────┤
│ L2 领域层   content/repository.ts  content/diff.ts             │
│             取数契约 + 等价性/差异计算（纯函数，可单测）           │
├──────────────────────────────────────────────────────────────┤
│ L1 内容产物 src/generated/*（构建期生成，只读，不手改）           │
├──────────────────────────────────────────────────────────────┤
│ L0 内容源   content/**（YAML + Markdown，唯一人工编辑入口）       │
│             经 scripts/pipeline/ 单向编译至 L1                   │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向单一且严格单向**：L4 → L3 → L2 → L1 →（构建期）L0。
**禁止**：L4/L3 直接读 YAML；L1 手改；`content/` 里出现任何可执行代码。

### 3.2 容器与边界

| 容器 | 运行时机 | 职责 | 明确不做 |
| --- | --- | --- | --- |
| **内容编译管线**（Node / tsx） | 构建期 / 本地 | 校验、合并、抽取、高亮、产物生成、报告 | 不做任何网络请求以外的业务逻辑；不渲染页面 |
| **静态 SPA**（浏览器） | 运行期 | 装载分片内容、计算差异、渲染交互 | 不解析 YAML、不做 schema 校验、不做语法高亮 |
| **CI**（GitHub Actions） | 提交时 | 跑校验规则集并阻断、跑测试、构建、发布 | 不承担内容生产 |

### 3.3 两个数据流

**构建期（唯一的内容真源路径）**

```
content/**/*.{yaml,md}
   │
   ├─▶ [1] validate   7 条规则集，失败即非零退出（CI 阻断）
   │
   ├─▶ [2] normalize  校验并解析 → 内容 IR（内存）
   │                     · 按 featureId 合并双轴
   │                     · 从代码内联 @note 抽取 Annotation[] 并剥离标记
   │                     · 校验 equivalence / flags / provenance 完整性
   │                     · 解析 Markdown（markdown-it + 白名单）→ HTML
   │
   ├─▶ [3] highlight  Shiki（主题 css-variables）→ HTML 字符串
   │
   └─▶ [4] emit
         src/generated/registry.gen.ts        # 语言注册表（含 LanguageId 派生）
         src/generated/content/<topicId>.json # 按 topic 分片
         src/generated/attributions.json      # 许可台账
         src/generated/report.json            # 覆盖率 / status 分布
         public/sitemap.xml                   # 语义化路由清单
         public/robots.txt

   └─▶ [5] prerender   ← D-B 新增，vite build 之后
         vite-ssg 枚举所有路由 → vue/server-renderer 渲染
         dist/<route>/index.html              # ★ 含真实内容的静态 HTML（SEO 入口）
         dist/404.html                        # GH Pages SPA fallback
```

> **`[5] prerender` 是 SEO 的关键落点**：爬虫（尤其不执行 JS 的百度）直接读 `dist/<route>/index.html` 就能拿到该特性在 JS/Python 里的完整代码对照。CSR 只作为水合层，负责交互（切语言、切展示模式、切基准）。
> **约束**：预渲染要求"任意路由可在 Node 环境独立取数"——这正是 `ContentRepository` 存在的意义（§7.1），也是它不被替换成"直接 import JSON"的原因。

> **注意**：diff 与等价性**不在构建期预计算**（理由见 ADR-05 与 §7.4）。构建期只做"内容→HTML"的确定性转换。

**运行期**

```
App boot
  └─ registry.gen.ts（随主包，< 2KB）
       ├─ 恢复用户设置：theme / density / baselineLang / activeLangs / presets（pc:v1:*）
       └─ router 解析
            └─ ContentRepository.importTopic(topicId)   ← 动态 import 分片
                 └─ 视图渲染
                      ├─ useBaselineDiff → content/diff.ts（jsdiff）按需计算
                      └─ 用户交互 → usePersistedState 回写设置
```

**两层数据流的分界点**：`src/generated/`。它左边是"作者的世界"（YAML/Markdown，可人工编辑），右边是"程序的世界"（JSON/TS，机器生成）。跨越分界点只能由 `npm run content:build` 单向完成。

### 3.4 接口契约总表（"谁怎么用谁"）

| 契约 | 定义处 | 实现方 | 使用方 | 运行时机 |
| --- | --- | --- | --- | --- |
| `LanguageId` 及相关类型 | `src/generated/registry.gen.ts`（生成） | 管线 | 全部 | 类型层（零运行时） |
| `ContentRepository` | `src/content/repository.ts` | 静态分片实现 | stores / views | 运行期 |
| `ContentValidator`（规则集） | `scripts/pipeline/rules/*.ts` | 管线 | CI | 构建期 |
| `NoteExtractor` | `scripts/pipeline/extract-notes.ts` | 管线 | 管线 | 构建期 |
| `CodeHighlighter` | `scripts/pipeline/highlight.ts` | Shiki 封装 | 管线 | 构建期 |
| `DiffEngine` | `src/content/diff.ts` | jsdiff 封装 | composables | 运行期 |
| `Runner` | `src/types/runner.ts` | 未实现（`kind:'none'`） | 预留 | — |

每个契约都必须满足：**只有一个实现**（首期）、**可替换**（未来换 SSG / 换 diff 库 / 换高亮器不动上层）。

## 4. 内容模型（单一真源）

### 4.1 建模原则

1. **一个概念只有一个实体**。如果两个实体可以用相同的字段表达同一件事，就合并。
2. **手写字段只表达"人才能判断的事实"**（如"Python 没有等价的 `var` 提升"）；机器能推导的（差异行、相似程度、覆盖率）一律不写进内容源。
3. **类型不手写**：`src/types/*` 是 `z.infer<schema>` 的再导出（`import type` 被编译期擦除，零运行时成本）。schema 是契约的唯一来源，杜绝"手写 interface 与 Zod schema 漂移"。
4. **锚定要抗编辑**：任何跨文件引用都不能依赖"第几行"这类脆弱位置。
5. **富文本只允许受限 Markdown**，不允许裸 HTML（安全边界，见 §9.3）。

### 4.2 实体关系

```
Topic ─┬─▶ Chapter ──(有序)──▶ Feature ──┬──▶ Snippet[lang]   （矩阵一格）
       │                                  │
       │                                  └──▶ Pitfall*        （通过 featureId 反查）
       │
       └─▶ ConceptGroup ──▶ ConceptEntry[lang]   （心智模型对照，N 列投影）
                              └──▶ GlossaryTerm*  （术语，可独立检索）

Problem ──▶ Solution[lang]     （M3 实战：与 Feature/Snippet 同构，见 §4.3.6）
RoadmapStage[lang]             （M7：按目标语言分路径）
```

> `*` = 可独立存在（不强制挂在某个 Feature 上），但鼓励挂载以获得双向导航。

### 4.3 关键实体定义

#### 4.3.1 语言注册表（构建期生成）

```ts
// src/generated/registry.gen.ts —— 由 scripts/build/generate-registry.ts 生成，禁止手改
export const allLanguageIds = ['javascript','typescript','python','kotlin','swift','dart','arkts'] as const;
export const enabledLanguageIds = ['javascript','python'] as const;

export type LanguageId = (typeof allLanguageIds)[number];      // 全集：内容源可引用任意一门
export type EnabledLanguageId = (typeof enabledLanguageIds)[number]; // 已启用：UI 可渲染
```

**为什么拆成两个**：`Snippet.lang` 必须能指向尚未启用的语言（否则给 Python 写好内容但还没启用时无法入库）；而 UI 列表只能迭代已启用的。v1 的单一 `LanguageId` 联合类型无法同时满足，且是"手写类型"（与"零代码改动"的承诺冲突）。

```ts
export interface LanguageMeta {
  id: LanguageId;
  name: string;                 // 'Python'
  shortName: string;            // 列头短名 'Py'
  aliases: string[];            // ['py'] 供搜索
  version?: string;             // '3.12'  内容所依据的版本（版本漂移追踪）
  fileExtension: string;        // '.py'
  comment: { line: string; block?: [string, string] };  // 驱动 @note 标记解析与注释高亮
  shikiLang: string;            // 'python' 驱动高亮，加语言不改代码
  paradigm: string[];
  typing: 'dynamic' | 'static' | 'gradual';
  typeSystem?: 'structural' | 'nominal';
  memoryModel: 'gc' | 'arc' | 'manual';
  concurrency: string[];
  baseline: boolean;            // JS = true，默认基准
  links: ResourceLink[];
}
// 已删除：status: 'active' | 'planned'
//   理由：与 content/registry.yaml 的 enabled 是两个开关控同一件事，且可冲突。
//   启用与否是"发布决策"，归 registry.yaml 单一管理。
```

#### 4.3.2 内容骨架

```ts
export interface Topic   { id: string; title: string; order: number; summary?: string; }
export interface Chapter { id: string; topicId: string; title: string; order: number;
                           summary?: string; featureIds: string[]; }   // 数组顺序即展示顺序

export interface Feature {                    // 对比最小单元 = 矩阵一行
  id: string;                                 // 全局唯一，见 §4.4 命名约定
  topicId: string;
  chapterId: string;
  title: string;
  kind: 'syntax' | 'concept' | 'behavior' | 'mapping';
  summary?: string;                           // 纯文本一句话
  body?: string;                              // 受限 Markdown；权威说明写这里，不写进 note
  tags?: string[];
}
// 已删除：kind: 'pitfall'（与 M4 Pitfall 实体重复）
// 已删除：weight（与 Chapter.featureIds 数组顺序重复）
// 已删除：note（与 body 语义重叠，合并为 body）
```

#### 4.3.3 一格内容

```ts
export interface Snippet {                    // 每语言一个实现 = 矩阵一格
  lang: LanguageId;
  code: string;                               // 可含内联 @note 标记，构建期抽取
  equivalence: Equivalence;                   // ★ 唯一的"是否不同"判据（手写）
  flags?: SnippetFlag[];                      // 只表达事实性标注，不表达"是否不同"
  output?: string;                            // 手写运行结果（无 runner，需同等校对）
  notes?: Annotation[];                       // 构建期从 code 抽取，内容源不手写
  review: ReviewRecord;                       // provenance + 审阅状态
}
// 已删除：status（并入 review.state）；已删除：source（拆成 provenance 与 review）
// 已删除：flags 中的 'differs'（由 equivalence 推导）

export type Equivalence = 'identical' | 'analogous' | 'divergent' | 'absent';
//  identical  同构：语义与写法几乎可直接迁移（如 `let x = 1` / `x = 1`）
//  analogous  形似：结构相近但有关键差异，值得展开读
//  divergent  语义不同：看起来像但行为不同（迁移陷阱的高发区）
//  absent     无等价：该语言没有这个概念（必须有替代做法说明）

export type SnippetFlag = 'partial' | 'deprecated' | 'new' | 'experimental' | 'api-only';
```

**为什么把 `differs` 删掉**：v1 同时用"手写 `flags.differs`"和"计算出的 SimilarityBadge 分数"回答同一个问题。二者必然漂移，且用户会看到自相矛盾的信号（单元格标"一致"但相似度 30%）。v2 只保留**人判断的等价性**作为唯一判据，机器只负责**把等价性渲染成行级 diff**。

#### 4.3.4 出处与审阅（拆分 provenance / review，修 P7）

```ts
export type Provenance =
  | { origin: 'thealgorithms'; url: string; license: 'MIT';      author?: string; retrievedAt: string }
  | { origin: 'rosettacode';   url: string; license: 'GFDL-1.2'; author?: string; retrievedAt: string }
  | { origin: 'manual';        license: 'CC-BY-4.0' }            // 作者原创，站点自身许可
  | { origin: 'llm';           model: string; promptTemplateId: string; generatedAt: string };

export interface ReviewRecord {
  state: 'draft' | 'reviewed' | 'verified';
  provenance: Provenance;
  reviewedBy?: string;
  reviewedAt?: string;
  notes?: string;      // 校对备注，不面向读者
}
```

**刻意不给 `origin: 'llm'` 加 `license` 字段**：LLM 输出不产生可署名的许可证。v1 要求"`license` 不得为 `unknown`"，在 LLM 是主力来源的前提下，等于强迫作者把 LLM 产出标成 `MIT` 或 `GFDL-1.2`——那是**错误的许可陈述**，比留空更危险。LLM 产出的合规责任通过 `review`（人工审阅记录）+ 许可台账（§6.1）承担，而不是伪造一个 license 值。

#### 4.3.5 踩坑与心智模型

```ts
export interface Pitfall {                    // M4，全站最高价值模块
  id: string; title: string;
  symptom: string; cause: string; fix: string;   // 支持受限 Markdown
  severity: 1 | 2 | 3;                           // ⭐
  languages: LanguageId[];                       // 该坑涉及的语言
  fromBaseline: boolean;                         // 是否"JS 开发者必踩"
  featureId?: string;                            // 反查 Feature（可选）
  tags?: string[];
}

export interface ConceptGroup {               // 心智模型对照（修 P13-③：支持 N 列）
  id: string; concept: string;
  entries: Partial<Record<LanguageId, { label: string; detail: string }>>;
  // 两列视图只是 entries 的一个投影（baseline 一列 + 当前基准之外的所有列）
  // v1 的 { baseline, target } 结构在 7 语言下无法表达
}

export interface GlossaryTerm {
  term: string; aliases?: string[];
  perLanguage: Partial<Record<LanguageId, string>>;  // 该语言里的对应叫法
  note?: string;
}
```

#### 4.3.6 实战（M3，修 P13-②）

**不新建 `Problem`/`Solution` 实体**——它与 `Feature`/`Snippet` 完全同构（"一个题目在 N 门语言里各有一份实现"与"一个特性在 N 门语言里各有一份写法"是同一个结构）。

落法：M3 的内容组织为 `topicId: practice` 的 Topic，每个题目 = 一个 `Feature`（`kind: 'syntax' | 'behavior'`），每门语言的实现 = 一个 `Snippet`。需要"题目专属"的元数据（难度、输入输出、验收）时，用 `Feature.body` 的受限 Markdown + `Snippet.output` 承载；若实践后确认字段不足以表达，**再**引入 `PracticeMeta` 扩展字段，而不是预先造第二套 schema。

**收益**：矩阵视图、卡片并排视图、差异机制、校验规则、覆盖率报告在 M3 上**零改动复用**。v1 的做法会让 M3 需要一套平行组件。

#### 4.3.7 路线图

```ts
export interface RoadmapStage {
  id: string; lang: LanguageId; order: number;
  title: string; durationHint?: string;         // '3-5 天'
  todo: string[];                               // 做什么
  acceptance: string[];                         // 验收标准（可勾选）
  resources?: ResourceLink[];
}
```

### 4.4 命名与约定

| 项 | 约定 | 理由 |
| --- | --- | --- |
| 实体 id | `kebab-case`，Feature 用 `"<topic 前缀>/<slug>"`，如 `basics/var-declaration` | 双轴目录中需要全局唯一且可读；避免跨文件撞名 |
| 文件 | 一个 Chapter 一个 YAML（`content/topics/basics/01-variables.yaml`） | 减小合并冲突面，便于按章分片 |
| 语言目录 | `content/languages/<LanguageId>/`，目录名 === `meta.id` | 自动发现依赖此约束，`validate` 强制 |
| 注释标记 | 统一 `@note`，前缀用该语言自身的注释符 | 见 ADR-10 |
| 枚举值 | 小写 kebab（`no-equivalent`）或单驼峰（`css-variables`），同一枚举内保持一致 | 避免 `noEquivalent`/`no-equivalent` 混用 |

### 4.5 显式删除 / 合并清单

| 项 | 处置 | 依据 | 收益 |
| --- | --- | --- | --- |
| `Feature.kind: 'pitfall'` | **删** | 与 `Pitfall` 实体重复；一个坑既可以是 Feature 又是 Pitfall，会产生两份内容 | 消除"同一事实两处维护"的腐坏源 |
| `Feature.weight` | **删** | `Chapter.featureIds` 数组顺序已表达优先级 | 去掉一个可被忽略的字段 |
| `Feature.note` | **合并进 `body`** | 两者都是"跨语言综述"，只是长度不同 | 作者不再纠结该写哪个 |
| `Snippet.status` | **并入 `review.state`** | 状态与出处/审阅者属于同一件事 | 一次改动即完成状态流转 |
| `Snippet.source` | **拆为 `review.provenance`** | 许可字段对 LLM 产物无意义（P7） | 许可陈述不再出错 |
| `SnippetFlag 'differs'` | **删** | 由 `equivalence` 推导 | 消除双判据（P4） |
| `SnippetFlag 'no-equivalent'` | **删** | 由 `equivalence: 'absent'` 表达 | 同上 |
| `LanguageMeta.status` | **删** | 与 `registry.enabled` 重复且可冲突 | 单一开关 |
| `SimilarityBadge`（数值） | **删** | 无区分度，伪精度（P5） | 少一个误导性 UI 元素 |
| 运行时 `import.meta.glob('*.yaml')` | **删** | 双真源（P1） | dev/prod 行为一致；客户端包减小 |
| 运行期 `js-yaml` / `zod` | **移入 devDependencies** | 校验只发生在构建期 | 客户端包减少约 40–60KB（未压缩，量级估算） |
| 构建期预计算 diff | **删** | 基准可切换 + 可视集随交互变化（§7.4） | 产物体积与构建时长显著下降 |
| 首期 `minisearch` / `@tanstack/vue-virtual` | **推迟** | 搜索是二期；首期单章 ≤ 120 行，无需虚拟化 | 减少首期依赖与复杂度 |

## 5. 内容组织与信息架构

### 5.1 双轴目录结构（保留 v1 设计）

- **轴一 按主题**（语言无关）：`content/topics/<topicId>/*.yaml` —— 只定义"有哪些 Chapter、哪些 Feature"，**不含代码**
- **轴二 按语言**：`content/languages/<lang>/snippets.yaml` —— 按 `featureId` 提供代码
- **构建期 merge**：按 `featureId` 合并为 `Feature + Partial<Record<LanguageId, Snippet>>`

理由（保留 v1）：加语言只写覆盖层；加特性只在 topics 加一行 + 各语言补 snippet；"对比"是天然操作（一行 = 一个 Feature，列 = 各语言的覆盖值）。

**补强**：v1 未定义"某语言该 Feature 缺 snippet"时的语义。v2 规定——

| 情况 | 内容源写法 | 构建行为 |
| --- | --- | --- |
| 有实现 | 正常 `Snippet` | 正常渲染 |
| 该语言无此概念 | `equivalence: 'absent'` + `code` 为空字符串 + `body` 说明替代做法 | 渲染灰底"该语言无此概念" + 替代做法的链接/说明 |
| 尚未撰写 | **不写该语言** | `validate` 报"覆盖率缺口"，按严重度分级：已启用语言的 `divergent`/`absent` 缺失 → **阻断**；其他 → 警告 |
| 部分支持 | `equivalence: 'analogous'` + `flags: ['partial']` | 琥珀标记 + partial 徽章 |

> v1 把"缺失"与"无等价"混为一谈（都标 `no-equivalent`），会让"还没写"和"语言里真的没有"看起来一样，从而掩盖内容缺口——这正是覆盖率报告要抓的东西。

## 6. 内容编译管线

### 6.1 数据源与许可策略（修正 v1 的口径不一致）

**v1 的两处矛盾**：① §2 说"内容来源：**TheAlgorithms 为主**"，§7.1 说"**自研生成为主力来源**，覆盖 M0/M1/M2/M5/M6"；② 要求 LLM 产物填 `license`（见 §4.3.4）。

**v2 的统一口径（按模块分派）**：

| 模块 | 主力来源 | 理由 |
| --- | --- | --- |
| M0 哲学 / M1 基础语法 / M2 高级语法 / M5 工具链 / M6 并发内存 / M7 路线图 | **自研（LLM 生成 + 人工校对）** | 这些是"最小语法与生态对照"，TheAlgorithms 里不存在（它是算法库） |
| M3 实战（算法类题目） | **TheAlgorithms（MIT）** | 正是它的强项；MIT 只需保留版权声明 |
| M4 迁移陷阱 | **自研（人工为主，LLM 辅助）** | 属于经验知识，需作者亲身判断，不可外包给模型 |
| 心智模型对照 / 术语词典 | **自研（人工为主）** | 同上 |
| 少量多视角补充 | Rosetta Code（**首期不引入**，见 Q6） | GFDL 1.2 合规成本 > 收益 |

> **v1 的"TheAlgorithms 为主"是错的**：TheAlgorithms 是算法实现集合，无法提供"变量声明怎么写"这类内容。以它为主力会让 M1 无米下炊。

**许可台账（新增，把"合规"从口头约定变成可检查资产）**

`src/generated/attributions.json` 的每条记录形如：

```jsonc
{
  "sourceId": "thealgorithms/python",
  "url": "https://github.com/TheAlgorithms/Python",
  "license": "MIT",
  "obligation": "保留版权声明与许可文本",          // 该许可要求我做什么
  "fulfilledAt": ["/attributions#thealgorithms-python", "页脚全局声明"], // 我在哪履行的
  "usedBy": ["practice/…"]                        // 用在哪
}
```

`/attributions` 页面即由它渲染；`validate` 检查**每条已发布 snippet 的 provenance 都能在台账中命中**，否则阻断。这解决了 v1 "写了合规要求但无法验证是否履行"的问题。

**硬性合规规则（进 §6.3 规则集）**

1. 每条已发布 snippet 的 `review.provenance` 必填，且 `origin` 必须是四类之一
2. `origin: 'thealgorithms'` → 必须有 `url` + `retrievedAt`，且 `license === 'MIT'`
3. `origin: 'rosettacode'` → 必须有 `url`，且**必须**在台账中登记 GFDL 履行位置（独立分区页脚）
4. `origin: 'llm'` → 必须有 `model` + `promptTemplateId` + `generatedAt`，且 `review.state !== 'draft'`
5. 站点自身代码与原创内容采用 **MIT**，`origin: 'manual'` 的内容同样适用（`LICENSE` 文件 + 页脚声明）

### 6.2 四阶段管线（修正版）

```
scripts/
├─ pipeline/
│  ├─ 01-import.ts        拉源 → scripts/data/raw/<source>/<date>/（含 url+license+retrievedAt 快照）

│  ├─ 03-validate.ts      跑 rules/* 规则集 + 覆盖率报告（非零退出供 CI）
│  ├─ 04-build.ts         合并 → 抽取 @note → 渲染 Markdown → Shiki 高亮 → emit

│  │   ├─ r01-schema.ts             Zod 结构合法性

│  │   ├─ r03-provenance.ts         provenance / 许可 / 台账命中
│  │   ├─ r04-notes.ts              @note 标记全部成功解析

│  │   ├─ r06-status.ts             发布门槛（draft 不得进入生产）

│  ├─ sources/
│  │   ├─ thealgorithms.ts
│  │   └─ rosettacode.ts          （首期不接入，保留实现）
│  └─ generate/
│      ├─ prompt-templates/
│      └─ llm-provider.ts
├─ build/generate-registry.ts   → src/generated/registry.gen.ts
```

**四阶段职责**

| 阶段 | 输入 | 输出 | 关键约束 |
| --- | --- | --- | --- |
| 01 import | 外部源 | `scripts/data/raw/**`（原始快照） | 参数化（`--source --lang`）；抓取节流 ≥ 1 req/s；快照含 `url+license+retrievedAt`，保证可追溯可重跑；目录 `.gitignore` |
| 02 generate | 原始素材 + `LanguageMeta` + 提示词模板 | 候选 `Snippet`（`state: draft`） | 产物**一律 draft**；provider 接口可替换；**生成结果不直接写入 `content/`，而是落到 `content/staging/` 由人工挑选沉淀** |
| 03 validate | `content/**` 全量 | 覆盖率报告 + 退出码 | 规则集可插拔；失败非零退出；报告同时输出"已发布 / 未发布"两类计数 |

> **02 的新增约束（v1 缺失）**：v1 让 generate 直接产出对齐 schema 的 draft，作者面对的是"满城皆 draft"。v2 引入 `content/staging/`：生成物先落暂存区，作者**主动挑选 + 改写**后移入 `content/languages/<lang>/`，此时才赋 `review.state: 'draft'` 并进入正式管线。这让"作者写的内容"与"机器写的内容"在目录上就分开，`content-report` 能直接回答"站里有多少内容是机器写完还没被人碰过的"。

### 6.3 校验规则集（CI 阻断清单）

| 规则 | 检查内容 | 失败级别 |
| --- | --- | --- |
| R1 schema | 所有 YAML/MD 通过 Zod 校验；枚举值合法 | **阻断** |
| R2 coverage | 每个**已启用**语言的每个 Feature：要么有 snippet，要么显式 `equivalence: 'absent'`；缺口率 > 阈值（首期 10%） | **阻断** |
| R3 provenance | provenance 完整；MIT 有 url+retrievedAt；LLM 有 model+template；台账命中 | **阻断** |
| R4 notes | `code` 中所有 `@note` 标记均被成功解析，且 `notes` 行的 `text` 非空 | **阻断** |
| R5 refs | 所有 `featureId`/`topicId`/`lang` 引用存在；无孤儿 snippet（指向不存在的 Feature） | **阻断** |
| R6 status | 按 `registry.publishPolicy` 判定：`reviewed-only` 下所有 snippet 必须 ≥ `reviewed`；`include-draft-with-badge`（首期）下 draft 允许发布但**必须在 UI 上标注** | **阻断**（严格模式）/ **警告 + 报告**（首期宽松模式，见 D-A） |
| R7 links | 所有 url 为 `https:`；无 `javascript:`/`data:` | **阻断** |
| R8 命名 | 目录名 === `meta.id`；id 符合 §4.4 约定；无重复 id | **阻断** |
| R9 注释符 | `@note` 标记所用前缀与 `meta.comment.line` 一致 | 警告 |
| R10 台账覆盖 | 台账每条记录都有 `fulfilledAt` | 警告 |

> v1 只有"schema + 交叉检查"两类，且 `status`、`@note`（v1 的行号锚定）、引用完整性均未覆盖。R6 是修 P6 的关键闸门。

### 6.4 作者工作流（可落地性）

**加一个 Feature**

1. 在对应 `content/topics/<topic>/<NN>-<chapter>.yaml` 的 `featureIds` 追加 id，并写 `title`/`body`
2. 在 `content/languages/javascript/snippets.yaml`、`.../python/snippets.yaml` 各加一条同 `featureId` 的 snippet（含 `equivalence`、`review.provenance`）
3. `npm run content:validate` → 看缺口报告
4. `npm run dev` 预览（dev 会自动重建产物）
5. `npm run content:report` 确认覆盖率与 status

**加一门语言**

1. 复制 `content/languages/_template/` 为 `content/languages/<id>/`
2. 填 `meta.yaml`（id 必须等于目录名）
3. 补 `snippets.yaml` 等覆盖层
4. 在 `content/registry.yaml` 里 `enabled: true`
5. `npm run content:build && npm run verify:ext` → 验证"组件零改动"

**内容校对**（人工环节）

```bash
npm run content:report          # 列出全部 draft 与缺口
# 逐条改 YAML：state 从 draft → reviewed，填 reviewedBy / reviewedAt
npm run content:validate        # 确认 R6 通过
```

校对者**只改 YAML/Markdown，不碰代码**。

### 7.1 装载与分片

| `attributions.json` | < 50 KB | 仅 `/attributions` 路由 |
| `sitemap.xml` | — | 静态文件 |

**分片粒度决策：`chapterId` 级（一章一个文件）**。原方案是 `topicId` 级，在 8 个 Feature 的量级下没问题；内容补到 **72 个 Feature 后单 topic 分片涨到 732 KB**，首屏要下载整章 8 倍的数据——这正是 §9.1 写明的「单章分片超预算就按 section 细分片」的触发条件，实测触发并已修正。改后单章 69–107 KB（gzip 8–11 KB），也贴合真实访问模式（用户几乎总是访问某一章）。

**为什么不再细到「一个 Feature 一个文件」**：Feature 是同一张表里的一行，切语言、切展示模式都要用到整章数据；再细会让「切语言」产生额外请求与闪烁，收益为负。

**估算过程**（供后续校准，非承诺）：以每格高亮 HTML ≈ 1.3–1.5 KB 计（Shiki 的 span 标记很啰嗦，但 gzip 压缩率极高，实测 **709 KB → 77 KB，约 9:1**）。原按 topic 分片的估算已被实测推翻：8 章 72 个 Feature 时单 topic 分片达 732 KB，因此改为**按章分片**（见下）。7 语言时按同样比例外推，单章约 350–400 KB 未压缩 / 40 KB gzip，仍在 §9.1 的预算内；若届时超限，触发条件是把分片再按「语言分组」拆开（多数场景只同时看 2–4 门语言）。

**分片粒度决策**：`topicId` 级（首期 8 章 → 最多 9 个分片）。不加更细粒度：更细会让"切语言"产生额外请求与闪烁，收益为负。

### 7.2 状态模型

| 状态 | 归属 | 持久化 | 说明 |
| --- | --- | --- | --- |
| `baselineLang` | `languageStore` | ✅ `pc:v1:baseline` | 默认 `'javascript'` |
| `activeLangs` | `languageStore` | ✅ `pc:v1:langs` | 当前显示的列；默认 `['javascript','python']` |
| `presets` | `languageStore` | ✅ `pc:v1:presets` | 命名组合，含"移动端三件套""全语言""仅 JS+目标" |
| `viewMode` | `uiStore` | ✅ `pc:v1:viewMode` | `matrix` / `side-by-side` / `baseline-diff` |
| `density` | `uiStore` | ✅ `pc:v1:density` | `compact` / `comfortable` |
| `theme` | `uiStore` | ✅ `pc:v1:theme` | `light` / `dark` / `system` |
| `content`（当前 topic） | `contentStore` | ❌ | 路由驱动，切换即释放 |
| `roadmapProgress` | 组件局部 | ✅ `pc:v1:progress:<lang>` | 仅勾选状态 |

**持久化统一经 `usePersistedState(key, default, { version })` 封装**（基于 `@vueuse/core` 的 `useLocalStorage`），集中处理：命名空间前缀 `pc:`、版本号、解析失败回退默认、跨标签页同步（`storage` 事件）。

**版本策略**：key 中带 `v1`；当持久化结构与默认值不兼容时，递增为 `v2` 并**直接丢弃旧值**（不写迁移代码——单用户工具，迁移成本 > 收益）。这条明确写死，避免以后纠结。

### 7.3 对比视图（三模式一视图）

`ChapterCompareView` 的三种展示模式共享同一份数据与同一套交互状态：

| 模式 | 布局 | 适用 | 关键交互 |
| --- | --- | --- | --- |
| `matrix` | 行 = Feature，列 = 语言；表头行 + 首列双向 sticky | 系统浏览"某特性在所有语言怎么写" | 行可展开看完整代码与说明；行分组折叠 |
| `side-by-side` | N 张卡横向 `scroll-snap`；窄屏自动纵向堆叠 | 深入阅读单个特性 / 单道题 | 卡片独立滚动；卡头显示语言名 + 后缀 |
| `baseline-diff` | 基准列固定最左、满不透明；其余列显示行级 diff + 等价性徽章 | 迁移学习核心视角"和我的 JS 比，差在哪" | "只看有差异的项"开关 |

**7 门语言横向空间不足的分层解法（保留 v1）**：`LanguagePicker` 自由增删列 + 软上限 4 列（超出时提示切换基准差异模式）；基准固定最左 sticky；首列 sticky；列宽三档预设；命名预设存 localStorage；视口 < 768px 自动切 `side-by-side`。

**新增**：模式切换与基准切换都**不产生路由跳转**（保留滚动位置与展开状态）；当前 `baselineLang` 由 **`?baseline=` query 参数**同步，使"以 Python 为基准看 JS"的链接可分享。

### 7.4 差异机制（重定义为 5 层，无重叠）

| 层 | 机制 | 数据来源 | 计算时机 |
| --- | --- | --- | --- |
| L1 | **等价性标记**：四态徽章（同构 / 形似 / 语义不同 / 无等价），**颜色 + 图标 + 文字三重编码** | `Snippet.equivalence`（手写） | — |
| L2 | **行级 diff 高亮**：非基准列对基准列做行级对比，新增/删除着色 | 运行时 `content/diff.ts`（jsdiff） | 运行时 |
| L3 | **"只看有差异的项"过滤**：过滤掉所有语言均为 `identical` 的 Feature | 由 `equivalence` 派生 | 运行时 |
| L4 | **行为差异内联注释**：`@note` 抽取出的 `Annotation`，斜体 + `←` 引出，沿用 hyperpolyglot 惯例 | 构建期抽取 | 构建期 |
| L5 | **无等价说明**：`equivalence: 'absent'` 的单元格显示"该语言无此概念"+ 替代做法 | `Snippet.body` / `Feature.body` | — |

**为什么 diff 放在运行时**：基准语言可由用户在 7 门中任选 → 构建期需预计算 7×6=42 组两两对比；且行展开、"只看差异"都会改变实际渲染集合。jsdiff 体积小（量级 < 10 KB gz），运行时按需计算一次并缓存（`Map<`${featureId}|${baselineLang}|${lang}`, DiffResult>`）足够快。

**为什么删除相似度分数**：见 P5 与 ADR-05。

### 7.5 代码展示规范

| 项 | 决策 |
| --- | --- |
| 高亮 | **Shiki，构建期预高亮，主题 `css-variables`（单份 HTML + CSS 变量切换明暗）**；Shiki 为 devDependency，不入客户端包 |
| 行级 diff / 行号 | 用 `@shikijs/transformers` 的 transformer（行号、行高亮、diff 标记），与 jsdiff 的输出对接，**不另写代码渲染器** |
| 复制按钮 | 右上角，复制**原始 code**（非高亮 HTML），复制内容已剥离 `@note` 标记 |
| 行号 | 可选；`baseline-diff` 模式默认开，`matrix` 默认关 |
| 长代码折叠 | > 15 行默认折叠，显示"展开（共 N 行）" |
| 块头 | 语言名 + 文件后缀（`main.py`） |
| 缺省态 | 灰底"该语言无此概念" + 替代做法，不留白 |
| 明暗切换 | 切换 `data-theme` 属性驱动 CSS 变量；**无闪烁、无重新渲染** |
| 降级路径 | 若 §2.3-Q5 证实 `css-variables` 主题丢失字体样式：改为双主题 HTML 输出，但**必须同时**按 topic 分片（此时单章体积约翻倍，仍在预算内） |

## 8. 可扩展性机制

### 8.1 加一门语言（修正"零改动"的表述）

**v1 的承诺**："新增一门语言 = 只加数据目录，组件零改动"，同时又说"唯一软改动：`registry.yaml` 里 `enabled: true`"，而 `LanguageId` 是**手写联合类型**——加语言必然要改 `src/types/language.ts`。三句话互相矛盾。

**v2 的准确承诺**：

> 新增一门语言 = ① 加一个数据目录；② 在 `content/registry.yaml` 注册；③ 重跑构建。
> **不需要改动任何组件、类型、路由、schema 代码。**

实现方式：

1. `LanguageId` 由 `generate-registry.ts` **生成**（扫描 `content/languages/*/meta.yaml`），不是手写
2. 语言列表、Shiki 语言包、列头、注释符全部数据驱动
3. `verify-extensibility` 脚本在 CI 中执行"加一门假语言（`_fixture`）→ 构建 → 检查 `git diff --name-only`"，断言改动文件集**只含** `content/**`，否则失败

**同时拆掉 v1 的自我欺骗点**：`enabled: false` 的语言，其内容仍可入库并通过校验（`allLanguageIds` 包含它），只是不渲染。这避免了"想先攒内容后启用"时被迫把内容塞进临时目录。

### 8.2 加特性 / 加模块

| 操作 | 改动面 |
| --- | --- |
| 加 Feature | 1 个 topic YAML + N 个 snippet YAML；0 代码 |
| 加 Chapter | 1 个新 YAML 文件 + 在 Topic 里排 order；0 代码 |
| 加 Topic（新模块） | 1 个目录 + `registry.yaml` 注册；0 代码 |
| 加新展示模式 | 需改代码（属功能扩展，非内容扩展） |

### 8.3 预留能力与触发条件

| 能力 | 预留形式 | **启动触发条件**（避免"预留"变成"永不做"或"过早做"） |
| --- | --- | --- |
| 在线运行代码 | `RunnerDescriptor`（全部 `kind: 'none'`）+ `CodeRunner` 接口；"运行"按钮由 feature flag 隐藏 | 至少 1 门语言有稳定的 WASM 运行时（如 Pyodide），且用户明确要求 |
| ~~全文搜索~~ | **已启用**（P4）——构建期产倒排索引（`scripts/pipeline/search-index.ts`），客户端按需加载；中文走 bigram 分词（ADR-21） | — |
| ~~静态预渲染~~ | **已启用**（D-B）——首期即用 `vite-ssg` 做构建期预渲染，不再是"预留" | — |
| 内容 i18n | `uiStore` 文案走 `t()`；`content/i18n/zh-CN.yaml` | 出现非中文读者（内容 i18n 成本极高，见 §9.4） |
| PWA / 离线 | 无 | 用户明确要求 |

> **搜索的触发阈值从「Feature > 200」下调了**（见 ADR-21）。200 是定稿时凭直觉给的数字，没有实测支撑；
> 而实际到 72 个对照格时，侧边栏已只能定位到「章」这一级 —— 想找「Python 怎么判断空数组」，
> 得先猜到它在 06 章，再在 9 行表格里逐行找。
> 判据因此改成**「凭导航无法直接定位到某一格」**，而这一条在 72 格时就已经满足了。
> 速查工具的核心能力，不该被一个拍出来的阈值挡住。

## 9. 非功能要求

### 9.1 性能预算（替代 v1 的"Lighthouse ≥90"）

| 指标 | 预算 | 测量方式 |
| --- | --- | --- |
| 首屏 JS（gz，不含按需分片） | ≤ 180 KB | `vite build` 报告 |
| 单章内容分片（gz） | ≤ 60 KB | 分片报告（实测 8–11 KB） |
| 搜索索引（gz，**按需加载**） | ≤ 90 KB | 构建期自动告警（实测 66 KB） |
| LCP（4G 模拟） | ≤ 2.5 s | Lighthouse 移动端 |
| INP | ≤ 200 ms | 同 |
| CLS | ≤ 0.1 | 同 |
| 切换语言列 / 基准的响应 | ≤ 100 ms（首帧） | 人工 + Performance 面板 |
| 矩阵渲染（7 列 × 14 行） | ≤ 150 ms | 同上 |
| 搜索首结果 | ≤ 100 ms | 人工实测 |

**实现手段**：路由级代码分割；分片懒加载 + 预取下一页；Shiki 构建期完成（运行时零高亮成本）；明暗切换走 CSS 变量（不重渲染）；**首期不引入行虚拟化**——改用 `content-visibility: auto` + 固定行高，触发再评估的条件是单章 Feature > 150。

> **为什么删掉虚拟化**：矩阵表 + sticky 表头 + 可展开行的虚拟化实现复杂度高（是首期最容易翻车的部分），而首期数据量（7 列 × 72 行 = 504 格）在 `content-visibility` 下表现良好。这是典型的"v1 过度设计"。

### 9.2 可访问性（新增）

| 要求 | 做法 |
| --- | --- |
| 不以颜色为唯一判据 | 等价性四态 = 颜色 + 图标（`=`/`≈`/`≠`/`∅`）+ 文字标签 |
| 表格语义 | 用真 `<table>` + `<th scope="col|row">`，不用 div 网格 |
| 横向滚动区可达 | 包裹 `role="region"` + `aria-label` + `tabindex="0"`，键盘可横向滚动 |
| 键盘导航 | 全站可 tab 到达；`:focus-visible` 有可见焦点环（token 化，非 outline:none） |
| 跳转链接 | 首页顶部 `SkipLink` → 主内容 |
| 对比度 | 正文/代码 ≥ 4.5:1（紧凑模式 12px 字要求同上，需实测） |
| 动效 | 尊重 `prefers-reduced-motion` |
| 缩放 | 200% 缩放不破坏布局 |

**目标**：WCAG 2.1 AA 的关键项（1.4.1 颜色使用、1.4.3 对比度、2.1.1 键盘、2.4.7 焦点可见、1.3.1 信息与关系）。

### 9.3 安全（新增）

**威胁面（纯静态站点，无后端 → 无认证/越权风险）**

| 威胁 | 路径 | 措施 |
| --- | --- | --- |
| **内容注入** | LLM 生成内容 → Markdown/HTML → 渲染 | 内容字段按"纯文本 + 受限 Markdown 子集"处理；`markdown-it` 关闭 `html: true`，`linkify` 保留但经协议白名单（R7）；**禁止裸 HTML** |
| **信任边界** | `v-html` 的唯一合法输入是 Shiki 的构建期输出 | 在代码层约束：`v-html` 仅出现在 `CodeBlock.vue` 与 `MarkdownContent.vue` 两处，并加注释说明来源可信 |
| **依赖供应链** | npm 依赖 | lockfile 入库 + Dependabot + CI 跑 `npm audit`（仅告警不阻断，避免阻塞） |
| **CSP 缺失** | GH Pages 无法下发响应头 | 用 `<meta http-equiv="Content-Security-Policy">` 兜底 `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'`（`unsafe-inline` 因 Vue 内联样式与 Shiki 的 `style` 属性必需）。已知限制：meta CSP 不支持 `frame-ancestors`/`report-uri`，无法防 iframe 嵌套——记录为接受的风险 |
| **外部资源** | 图片/字体/脚本 | 不引入任何第三方 CDN、字体、分析脚本 |

### 9.4 国际化（重新界定范围）

**v1 的问题**：说"中文单语，UI 文案抽语言包，预留 i18n"，但内容本身（Feature 标题、snippet 说明、踩坑文案）全是中文，且内容量远大于 UI 文案。这给人以"i18n 很便宜"的错觉。

**v2 界定**：

| 范围 | 是否支持 | 成本 |
| --- | --- | --- |
| UI 文案（按钮/标签/提示） | 首期抽象到 `content/i18n/zh-CN.yaml`，经 `t()` 取用 | 低（一次性） |
| **内容（Feature/Snippet/Pitfall/正文）** | **首期不支持，且明确列为长期非目标** | 极高（≈ 全部内容工作量 × 语言数） |

若未来真需要内容 i18n，路径是：`content/languages/<lang>/` 不变，另加 `locale` 维度（`content/<locale>/topics/...`），改动面是管线与分片命名，不是"加一个语言包"。

### 9.5 SEO 与分享（新增）

| 措施 | 首期 | 说明 |
| --- | --- | --- |
| history 模式 + 语义化路由 | ✅ | 为预渲染留路 |
| `404.html` 复制 | ✅ | GH Pages 的 SPA fallback（ADR-12） |
| 每个路由的 `<title>` / `<meta name="description">` 由内容数据驱动 | ✅ | 在路由守卫里写入 |
| `sitemap.xml` | ✅ | 构建期从 registry + topics 生成 |
| 静态预渲染（每路由产出 HTML） | **✅ 首期必做**（D-B） | 用 `vite-ssg`；产出含真实内容的 HTML，CRS 仅作水合 |

**知道并接受**：首期为 CSR，搜索引擎对正文的收录效果弱。若 §2.3-Q2 确认"必须被搜到"，应在 M3 之后立刻安排预渲染（用 `vite-ssg` 或自写脚本对热门路由生成 HTML 壳）。

### 9.6 成本（新增）

| 项 | 估算 | 前提 |
| --- | --- | --- |
| **现金成本** | **≈ 0** | GH Pages 免费（1 GB 仓库 / 100 GB 月流量软限制），无后端无账号，无第三方服务；可选域名 ≈ ¥60/年 |
| **LLM 生成成本** | 全量重跑（≈ 420 snippet × 约 2k 输入 / 0.5k 输出 token）在主流商用模型下 **< $5** | 与人工校对成本相比可忽略 |
| **工程成本** | **≈ 20–30 人日**：脚手架 3–5；对比视图与差异机制 5–8；管线 4–6；其余模块视图 5–8 | 单人、业余时间 |
| **内容成本（真正的关键路径）** | **首期（JS+Py / 8 章 / 144 snippet）：≈ 15–25 小时**（按每条 LLM 产出人工校对 3–5 分钟 + 72 条 Feature 正文 + 10 条踩坑）；**扩到 7 语言（≈ 420 snippet）：≈ 50–80 小时校对**，且随 M2/M3/M6/M7/M8 内容展开还会翻倍 | 这是 v1 路线图**完全没有计入**的部分 |
| **维护成本** | 语言版本漂移带来的定期复核：每语言每 6–12 个月 ≈ 2–4 小时 | `meta.version` + 页面标注"内容基于版本 X" |

**结论**：这个项目**不缺工程工时，缺内容工时**。因此 v1 的路线图（把"扩展到 7 语言"当作一个工程里程碑）必须改为**工程线 + 内容线双轨**（§11）。

### 9.7 可维护性

| 措施 | 收益 |
| --- | --- |
| 类型由 Zod schema 推导（`z.infer`） | 手写 interface 与校验规则不可能漂移 |
| 校验规则集模块化（`rules/rNN-*.ts`），每条规则有单测 | 加规则不改主流程 |
| 生成物目录 `src/generated/` 头部写"自动生成，禁止手改" | 避免误改 |
| `registry.gen.ts` 与 `content/*.json` 纳入版本控制 | 便于 code review 时直接看到内容变更的产物差异（但需在 README 说明"改内容请改源"） |
| 单一真源 + 单向编译 | 排查问题时只需看 `content/` 一个地方 |

## 11. 实施路线（双轨：工程线 + 内容线）

**首期（P0–P3）的目标不是"功能齐全"，而是"闭环 + 可验证 + 可被收录"**：JS + Python 两列（**且只有这两列**，D-C）、三种展示模式、M1 前 8 章内容、**构建产物含预渲染 HTML**（D-B）、部署可用。

> **D-A 对路线图的影响**：内容线的验收标准从"达到 `reviewed`"改为"**已入库 + 带未校对标注**"，`reviewed` 转为迭代目标而非发布前置条件。这消除了 v1 路线图"内容没校对完 → 站点永远发不出去"的死锁。

| 里程碑 | 工程线（Engineering） | 内容线（Content） | 验收标准 |
| --- | --- | --- | --- |

**注意（D-D）**：ArkTS 必须作为**独立语言身份**接入——保留独立列、独立的 `meta.yaml`、独立的运行时/生态对照（HarmonyOS 的 ArkUI/ArkTS 运行时与 TS 的 Node/浏览器运行时差异是它最大的价值点），**不得**与 TypeScript 合并或降级为"TS 的变体视图"（待确认 Q4 已关闭）。

### 15.1 实测结论（设计假设被验证或推翻）

| # | 设计中的假设 | 实测结果 | 处置 |
| --- | --- | --- | --- |
| 1 | ADR-04：`css-variables` 主题可作为单份 HTML 的高亮方案 | **成立**，但有一个前提：shiki v1 的默认 bundle **不含**该主题，必须 `import { createCssVariablesTheme } from 'shiki/core'` 显式创建后注册 | 已在 `scripts/lib/render.ts` 显式创建 |
| 2 | Q5：该主题是否保留粗体/斜体？ | **不保留**。实测输出只有 `style="color:var(--shiki-token-*)"`，无 font-style / font-weight；shiki v1 的 `createCssVariablesTheme` 也不接受 `fontStyle` 选项 | **不放弃该主题**，改在 CSS 侧按 token 变量名补偿（`span[style*='--shiki-token-comment']{font-style:italic}`）。产物仍是单份 HTML |
| 3 | ADR-12：GH Pages 需要 `404.html` | 成立，另外发现一个**同样致命**的点：`ssgOptions.dirStyle` 默认是 `flat`（产出 `/foo.html`），而 GH Pages 不做「无扩展名 → .html」解析 → **只有首页能打开** | 显式设 `dirStyle: 'nested'`，并在 vite.config.ts 里写明原因 |
| 4 | 环境变量用 `BASE_PATH` / `SITE_URL` | **推翻**。这两个名字太通用，宿主环境已预设同名变量；更糟的是 Git Bash/MSYS 会把以 `/` 开头的环境变量值**自动改写**成 MSYS 根目录的绝对路径，导致 base 变成一条 PortableGit 路径、构建直接失败 | 改用 `PC_` 前缀 + **不带前导斜杠的写法**（`PC_BASE_PATH=code-lang-compare`），并在 `scripts/lib/env-paths.ts` 里识别被改写的值并给出修复提示 |
| 5 | §7.4：diff 用 jsdiff 在运行时算 | 成立，但发现 `diffLines` 会把相邻的删除+新增合并成一个块，导致**本来相同的行也被标成「不同」**（实测 `line3` 被误标） | 改用 `diffArrays` 做逐行精确对齐，行号与索引严格 1:1。这条由单元测试暴露，已加回归用例 |

### 15.2 设计未覆盖、实现期补上的

| # | 补的东西 | 为什么设计没覆盖 |
| --- | --- | --- |
| 1 | `@note` 标记允许出现在注释的**任意位置**（`// true —— @note! 说明`），且剥离时要清掉分隔符残尾 | 设计里写的是「标记紧跟注释前缀之后」，实际写内容时自然会写成「注释 + 破折号 + 说明」 |
| 2 | `equivalence: 'absent'` 允许携带代码，语义是「无等价语法，惯用替代写法如下」 | 设计里规定 absent 时代码为空；但「Python 没有 `?.`，它用 `getattr`」这种信息，给出替代写法比留空有用得多 |
| 3 | 许可台账**只登记实际被使用的来源**（原本登记法会产生「登记了但没人用」的噪音告警） | 设计里把台账写成静态清单；但台账真正要防的是反过来的情况——有内容使用却漏登记义务 |
| 4 | 路线图链接必须按「该语言是否真有路线图」渲染 | 设计假定每门语言都有 roadmap.yaml；实际只有 Python 有，结果侧边栏生成了 `/roadmap/javascript` 死链 |
| 5 | 预渲染产物里代码被 Shiki 拆成 token span，SEO 验收必须按 `textContent`（去标签且**不插空格**）判定 | 设计只写了「检查 HTML 含该页内容」；按字面字符串检查会因 token 拆分产生假阴性 |
| 6 | `content/topics/<模块>/` 承载跨语言列表（pitfalls / concepts / glossary），而不是 v1 设想的「每语言一份 pitfalls.yaml」 | 一条踩坑天然是跨语言的（`languages: [...]` 是数组），按语言拆文件会导致同一条坑在多处维护 |
| 7 | Chapter 内联 `features`，不再单独拆 feature 文件 | v1 的 `Chapter.featureIds: string[]` + 独立 Feature 需要跨文件手工同步 id，是纯负担 |

| 项 | 解决的问题 |

| 许可台账 `attributions.json`（含 `obligation`/`fulfilledAt`） | v1 提了合规要求却无法验证是否履行 |
| 7 条 CI 阻断规则 + 3 条警告（§6.3） | v1 只有 2 类检查，缺 status/引用/`@note` 校验 |
| `ContentRepository` 抽象 | 让未来接预渲染/换数据源不动视图层 |
| `generate-registry.ts` / `verify-extensibility.ts` | 把"加语言零代码改动"从口号变成 CI 可断言的事实 |
| `EquivalenceBadge`（颜色+图标+文字） | 替代数值评分，兼修可访问性 |
| `usePersistedState`（命名空间 + 版本） | 修 localStorage 无版本化 |
| 明暗主题独立设置（`light/dark/system`） | v1 只有密度，代码却要双主题，缺失显式设置项 |
| `content/staging/` 暂存区 | 隔离"机器产出"与"人工产出"，让 `content-report` 可度量 |
| 每条风险的**触发信号**列 | 风险不写触发信号就无法在发生时被识别 |
| `_template/` 语言模板 | 降低加语言的实操摩擦 |
| 内联 SVG 图解承载方案（`content/assets/diagrams/`） | v1 说 M6 要"概念图解"却未定义载体（避免引入 Mermaid 运行时） |
| 跳过导航链接 / 焦点 token / 横向滚动区键盘可达 | 可访问性基线 |
| 中英混合分词（`src/content/search-tokenize.ts`，bigram） | MiniSearch 默认分词对中文**静默失效**；`Intl.Segmenter` 实测把「数组」切碎 |

| 搜索索引的独立体积预算 + 构建期告警 | 索引随内容量线性增长，等它悄悄长到几百 KB 才发现就晚了 |
