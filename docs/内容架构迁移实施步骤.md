## 第 1 章 · 迁移的形状

为什么不能一步到位、又为什么必须有一个原子时刻：

```
增量期(可构建)  →  原子切换(唯一破坏性时刻)  →  内容爬坡(每批可构建)  →  收尾
```

- 增量期之所以可构建：旧 loader 只扫 `content/topics/` 与 `languages/<id>/snippets/`，新增的
  `catalog/`、`languages/<id>/<section>/`、`pairs/` 对它**不可见**，旧管线原样跑绿。
- 原子时刻之所以不可拆：`RenderedSnippet` / `RenderedChapter` 的形状变了，而 `repository.ts` 的
  `import.meta.glob` 立即按新形状消费；`analyzeContent()` 又是 validate / build / tests 的共用入口。
  任何一步单独落地，项目既读不了新内容也读不了旧产物。
- **主干策略下的含义**：虽然是分步提交，但「规则 + 构建产物 + 运行时」三步必须落在**同一个提交**里。
  此处会有一段时间构建红，已接受。

- **c 步最承重的一处**：`features` / `featureIndex` **必须改为从池构建**，不能再遍历 per-baseline catalog ——
  照旧遍历会让同一个 feature 被三个基准各插一次，R20 直接报「全局 feature id 重复」error，
  `stats.featureCount` 也 ×3。per-baseline catalog 只用于「分组 / 可见性 / 覆盖率」。

- **坑**：一章页现在要按「本章引用 features 的 `group` 集合」加载多份分片再合并。
  合并结果**必须保留外层 lang 键** —— 两个布局用 `!shards[lang.id]` 区分「加载中」与「这门语言没写」，
  丢了它未加载的格子会永远转圈，`finalize-dist` 的空壳探针会红。

## 第 4 章 · 必须成对修改的同步点

「改 A 不改 B 会静默失败」的位置：

| 同步点 | A | B | 漏改后果 |
| --- | --- | --- | --- |
| **池 `group` → 分片键** | `analyze` 的池 | `core.loadLanguageContent` / `04-build` 的 emit / `repository.boxShardPathOf` / `stores/content` | **四处各拼一遍**，任一处错 = 整页空白且不报错 |
| **章 → group 展开** | `04-build` 的路由判据 | `guards` 的加载集合 / `ChapterCompareView` 的列裁剪 / store | 列缺内容或整页空白 |
| **catalog 产物形状** | `schemas.RenderedCatalog` | `core.loadCatalog` / `04-build` 的 emit / `finalize-dist` 的内联接口 / `repository` 的消费 | 产物与运行时漂移 |
| **per-baseline catalog 的 baseline 键** | 文件名 | 文件里的 `baseline` 字段 / `catalogOf(基准, 板块)` 的过滤 | **静默取到另一个基准的章节** |
| **`featureIndex` 去掉 chapter** | `src/schemas/index.ts` | `repository.FeatureMeta` / `guards` / `FeatureView` / `search-index` 的 context | 详情页空白或跳错章 |
| 双角色取值 | `src/schemas/index.ts`（契约） | `04-build.ts` 的 `renderBox` / `boxView.ts` / `CodeBlock.vue` / 两个 Layout | 基准列显示成对比说明 |
| 基准 / 对比约束 | `analyze.ts` 的 R8 | `scripts/build/generate-registry.ts` 的自检 | 校验放行但构建 throw |
| 全局 feature id | `src/schemas/index.ts` 的格式定义 | `analyze.globalIdOf` / 搜索 url / 锚点 / 详情页路由 / `refFeatureId` / `finalize-dist` 的探针正则 | 四处各拼一套 id → 404 或锚点错位 |
| 「加载中」判定 | 两个布局的 `!shards[lang.id]` | `stores/content` 暴露的形状（**必须保留外层 lang 键**） | 未加载的格永远转圈 |
| 路由探针 | `finalize-dist` 识别的路由 | `probeTextFor` 的返回值 | 返回 null → **整条验收被静默跳过** |
| 板块字面量 | 新代码里的字符串 | `verify:ext` / `verify:sections` | 两个闸门红，且报错指向错误结论 |
| **章节是否有内容的判据** | `04-build` 的路由判据 | `guards` 的 404 判据 / `SideNav` 的二级项 / `HomeView` 的卡片与计数 / `LanguageView` 的章节列表 / `sectionEntryPath` | 章节分类先于内容落库（S7 骨架期就是这种状态）：任一处漏了 `hasChapterContent`，那一处就会出现**点进去 404 的死链**或虚高计数 |

| `mechanism` 语言机制 | 6（types / generics / memory / concurrency / async / meta） | 29 |
| `practice` 工程实践 | 3（packages / toolchain / testing） | 17 |

可见性只认内容（`hasChapterContent`），所以没有内容的板块整组隐藏、没有死链。

> 文档里「约 160 个知识点」的估算在这里被第一次检验：实际落在 **104**，
> 与 `express` 已显示的压缩比（旧 72 条 basics → 26 条）一致。

### 6.2 分批：**按板块纵深，板块内三基准并行**

**一批 = 一个 (板块, 存放组)**，批内写 **JS / Python / Java 三份**文件
（每份都含 `baseline` + 另外两份 `vs`）。这么排的理由：

- 板块完成时**三个基准视角同时成立**，不会有「某个基准点进去是空的」这种中间态；
- **永不回填** —— 若先把 JS/Python 铺满再引入 Java，就得回头给已有文件补 `vs.java`；
- 内容的总量不变（每格的内容量是固定的），变的只是「多快看到可读的页面」。

| 板块 | 批次（存放组） | 批数 |
| --- | --- | --- |
| `express` | `bindings`（含补 JS 的 `vs.python`/`vs.java`）→ `values` → `operators` → `control-flow` → `functions` → `strings` → `containers` | 7 |
| `model` | `modules` → `errors` → `collections` → `iteration` → `objects` → `abstraction` | 6 |
| `mechanism` | `types` → `generics` → `memory` → `concurrency` → `async` → `meta` | 6 |
| `practice` | `packages` → `toolchain` → `testing` | 3 |

**板块完成的信号**：该板块的 **R23 / R24 / R27 聚合行归零**，
且 `content:report` 的逐存放组账本里三个基准都写满（末尾出现 `✔`）。

### 6.3 板块之后

1. **rust / go**：两门都不是基准候选，只写 `vs.{javascript,python,java}` 三份、不写 `baseline`。
   纯新增，不触发任何回填 —— 所以放最后。
2. **速查重指**：`content/pairs/*/pitfalls.yaml` 的 72 条 `featureId` 仍指向 v1 旧 id
   （6 条 R5 warn），按新板块重指。
3. **校对升级**：`review.state` 从 `draft` 升到 `reviewed` 并补 `reviewedBy` / `reviewedAt`（R17）。
   体量大，可能顺延到 S8。

## 第 7 章 · 风险与回退

三个代价最大的点，各自给缓解手段：

| 风险 | 缓解 |
| --- | --- |
| **catalog 粒度定错**（feature 太粗→信息量不足；太细→成本爆炸） | 每开一个新板块先只写**池**（纯设计、不写正文），池一列出来工作量就可见了；粒度可在铺开前免费调 |
| **双角色契约设计错**（`baselineHtml` / `vsHtml` 形状没定死） | S1 就把形状写进契约；S5 若再改，repository / 视图 / `finalize-dist` 会一起返工 |
| **R22 / R23 分级未定就开写** | 迁移期一律 warn，内容稳定后按板块收紧成 error |
| **S6.5c 里「章 → group → 分片键」在四处各拼一遍**（emit / `boxShardPathOf` / store / 视图） | 收敛成单一函数 `groupsOfChapter(基准, 板块, 章节)`；加构建测试断言「每个 emit 出的分片路径 ↔ `boxShardPathOf` 的键逐字相等」 |
| **`featureIndex` 的来源只翻一半**（半从池、半从 per-baseline catalog） | 契约测试断言「`featureIndex` 大小 == 池的 feature 数」+「每个 catalog 引用都能在池里解析」 |
| **`finalize-dist` 探针静默失效**（per-baseline catalog 会同时踩中章节探针与 feature 正则两处） | 把 `probeTextFor` 改成「凡是识别出的路由，探针必须返回非 null，否则计失败」，并打印实际检查条数 |

**回退策略**：归档不删 → `git revert` 可整体退回；`src/generated/` 全部可再生。

## 第 8 章 · 执行前必须拍板的清单

- **R22（`vs` 完整性）/ R23（基准列非空）在迁移期的级别** —— 沿用旧 R18/R19 的过渡期策略：
  **warn，内容稳定后按板块收紧成 error**。（已定：warn）
- **新模型下搜索分片的键** —— 已定：**按语言分片**（`search-index/<语言>.json`），
  pair 文档归入**目标语言**分片。章节按基准分组不影响它 —— 索引收入的是注记与说明文本，
  不含章节标题。
- **初始启用集合与爬坡阶梯** —— 已定：初始只启用 JS/Python/Java/rust/go 五门，
  爬坡按第 6 章的分批。
- **`_template` 脚手架在新目录结构下的形态** —— 已定：`languages/_template/<板块>/<group>.yaml`，
  与真语言同构（脚手架不参与构建，因此不会因为板块还没建而报缺）。
- **`absent` / 三槽全空在矩阵里的渲染形态** —— 已定（S6）：`absent` 渲染灰格 +「本语言无此概念」+ ∅ 徽章；
  键缺失渲染更淡的留白。两者刻意分开。
- **章节 id 是否要在基准间保持可读的对应关系**。← **未决**：同名章节不代表同义，
  但完全不对应会让「切基准后我在哪一章」这件事失去连续性（`useBaselineSwitch` 的回落逻辑因此变复杂）。
  倾向：**尽量复用 id 表达相近的意思，但不强制**。
