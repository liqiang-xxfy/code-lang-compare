# 多列板块的说明下沉到每一列（ADR-35）

> **状态：已实施（2026-10-02）。** 架构与 294 条基准列内容已同批落地；
> 对比列正文分批补，账目见 `npm run content:report`。
> 决策条目见 [项目架构设计.md](项目架构设计.md) 附录 A 的 ADR-35，
> 书写口径见 [内容书写标准.md](内容书写标准.md) §2。
>
> 本文是**实施记录**：既说明为什么这么改，也留下改动落点与验收口径，
> 便于日后回看「当时为什么这么定」。

---

## Context

章节型对比页原本把「这条 feature 是什么」写成一份**共享说明**（`feature.body`），
渲染在所有列的上方（`SideBySideLayout.vue:83`）。这在**单对单**的迁移教程里成立：
列恒为 `[基准, 目标]`，一份共享说明正好。

但在**单对多**的基础语法与心智模型里它不成立：

1. 列是用户勾选的 1~5 门语言，一份写在基准视角下的共享说明**盖不住各语言自己的事实**，
   也放不下各自与基准的差别；
2. 它在矩阵模式下**根本没有渲染点**（`MatrixLayout.vue` 不引用 `feature.bodyHtml`）——
   同一份内容在两种展示模式下一个有一个没有；
3. 矩阵恰恰是**默认展示模式**，所以连迁移教程那份共享说明在默认视图下也一直不可见
   （本次顺带发现的既有缺陷，未一并修，见「已知遗留」）。

改成：**每列在自己的代码下方写自己的说明**。基准列写本语言的客观事实，对比列写与基准的
差别；客观事实里那些贴着某一行的注意事项，走已有的 `@note` 内联机制，不再重复成段。
存储随之对称：五门语言一律 `code + body` 两个字段，`feature.body` 退到只剩单列板块在用。

## 已确认的决策

| # | 决策 |
|---|---|
| 1 | 基准列说明**下沉到语言覆盖层**，五门语言存储对称 |
| 2 | **先改架构，内容分批补**；「每格应有 body」过渡期 warn |
| 3 | 矩阵模式**每格完整显示** |
| 4 | 单特性详情页 `/feature/:id` **去掉顶部块** |
| 5 | `snippet.body` 一个字段两种角色（基准=客观事实，对比=差别），可选；事实类注意事项走 `@note` |
| 6 | 294 条**先全部原样搬进基准列**，之后按 warn 清单分批清理跨语言内容 |
| 7 | 搜索索引**上调预算，不做 summary-only 优化** |

## 范围外（未动）

`migration` 6 个 topic 保持现状（`feature.body` 仍在代码上方渲染，`kind: exercise` 的题面
依赖它）；`pitfalls` / `glossary` / `roadmap` 三个列表型板块未动；`.pc-code-extra` 的 CSS 未动。

## 改动落点

### A. 渲染（两处，各一行）

判据用 `sectionIsMulti()`（[src/content/repository.ts](../src/content/repository.ts) 已导出，
读板块注册表的 `columns`）—— 它是 ADR-28 三轴模型里 `columns` 的唯一读取口，
比 `scope === 'baseline'` 或写死板块名都准确；未知 section 时返回 `false`，
失败方向是「宁可多渲染，不可静默丢内容」。

- [SideBySideLayout.vue:83](../src/components/compare/SideBySideLayout.vue#L83)
  → `v-if="feature.bodyHtml && !sectionIsMulti(chapter.section)"`
- [FeatureView.vue:204](../src/views/FeatureView.vue#L204)
  → `v-if="feature.bodyHtml && !isMultiSection"`（`isMultiSection` 从 `topicCfg` 派生）

**矩阵与 `CodeBlock` 零改动**：[CodeBlock.vue:198](../src/components/code/CodeBlock.vue#L198)
已经是 `snippet.bodyHtml` 的唯一渲染点，且被 `SideBySideLayout` / `MatrixLayout` / `FeatureView`
三处共用，所以「每列代码下方各写一段」在三个场景自动生效。`MatrixLayout` 本来就不渲染
`feature.body`，决策 3 无需额外代码。

### B. Schema 语义（只改注释，未加字段、未加 refine）

[src/schemas/index.ts](../src/schemas/index.ts)：`featureSchema.body` 注明仅供单列板块使用；
`snippetBase.body` 改写为一个字段两种角色；`exercise` 的说明补上「只存在于单列板块」的边界。

不重命名（migration 150 条内容在用，改名收益为零）；不加 refine（`featureSchema` 看不到
registry 里的 `section`，跨文件判断按既有分工归 `analyze.ts`）。

### C. 校验规则

真值在 `registry.sections[cfg.section].columns`。脚本里**不能** import
`src/content/repository.ts`（它用 `import.meta.glob`，Node 侧不可用），
直接在 [scripts/lib/analyze.ts](../scripts/lib/analyze.ts) 的 R2 覆盖率循环内读 registry。

| 规则 | 级别 | 判定 |
|---|---|---|
| **R18**（新） | warn → 最终 error | 多列板块且 `equivalence !== 'absent'` 且无 `body` |
| **R19**（新） | warn → 搬运验证后翻 error | 多列板块仍有 `feature.body` |
| **R12**（扩展） | warn | 扫描文本纳入 `s.body`，使「基准列的 body 点名其他语言」可被标出 |
| **R11**（放宽） | warn | 追加 `&& !s.body?.trim()`；多列板块跳过（R18 已覆盖同一格） |

R2 里那条「`absent` 无 body」的 warn 保持原样。R18 排除 `absent` 以避免同一格两条重复告警。

**两条新规则都按 `(topic, 列)` 汇总成一条输出**，不逐条 emit：多列板块共 974 格，
过渡期缺口以百计，`formatIssues` 不截断，逐条会打印上千行把真正要看的 error 埋掉。
这与仓库既有的 `pendingByLang` / `draftByLang` 同一处理。逐条待办在 `content:report`，
两份输出共用 `scanBaselineBodies()` 一份判定，避免「报告说 176 条、校验说 170 条」这种对不上。

### D. 搬运脚本

[scripts/migrate/feature-body-to-baseline-snippet.ts](../scripts/migrate/feature-body-to-baseline-snippet.ts)，
用 `npx tsx` 跑，不进 `package.json`（一次性工具）。目标 6 个 topic：

```
basics-javascript→javascript   basics-java→java   basics-python→python    (8 章 72 feature 各)
concepts-javascript→javascript concepts-java→java concepts-python→python  (5 章 26 feature 各)
```

**行级文本手术，绝不 `js-yaml.dump`** —— `content/` 下的 YAML 是手写的、带大量注释，
dump 会摧毁注释、重排键序、改写块标量。做法：

- 定位：feature 用 `/^ {2}- id:/`，body 块首用 `/^ {4}body: \|/`；块结束 = 第一个非空且
  缩进 ≤ 4 的行。缩进由块内首个非空行决定（YAML 语义）。
- 插入点：条目**末尾**（不是 `review:` 之前 —— 6 个目标里只有 `basics-javascript` 是逐条写
  `review:`，其余用文件级默认）。
- **先插后删**，任何时刻崩溃都不丢正文。
- 幂等状态机（topic 有 / snippet 有）：`T,F`→插+删；`F,T`→跳过；`F,F`→跳过；
  `T,T`→逐字相同则只删，不同则覆盖（concepts 那 78 条按「先全部搬」覆盖，清单进报告）。
- **写盘前的安全网是逐键 `deepEqual`**，不是「能解析」：把手术结果与「手术前解析结果 +
  按新位置填好的 body」比对。缩进写错两格 YAML 照样解析得出来，只是内容变了。
- 行尾运行时探测并原样写回（仓库是 LF，但 `core.autocrlf=true` 且无 `.gitattributes`）。
- `--dry-run` / `--verify` 两个模式。

### E. 待补账目可见性

[scripts/pipeline/content-report.ts](../scripts/pipeline/content-report.ts) 新增两块：
按 topic 的多列板块 body 覆盖表（基准列 / 对比列分别计数）、R12 待清理明细（带实际命中的词，
便于识别误报）。`report.json` 本来就带 R18/R19/R12 的 issues，CI 与脚本可直接过滤。

### F. 索引预算

[04-build.ts](../scripts/pipeline/04-build.ts) 的 `SEARCH_INDEX_BUDGET_KB` 由 90 上调到 280。
**是承认现状而不是取消红线**：实测 js 247 / py 145 / java 136 KB(gz)，它仍是一条增长告警。
唯一能回到 90 KB 的是 ADR-21 那条路（summary-only 或按 section 域内检索），
代价是牺牲检索精度，属独立的产品决策。

`docs/内容书写标准.md` §2 / §7 / §11 / §13、`docs/项目架构设计.md` §2.4 与 ADR-35、
`CLAUDE.md` §2.2 / §3 / §4 / 硬约束 / 测试地图 / 已知遗留。

### 后续：R12 清理（2026-10-02 完成）

架构落地后紧接着做了「对比列正文含跨语言内容」这笔账，**R12 已归零**。
账目与口径记在这里，便于日后回看这批正文是怎么从基准列搬到对比列的。

| 项 | 起点 | 终点 |
|---|---|---|
| R12 待清理 | 176 条 | **0 条** |
| 对比列 body 覆盖 | 134/680 | **231/680**（R18 缺口 546 → 449） |

六个 topic 分四批提交，做法按 topic 的性质分成两类：

- **concepts 三套（80 条）是删重复**。它们的对比列本来就写全了（26/26、52/52、26/26），
  基准列那段是同一件事的第二遍。所以主体是删，只有对比列没覆盖到的实质差异才补写过去
  （Java 的名义式类型、JS 的 `===` 约定、Python 的 `unhashable type`、原始字符串的原因等）。
- **basics 三套（96 条）是真搬运**。对比列几乎空着（basics-java 是 0/144），
  删了基准列就真丢内容，必须改写进对应语言的对比列 —— 顺带把这些格子从「无 body」
  变成「有 body」，R18 缺口因此降了 97 格。

「只补被点名的那门语言」是当时的取舍：`basics-java/var-declaration` 这类只点了一门语言的，
另一列仍然空着，同一行看着不齐。要补平是 R18 那笔账的事，见下。

**R12 的级别没动**，仍是 warn。它现在账目为 0，翻成 error 就等于给这条口径装上闸门 ——
但那会让任何一次「基准列顺口提一句别的语言」直接阻断构建，是否值得是独立的产品决定。

## 风险与已知遗留

| 项 | 说明 |
|---|---|
| **矩阵默认视图下迁移教程的共享说明不可见** | 既有缺陷，本次未修（`MatrixLayout` 从不引用 `feature.bodyHtml`）。要修是在矩阵里给 feature 行加一条跨列说明行，属新交互 |
| **concepts 的 78 条基准列原有摘要被覆盖** | 按「先全部搬」的决策。原文在 git 历史里，脚本报告列了清单 |
| **对比列正文含跨语言内容** | **已清（2026-10-02，176 → 0）**，见上文「后续：R12 清理」。留下的两点：① 只补了被点名的那门语言，`basics-java/var-declaration` 这类另一列仍空，行内不齐 —— 归 R18 那笔账；② 检测器只认语言显示名，绕开措辞的幽灵引用（Java 基准列里的「没有 GIL」、以「另两门语言」代指）要人工过 |
| **矩阵行高** | 5 列 × 长正文会把行撑高。本轮按需求做全量显示；后续可给 `.pc-cell-inner .pc-code-extra` 加 `max-height + overflow:auto`，属独立优化 |
| **`renderMarkdown` 的 `shikiLang` 差异** | feature body 走 `04-build.ts:354`（无 shikiLang），snippet body 走 `:326`（带 shikiLang）。搬运的验收口径是 **YAML 层逐字相等**，不是 HTML 逐字节相等 |
| **R11 放宽的副作用** | 某些「有 body 但没讲差异」的格子不再报警，属有意（正文质量无法自动判定），由内容评审兜底 |
