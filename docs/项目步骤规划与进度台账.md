### 0.3 记事（倒序）

**2026-10-04 · 首页基准卡片的命中区铺满整卡（补 2026-10-03 那条留下的缺口）** ——
用户反馈「点『我熟悉某某语言』的卡片，点下去不动，第二次点才生效」。查出来是
**视觉可点 ≠ 实际可点**：卡片是 flex 容器，主链接只有标题 + 计数两行（约 42px），
而卡片总高 98px —— 上下内边距各 14px、与次级链接之间的 gap 8px，**共 38px 是死区**。
偏偏 hover 的浮起 / 变色（底色 / `border-color` / `box-shadow` / `translateY(-2px)`）
是加在**整张卡片**上的，于是整卡看起来都可以点，点在内边距上却没有任何反应。
这正是 2026-10-03「加强调色底与描边，让『这是可以点的』在不动鼠标时也看得出来」那次的
遗留缺口 —— **视觉信号加上去了，命中区没跟上**。

修法是 **stretched link**（`.pc-baseline-main::after { content:''; position:absolute; inset:0 }`，
配 `.pc-baseline-card { position: relative }`）。伪元素绝对定位、不占流，卡片的 flex 排版
一动不动。**次级链接必须 `position: relative; z-index: 1` 浮上来**，否则它自己也会被主链接的
伪元素吃掉点击 —— 而「了解 X 这门语言」是 `/lang/:id` 全站唯一的入口，不能哑掉。
**为什么不干脆把整卡换成 `<RouterLink>`**：卡里还有第二个链接，链接里套链接是无效标记
（模板注释里已经写着这条，这次是给后半句补上落点）。

实测（`document.elementFromPoint` 沿卡片高度逐点探测，修复前后各一轮）：修复前
**0–15% 与 85–100% 两段命中的是卡片本身**（死区），修复后**除 1px 边框线外全部命中**；
其中 70–80% 仍是次级链接自己的命中区，四角与中心全部落在主链接。
`npm run build` 预渲染验收全绿（190/190 条路由）、144 条测试全绿、
`content:validate` 仍是 error 0 / warn 1（未新增）。**只动 CSS，无字段 / 规则 / 判据变化，
架构文档不动、不加 ADR。**

> **顺带查清的另一件事（未改）**：同一轮排查里发现**左栏顶部的基准切换按钮有另一个
> 不同性质的问题** —— 它是全站唯一的 `<button @click>` 型导航控件（`BaselineTabs.vue`），
> 其余入口一律是 `RouterLink`（渲染成 `<a href>`）。后果是：**hydration 完成前点它完全没有
> 反应**（button 没有原生行为，JS handler 又还没绑上），得点第二次。阻断 JS 做过对照实验：
> 点基准按钮 URL 纹丝不动，点卡片（`<a>`）则照常原生导航。它**每次构建后**特别明显，
> 因为 JS 文件名带新 hash、缓存失效，首屏要多下 83 KB(gz) 的 `app.js` 才 hydration 完。
> 用户本次确认要修的是卡片命中区，故**此项按原样保留、未动**，记在这里备查。

## 第 1 章 · 迁移的形状

为什么不能一步到位、又为什么必须有一个原子时刻：

```
增量期(可构建)  →  原子切换(唯一破坏性时刻)  →  内容爬坡(每批可构建)  →  收尾
```

- 增量期之所以可构建：旧 loader 只扫 `content/topics/` 与 `languages/<id>/snippets/`，
  新增的 `catalog/`、`languages/<id>/<section>/`、`pairs/` 对它**不可见**，旧管线原样跑绿。
- 原子时刻之所以不可拆：`RenderedSnippet` / `RenderedChapter` 的形状变了，而 `repository.ts` 的
  `import.meta.glob` 立即按新形状消费；`analyzeContent()` 又是 validate / build / tests 的共用入口。
  任何一步单独落地，项目既读不了新内容也读不了旧产物。
- **主干策略下的含义**：虽然是分步提交，但「规则 + 构建产物 + 运行时」三步必须落在**同一个提交**里。
  此处会有一段时间构建红，已接受。

- **做什么**：四个板块的池 + 每基准的章节分组 + 脚手架。**纯设计，不写正文。**

**实际执行（三处与原计划的差）**：

1. **`express` 池在 S7.1 被修订了一次**：26 → **27** 个 feature、6 → **7** 个存放组 ——
   把 `strings` 拆成 `strings`（string-literals / string-common-ops）与 `containers`（arrays / maps），
   并新增 `naming-convention`（存放组 `bindings`）。理由是试写正文时发现「字符串」一章
   把数组与映射一起讲，读者对不上号。**这次修订没有动任何内容文件** ——
   正是「池与分组可以自由增删改」（骨架先行的意义）的一次实证。
2. **Java 视角的章节分类改过一次**：原计划的独立 `naming`（命名与可见性）章被撤掉，
   `naming-convention` 并入 `types` 章。触发原因是发现**写错了事实** ——
   草稿称「Java 靠首字母大小写决定可见性」，那是 **Go 的规则**（`Name` 导出 / `name` 包内可见）；
   Java 的命名是纯约定，可见性靠 `public` / `private`。修正落在三处：池的 summary、
   `catalog/express/java.yaml`、`docs/内容书写标准.md` 的示例。
3. **`_template` 从 1 个内容文件变成 4 个**：`express/bindings` + `model/errors` +
   `mechanism/types` + `practice/testing` —— 每个板块一个代表，这样新语言脚手架的
   目录形状与真语言完全同构，不会因为「某个板块还没建」而看起来像缺文件。

**计划外的发现（已修）**：骨架落库**本来会产生一整屏 404 死链**。
有四处列章节的地方只查「有没有章节分组」，没查「有没有内容」：
`SideNav` 的二级项、`HomeView` 的卡片与计数、`siblingsOf` 的上一章 / 下一章、`sectionEntryPath`。
骨架一落地它们就会把 12 份分组里的每一章都列出来 —— 而其中大部分点进去是 404。
处置：把判据收敛成一个函数 `hasChapterContent(lang, baseline, section, chapter)`，
并加 `visibleChaptersOf(baseline, section)` 供「列该基准自己的章」的四处统一调用；
`tests/unit/section-model.test.ts` 新增一条断言守着「章节可见性与路由同源」。
（这条判据后来升格为架构文档 §5.3，并记作 ADR-55。）

## 第 6 章 · 接下来的步骤

### 6.1 S7.5 · rust / go 作为对比列 ✅

**做什么**：给 `rust` 与 `go` 各写 22 个存放组的内容文件，
每格只写 `vs.javascript` / `vs.python` / `vs.java` 三份，**不写 `baseline`**。

**为什么放最后**：两门都不是基准候选（`meta.yaml` 里没有 `baseline: true`），
所以**纯新增、不触发任何回填** —— 任何先做它的顺序都会让「已经写完的三个基准」
看起来像没写完。反过来，先做完三个基准，再补这两门，每一步都是加法。

**为什么值得写**：三个基准候选之间**都是 GC + 动态/半静态语言的组合**，
有些格子天然写不出差异（`mechanism/memory` 的 `ownership-borrow` / `lifetime`
在 JS / Python / Java 下全是 `absent`）。rust 与 go 一进来，
这些格子立刻变成站上信息量最大的地方 ——
Rust 的 `ownership-borrow` 是 `identical`（它就是本体），Go 的是 `absent` 但有一套替代做法。
Java 视角下 `bundler` / `event-loop` / `async-await` / `dynamic-eval` 那几行的四门分布同理。

**工作量**：104 知识点 × 2 门 = **208 格**（每格 3 份 `vs`）。

**实际采用的分批**：**按 (板块, 存放组) 一批、批内两门一起写** —— 共 22 批，
与 S7.1–S7.4 的节奏一致。计划里原本建议「按语言分两批」，
执行时改成按存放组，理由是**对照着写质量更高**：
同一个知识点在 rust 与 go 下的差异往往正好是互补的
（比如「没有继承」这一格，Rust 的答案是 trait、Go 的答案是嵌入），
放在一起写能立刻发现「这一格到底在比什么」。代价是上下文切换多，
但每批只有 2 个文件。

**完成信号**不是「某个板块写完」（这两门没有基准视角），
而是「该语言的 4 个板块的 R24 / R20g 归零」。

**进度**：**22/22 批已完成**，两门各 104/104。

**验收**：

```bash
npm run content:validate     # rust / go 的 16 条 R24+R20g 已全部归零（当时账只剩 R5 / R6）
npm run content:report       # 这两门的覆盖率从 0/104 涨到 104/104
npm run build && npx vitest run
```

**过程中沉淀的八条差异重心**（写 `mechanism` / `practice` 时反复用到，
也是这一批内容里信息量最集中的地方 —— 前四条来自 `express` + `model`，后四条来自 `mechanism`）：

| 重心 | Rust | Go |
| --- | --- | --- |
| 可变性 | `let` 默认不可变，`mut` 是加出来的许可；不可变是**深**的 | 没有「不可改绑的变量」，`const` 是编译期常量 |
| 空值 | 既无 `null` 也无 `undefined`，用 `Option<T>` | 无 `undefined`，用**零值**；`nil` 只对引用类类型有意义 |
| 复用 | 无继承，trait（**显式实现**）+ 组合 | 无继承，嵌入 + 接口（**隐式满足**）—— 但不是子类型关系 |
| 集合语义 | 切片是**借用视图**；`Vec` 不可变时连 `push` 都不行 | 切片**共享底层数组**；结构体是**值类型**（赋值真的复制） |
| 内存 | **无 GC**：所有权 + 借用规则，释放点由编译器插入 | **有 GC**；但值/引用语义的显式选择承担了一部分「想清别名」的职责 |
| 并发 | 数据竞争是**编译错误**（`Mutex<T>` 把数据装在锁里） | goroutine + channel + `select`；锁与数据分离，靠 `-race` 兜底 |
| 异步 | 有 `async`/`await`，但**没有内建事件循环**（要 tokio）；取消 = drop | **没有异步函数这一层**：阻塞即正常，并发靠 `go`；取消靠 `context` |
| 元编程 | 编译期宏（无运行时反射、无 eval） | 有运行时 `reflect`，但只到导出成员；无注解，靠标签 + 代码生成 |

**写这类「还空着的对比列语言」时的注意点**（这一批开始时 rust / go 就是这种状态）：
它们当时已是 `enabled: true`，所以在左栏的对比语言选择条里可见、勾上会得到整列留白。
这在内容补齐前是可接受的（R20g 就是为这个状态设计的 warn），
要临时藏起来把那两行改成 `enabled: false` 即可，**不需要改任何代码**。
> **但 R22 / R23 在 S8 翻成 error 之后，这条捷径变了**：新启一门语言会立刻让构建失败，
> 必须先把内容写全。这是刻意的 —— 见 §6.3。

**第 1 项落点在左栏顶部、`position: sticky; top: 0`。** 之所以不是顶栏：
顶栏是**定高单行**的（`--pc-header-h` 这个常量被侧栏与矩阵表头的吸附位置读着，
不能靠换行解决），要多塞一组控件只能挤压导航 —— 试过之后发现
左栏才是它该在的地方：左栏正是**当前基准的**目录。
两个必须记住的实现细节：

- **`.pc-side`（滚动容器）的上内边距必须为 0**，那截间距由吸顶块自己带。
  留着 `padding-top` 的话，块在 `scrollTop=0` 时停在自然位置（上沿 + 14px）等于没吸住，
  吸顶前后差一截；实测过：`scrollTop=200` 时块的顶边停在 66 而不是 52。
  （**订正**：早先这里写成「sticky 的边界只能落在内容盒上沿」，把原因说反了 ——
  见下面第 12 项。）
- 吸顶块**必须自带不透明底色**，否则滚过去的菜单项从它身下透出来。

**已知代价（刻意接受）**：左栏收起时基准入口一并消失；窄屏（≤900px）下左栏是
正文上方的普通块、不吸顶。两处都与左栏本身的形态一致，不额外补入口。

**第 2 项改的是真源，不是显示层**：`registry.gen.ts` 的 `allLanguageIds` /
`enabledLanguageIds` / `languageMeta` 全部改按声明序排，于是基准候选、对比语言条、
矩阵列、首页三张基准卡一次到位。**踩到的坑**：一度想「按 registry 声明的 id 列表去装载
meta」，那会让「登记了但目录不在」先抛 ENOENT，把 R8 那条人话报错盖掉 ——
改成**先按目录装载、再重排**。

**第 3 项的判据与列裁剪同源**：章节型板块传进来的 `available` 用 `hasChapterContent`

这条规则真正的价值在**下一门语言刚启用、内容还没铺**的时候。

**第 4 项是一次删除，不是隐藏**：`diff.ts`（含缓存）、`DiffFilterBar.vue`、
`CodeBlock` 的 `diffs` / `blocksMismatch` / `paintDiff` / `diffSummary`、

`baseline-switch.test.ts` 里 diff 那 2 条，新增顺序断言后净减 10）。

**第 5 项的位置**：它与对比语言同一行、靠右。**只对章节型板块渲染** ——
速查三兄弟是一篇一篇文章，没有「排法」可切，给它们一个切了没反应的控件就是坏控件。

**第 6 项为什么不纯 CSS**：纯 CSS 做不到「有溢出才显示」—— `scroll-state()` 还没落地，
`:has()` 问不出布局。所以量一次 `scrollWidth`，并跟着滚动更新两端状态，
让遮罩在拖到那一头之后**自己消失**（一条永远挂着的「可左右拖动」，在拖不动时就是假话）。
提示文字只在**第一排**出现：一页有六七个 feature 面板，每个各挂一句同样的话就是噪声。

**第 8–9 项（第二轮反馈）—— 两个选择器长得一样、且等高。**
基准选择器原先用连体分段控件，想靠「实心 vs 浅色」说明它与对比语言是两个层级；
实测那个信号太隐晦，改成同一套 `.pc-btn` chip + 同一个方框外观。
等高**必须右向左看齐**：先按 `--pc-lang-bar-h` 把左栏方框拉高是错的方向 ——
左栏内容被撑开、上方多出一截空白，而页内那条一折行就把值带跑。正解是两边共用
同一套 chip 与同样的纵向 padding（6px），高度都落在 `.pc-btn` 的 29.6px 上，
恒为 **43.6px**，实测两边 `top/bottom` 完全相同（52 / 96）。
**`padding-top` 必须为 0** —— 这句只对 `.pc-side`（滚动容器）成立，
**对吸顶块自己是反的**：块的 `padding-top` 正是第 12 项用来留「离顶间隙」的手段，
机制的订正见下面的第 12 项。

**第 11 项查出来的是一个真 bug**：给 `pre.shiki` 加 `padding-right` 在**行号模式下
根本看不见** —— `pre` 是块级、宽 100%，横向溢出的是里面那层 `code`（长行），
滚到最右看到的是 `code` 的右沿，`pre` 的留白被它盖在后面。实测只剩 **1px**。
让 `pre` 自己也贴合内容（`width: max-content`）之后，留白成了溢出内容的最右一截，
实测变成 **16–17px**（逐块量过 8 个）。

**第 12 项（第三轮反馈）—— 吸顶时离顶留一截间隙。**
做法是给两个吸顶块各加 `padding-top: var(--pc-sticky-gap)`（8px，写进 `tokens.css`）。
sticky 约束的是块的**边框盒**：块吸在滚动口上沿之后（页内那条吸在 `--pc-header-h`，
左栏那条吸在自己的滚动口上，那个口的上沿与顶栏下沿重合），方框由这段上内边距往下推。
因为块自带不透明底色，那 8px 是「带状底」而不是缝 —— 滚上去的菜单项与正文标题从它
底下过，不会透出来（实测：左栏 `scrollTop=300` 时方框上沿仍是 60，缝里没有文字）。
**页内那条因此拆成两层**（外层吸顶留间隙、内层 `.pc-lang-bar-box` 才是方框）：
边框与圆角都在方框上，合在一层的话那 8px 会落进边框里，看起来只是内边距变大，
而不是「离顶有段距离」。实测两边方框上沿都落在 **y=60**（顶栏下沿 52 + 8）、
高都 **43.6px**，页内那条的实测高度（`--pc-lang-bar-h`）随之变成 **55px**
（= 8 + 43.6 + 3 的下间隙，表头落点跟着下移同样多）。

**订正第 1 项里「sticky 的边界只能落在内容盒上沿」那句**：那句话把 14px 缝隙的
原因说反了。真实原因是当时 **`.pc-side`（滚动容器）** 带了 `padding-top`，
吸顶块在 `scrollTop=0` 时停在**自然位置**（52 + 14 = 66），压根没吸住。
同一件事放在**吸顶块自己**身上则是正确用法 —— 第 12 项正是靠它留出间隙。
`.pc-side` 的 `padding-top` 依然必须为 0，但理由变了：这个滚动口的上沿要与顶栏
下沿重合，左右两个吸顶块才是同一个基准（都从 52 起算）。

##### 轮 ② 的对比轴比计划里写的更锋利

计划把轮 ② 定为「现代 GC 虚拟机语言的两种调度模型」，实际写下来，
真正的分水岭落在 **`async/cancellation`** 与 **`concurrency`** 两组上：

- **取消**：Kotlin 是**协作式真中断**（下一挂起点抛 `CancellationException`），
  Dart 的 `Future` **一旦创建就跑到底、没有任何取消 API** ——
  整个 `dart:async` 里找不到 cancel。能真取消的只有流订阅，
  另一个包里的 `CancelableOperation` 取消的也只是「结果的交付」。
  **两边的「取消」根本不是同一个词。**
- **共享状态**：Kotlin 的协程**可以**并行，但**不是默认** ——
  `launch` 不带调度器时继承外层的调度器，在一个单线程的事件循环作用域里
  （比如 `runBlocking { }` 里）就是排队执行，**这一点我最初写反了**，
  而且反得很难看：我自己那段示例代码用的是 `runBlocking`，
  正文却说「默认会并行」，**代码与论断互相打脸**（核实代理抓出来的，见下）。
  正确的口径是「要真并行得显式给多线程调度器」；
  一旦给了，`@Volatile` 就不够、`synchronized` 会阻塞线程要换挂起的 `Mutex`；
  Dart 把共享内存整个拿掉，于是 **`lock-mutex` 与 `atomicity` 两格写 `absent: true`** ——
  不是「还没写」，是**语言把问题从根上去掉了**（官方原话是「没有共享状态意味着
  互斥锁、锁与数据竞争都不会发生」），三份 vs 里交代替代方案
  （把状态关进一个 isolate、靠消息改）。

##### 一条**架构边界**，本轮踩到并记下来

`@note` 的解析要求标记出现在**该语言自己的注释前缀**之后（Dart 是 `//`）。
而 Dart 生态里 `pubspec.yaml` 用 `#`、shell 命令也用 `#` ——
于是这些代码块里的 `@note` 全部残留，`content:validate` 报了 **12 条 R4/R9 error**。

这是设计使然（R4/R9 正是为了防「前缀写错导致注记静默丢失」），
但它意味着**一类内容根本用不了注记机制**：语言生态里那些注释语法与语言本身
不同的配置文件。本轮的处理是把标记换成普通注释文字（`@note!` 改成「注意：」
保留强调，`@note` 直接去掉标记）—— 信息没丢，只是不再进注记抽取与搜索索引。
**将来若有第二门语言撞上同样情况，再考虑给 `meta.comment` 加一个备用前缀**
（那属于架构改动，要补 ADR）。

- **R22（`vs` 完整性）/ R23（基准列非空）的级别** —— 迁移期定为 warn（沿用旧 R18/R19 的策略：

- **`_template` 脚手架在新目录结构下的形态** —— 已定：`languages/_template/<板块>/<group>.yaml`，
