## 0. 项目速览

一句话：**选一门基准语言，沿六个板块并排对照目标语言，突出差异，让已有知识快速迁移。**

```
顶栏：☰ · 站点名 · 首页 · 多语言对比 · 速查 · 内容来源
左侧（「多语言对比」的子菜单，顺序 = 迁移者的学习路径）：
  迁移学习路线 → 基础语法 → 心智模型 → 迁移教程 → 迁移陷阱 → 速语词典

每个板块页内：以 X 为基准 · [Y][Z][…]   ← 基础语法与心智模型多选，其余四个单选
/compare/<基准> 落到「迁移学习路线」—— registry 里声明 landing: true 的那个板块
```

**板块顺序按学习路径排，不按内容形态排**（ADR-32）：先给总纲（我该按什么顺序迁），
再给两个基准级板块（基础语法逐条讲语法、心智模型讲语言之间的根本差异），
最后是三个对级板块（按主题、按症状、按术语）。站点落点之所以是路线，
是因为从「我要迁移」进来的人最缺的是顺序，不是某一章语法。

| 维度 | 现状 |
| --- | --- |
| 板块 | 6 个（**可注册的数据**，见 §2.3） |
| 基准语言 | JS（默认）/ Python / Java —— 三选一，**进 URL** |
| 对比语言 | 个人偏好，**不进 URL**，由页内选择条决定 |
| 语言 | 全集 10 门，启用 5 门（js / python / java / rust / go） |
| 内容 | 198 Feature / 612 实现，覆盖率 5 门语言均 100% |
| 审阅 | reviewed 120 / draft 492（策略 `include-draft-with-badge`） |
| 路由 | 212 条可索引 + 38 条仅预渲染 |
| 测试 | 122 条，含两条扩展性断言（`verify:ext` / `verify:sections`） |

## 1. 项目定位

### 1.1 目标用户与核心场景

| 项 | 内容 |
| --- | --- |
| 用户 | 有 JS/TS 基础、计划学其它语言的开发者 |
| 痛点 | 多语言语法并行学习时混淆、记不牢；官方文档按语言组织，不做跨语言对照 |
| 核心场景（按频次） | ① 忘了某语言怎么写某个东西 → 秒查；② 学一门新语言时按章节系统对照；③ 迁移中踩坑 → 按症状检索 |
| 使用姿势 | 桌面浏览器为主，移动端为阅读降级场景 |

**术语**：**基准语言**（baseline）= 被选为参照系的那一门；**目标语言**（target）= 与基准对照的那一门。二者是**内容维度**（每个基准有各自的一套内容与地址），不是运行时可变角色。

### 1.2 成功标准（可验收）

| # | 标准 | 验收方式 |
| --- | --- | --- |
| S1 | 打开任一章节深链，一次滚动内看清「该特性在各语言里怎么写、差异在哪」 | 人工走查 |
| S2 | 新增一门语言只改 `content/`，`npm run verify:ext` 通过 | 脚本断言 |
| S3 | 新增一个板块只改 `content/`，`npm run verify:sections` 通过 | 脚本断言 |
| S4 | 375px 宽视口可完整阅读任一章节，无横向溢出 | 移动端走查 |
| S5 | 内容准确：每条断言的代码都实跑过 | `content:report` 的 reviewed 比例 |

### 1.3 非目标（明确不做）

在线运行代码（只留接口）、账号与云同步、社区评论、**内容的多语言翻译**、原生 App、后端服务。

## 2. 内容模型

### 2.1 四个层次

```
topic ──▶ chapter ──▶ feature ──▶ snippet[lang]
（一套内容）（一章）   （一个对照点）（某语言的实现）
```

- **topic** = 一套内容。目录名即 id（`content/topics/<topicId>/`）
- **chapter** = 一章，一个 YAML 文件，`features` **内联**在其中（不再拆 feature 文件 —— 那需要跨文件手工同步 id）
- **feature** = 对比的最小单元 = 矩阵的一行
- **snippet** = 某门语言对某条 feature 的实现 = 矩阵的一格

**这套骨架是通用的**：迁移教程、高级语法、实战对比都复用它，因此免费获得校验、分片、搜索索引、行级 diff、`@note` 抽取、等价性徽章。

### 2.2 三轴：`section` / `baseline` / `target`

写在 `content/registry.yaml` 的 `topics` 段：

| 字段 | 含义 |
| --- | --- |
| `section` | 属于哪个板块（必须是 `sections` 段里已注册的） |
| `baseline` | 基准语言（from）。所有 topic 必填 |
| `target` | 目标语言（to）。`scope: pair` 的板块必填、`scope: baseline` 的必须缺省 |
| `languages` | R2 覆盖率的计算范围，缺省 = 全部已启用语言 |

**为什么 `target` 不进 URL**：它是「我现在想看哪个方向」，写进地址会让同一份内容散成 12 个地址，并让基础语法（多列并排）与对级板块（一篇文章）出现两套互不相容的 URL 语义。方向由运行时 `resolvePairTarget` 推导（最近挑的那门 → 已勾选里第一个该板块有内容的 → 该板块第一个可用方向）。

### 2.3 板块注册表

**板块是可注册的数据，不是写死的枚举。** 声明在 `registry.yaml` 的 `sections` 段：

```yaml
sections:
  basics:
    order: 1
    label: 基础语法          # 左栏短名
    title: 基础语法对比      # 页面标题
    shape: chapter           # chapter（有章节）| list（一页列表资源）
    scope: baseline          # baseline（以基准为参照、可多门并列）| pair（锁定两门）
    columns: multi           # multi（多选并排）| single（单选）
    seo: { title: "...", description: "..." }
```

**三个属性刻意分开，不能互相推导** —— 它们曾一起被压成 `section === 'basics'` 这一个判断，于是「基准级 + 单选」这类组合无法表达：

| 判据 | 读哪个属性 |
| --- | --- |
| 语言控件是否多选 | `columns` |
| 有没有「方向」概念（要不要 `resolvePairTarget`） | `scope` |
| 取章节分片还是整页列表 | `shape` |
| `/compare/<基准>` 落到哪 | `landing`（至多一个板块声明，见下） |

拆分的价值在**第二个基准级板块**（心智模型）出现时才真正兑现：它与基础语法同形，
却既不是 `basics` 也不是「对级」，此前那个 `section === 'basics'` 的判据在
`analyze.ts`、`content-contract.test.ts` 等处都会误判（ADR-28 已修正）。

**`landing: true`**：站点落点是**策展决策**（从「我要迁移」进来的用户最该先看到什么），
所以写成数据而不是在路由里点名 `'roadmap'` —— 换一个只该改 registry 一行；
写死 id 还会让 `verify:sections` 的白名单多一条「这里为什么可以出现板块名」的注解。
至多一个板块声明它（`registrySchema.superRefine` 会拦重复，否则会静默按 order 取第一个）；
一个都没声明时回落到「第一个章节型板块的首章」，即这个字段出现之前的行为。

派生链路：`registry.yaml` → 构建期生成 `src/generated/sections.gen.ts`（`SectionId` 联合类型）→ 编译进 `manifest.sections` → 客户端遍历 `orderedSections()` 排左栏、`SectionDispatchView` 按 `shape`/`renderer` 选组件。

> **类型与成员资格刻意分开**：`SectionId` 是生成的联合类型（保住 `section: Section` 的赋值检查），但 `sectionSchema` **不是** `z.enum(生成的清单)` —— 那会让 `content:validate`（跑在生成之前）拿上一版清单校验新内容，新增板块报「invalid enum value」这种指向错误原因的错。成员资格改由 `registrySchema.superRefine` 读当次 YAML 判定，生成物是否过期由 `verify:sections` 断言。

### 2.4 覆盖层（snippet 文件）

```
content/languages/<lang>/snippets/<topicId>/<NN>-<chapter>.yaml
```

文件顶层是**对象**：

```yaml
topic: basics-javascript        # 必须与目录名、与每条 featureId 前缀一致
review:                         # 文件级默认，条目可各自覆盖
  state: draft
  provenance: { origin: llm, model: ..., promptTemplateId: ..., generatedAt: ... }
snippets:
  - featureId: basics-javascript/var-declaration
    equivalence: divergent
    code: |
      let count = 0;    // @note 事实性提醒贴着那一行
    body: |
      这一列整体上是什么、和对面差在哪（受限 Markdown，渲染在本列代码下方）
```

四点设计：

1. **按 topic 分目录** —— 文件名只表达「第几章」。此前的平铺布局里文件名必须自己携带 topic 信息（出现过 `13-basics-python-01-variables.yaml` 这种拼名），且序号是**语言目录内的局部序号**，同一序号在不同语言下指向不同 topic
2. **`review` 可提到文件级** —— 同批生成的条目 provenance 往往逐字相同，一份 5 条的文件要抄 5 遍，全仓库曾因此重复 456 处
3. **`topic` 显式声明** —— 让 featureId 前缀有了可校验的来源（R15），而不是靠人记住目录约定
4. **`body` 一个字段两种角色**（ADR-35）—— 由「这一列是不是基准列」纯派生：基准列写本语言的客观事实，对比列写与基准的差别。多列板块的正文全在这一层，`feature.body` 只服务单列板块。贴着某一行的注意事项走代码里的 `@note`，不重复成段

### 2.5 列表型资源（陷阱 / 词典 / 路线）

与迁移章节**同放一个 pair 目录**，靠顶层是数组还是对象区分：

```
content/topics/js2python/
├── 01-functions.yaml    章节（顶层对象）
├── pitfalls.yaml        陷阱（顶层数组）
├── glossary.yaml        词典（顶层数组）
└── roadmap.yaml         路线（顶层数组）
```

**pair 归属由目录名反查 registry 得到，不写进每条 YAML** —— 同一条陷阱可能在多个方向成立，逐条写 `baseline`/`target` 会产生 12 份会各自漂移的副本。

### 2.6 等价性、注记、审阅

**`equivalence` 四态**是「与本 topic 的基准是否不同」的唯一判据：

| 值 | 含义 | 界面 |
| --- | --- | --- |
| `identical` | 同构，几乎可直接迁移 | `=` 绿 |
| `analogous` | 形似，结构相近但有关键差异 | `≈` 琥珀 |
| `divergent` | 语义不同，陷阱高发 | `≠` 红 |
| `absent` | 该语言没有这个概念 | `∅` 灰 |

`absent` **可以**给代码（表示「没有等价语法，这是惯用替代写法」），但必须用 `body` 说明。**基准列自己的 `equivalence` 恒为 `identical`**（它就是参照系，有测试钉住），页面上不渲染这枚徽章 —— 自指、零信息量。

**`@note` 内联标记**：差异说明写在代码里，不用行号锚定（行号会随编辑静默漂移）。构建期抽取**只剥掉标记本身**，两种语气的说明都**留在代码行内**贴着那一行读：

- 普通 `@note` → 说明原样留在注释里
- 高危 `@note!` → 同样留在行内，只是说明前多一个 `⚠`（同色、不额外着色）

高危项**曾**单独抽进代码块下方的说明栏；读者要在代码与说明栏之间来回跳，反而切断阅读，故取消该出口。抽取只剥标记而不整行搬走，**行数绝不能变**（行级 diff 与就近阅读靠它对位）。

**`review` / `provenance` 分离**：`review.state`（draft / reviewed / verified）表达校对进度，`provenance.origin` 表达来源。**`origin: llm` 刻意不填 `license`** —— 模型输出不产生可署名许可，强填 MIT/GFDL 是错误陈述，比留空更危险。合规责任由审阅记录 + 许可台账承担。

## 3. 数据流与分层

### 3.1 五个层次

```
L4 呈现层   views/ + components/
             只依赖 ContentRepository 接口与生成的静态注册表
L3 应用层   stores/ + composables/
             用户设置、当前基准/语言集、派生视图态（含运行时 diff）
L2 领域层   content/repository.ts  content/diff.ts
             取数契约 + 行级差异计算（纯函数，可单测）
L1 内容产物 src/generated/*（构建期生成，只读，不手改）
L0 内容源   content/**（YAML + Markdown，唯一人工编辑入口）
```

依赖方向严格单向：L4 → L3 → L2 → L1 →（构建期）L0。**禁止**：L4/L3 直接读 YAML；手改 L1；`content/` 里出现可执行代码。

### 3.2 构建期（唯一的内容真源路径）

```
content/**/*.yaml
   │
   ├─▶ [1] validate    R1–R17 规则集，error 级非零退出（CI 阻断闸门）
   │
   ├─▶ [2] generate    sections.gen.ts（SectionId）→ registry.gen.ts（LanguageId + 常量）
   │
   ├─▶ [3] highlight   Shiki 构建期预高亮（css-variables 主题，单份 HTML）
   │
   └─▶ [4] emit
         src/generated/content/<topicId>/<chapter>.json   一章一个分片
         src/generated/static/<基准>--<目标>.json          对级：陷阱/词典/路线
         src/generated/search-index/<基准>.json            搜索倒排索引，按基准分片
         src/generated/manifest.json                       ★ 路由/SEO/板块/topics 的单点来源
         src/generated/registry.gen.ts  sections.gen.ts  i18n.json  attributions.json
         public/sitemap.xml（需 PC_SITE_URL）

   └─▶ [5] prerender   （vite-ssg，`npm run build` 的一部分）
         dist/<route>/index.html     含真实内容的静态 HTML
         dist/404.html               GH Pages 的 SPA fallback
```

**`src/generated/` 是唯一的分界点**：左边是作者的世界（YAML），右边是程序的世界（JSON/TS）。跨越只能由 `npm run content:build` 单向完成 —— 这消灭了「改了 YAML 但忘了重建」导致的幽灵内容。

**`manifest.json` 是多处单点来源**：`routes`（预渲染与 sitemap 共用）、`pairs`（左栏与死链防护共用）、`sections`（板块属性）、`seo`（静态注入与运行时 `usePageMeta` 共用同一份文案）。

### 3.3 运行期

```
App boot
  └─ manifest.json + registry.gen.ts（随主包）
       ├─ 恢复用户设置（pc:v1:*）
       └─ router 解析
            └─ 守卫：解析方向 → 按需 import 分片 → 视图同步渲染
                 ├─ SectionDispatchView 按板块的 shape/renderer 选组件
                 ├─ 行级 diff 按需计算（jsdiff）+ 缓存
                 └─ 交互 → usePersistedState 回写
```

**守卫里完成取数**（而不是组件内 `await` / `<Suspense>`），是为了让 SSG 与 CSR 走同一条路径 —— 否则预渲染出的 HTML 与客户端渲染结果会不一致。

### 3.4 产物与体积

| 产物 | 体积 | 装载 |
| --- | --- | --- |
| 内容分片 | 单章 69–107 KB / **gzip 8–11 KB** | 路由级动态 `import()` |
| 对级静态资源 | 按 `(基准, 目标)` 拆文件 | 按需 |
| 搜索索引 | `javascript` **249 KB(gz)** / `python` **145 KB(gz)** / `java` **136 KB(gz)** —— 三个分片全超预算，最大的一片是红线的 2.8 倍 | 进 `/search` 才下载 |
| Shiki 高亮 HTML | 709 KB → gzip 77 KB（**约 9:1**） | 已内联进分片 |

## 4. 内容编译管线

### 4.1 脚本

```
scripts/
├─ pipeline/
│  ├─ 03-validate.ts       跑规则集，非零退出供 CI
│  ├─ 04-build.ts          合并 → 抽取 @note → 渲染 Markdown → Shiki → emit
│  ├─ search-index.ts      倒排索引（bigram 分词，按基准分片）
│  └─ content-report.ts    覆盖率 / 审阅状态 / 待校对清单
├─ build/
│  ├─ generate-registry.ts → registry.gen.ts（LanguageId 与站点常量）
│  ├─ generate-sections.ts → sections.gen.ts（SectionId），**零 import**（避免与 schemas 成环）
│  └─ finalize-dist.ts     预渲染产物收口：注入 title/description、404.html、**逐路由内容验收**
├─ lib/                    装载 / @note 抽取 / Markdown + Shiki 渲染 / 分析 / 环境变量
├─ verify-extensibility.ts      断言「加语言只加数据」
└─ verify-section-extensibility.ts  断言「加板块只加数据」
```

### 4.2 校验规则集

全部集中在 `scripts/lib/analyze.ts`，`validate` 与 `build` 共用同一份 —— 改校验只需改一处。

| 规则 | 管什么 | 级别 |
| --- | --- | --- |
| R1 | 结构（loader 的 Zod 解析） | error |
| R2 | 覆盖率：适用范围内不能有空洞 | error |
| R3 | provenance 完整性 | error |
| R4·R9 | `@note` 标记的前缀与解析（组合 id，从不单独出现） | error |
| R5 | 引用完整性（孤儿 snippet、未知语言、对级词典只讲本方向两门） | error |
| R6 | 发布门槛（`reviewed-only` 下 draft 阻断） | error |
| R7 | URL 白名单（必须 https） | error |
| R8 | 命名与一致性（topic 目录、章节 id 前缀、基准候选） | error |
| R10 | 许可台账 | error |
| R11 | `equivalence` 非 `identical` 却一条注记都没有 | **warn** |
| R12 | 基准列的注记点名了屏幕外的语言 | **warn** |
| R13 | `featureId` 前缀必须等于所属 topicId | error |
| R14 | topic 的 `section` 必须已注册；`scope: pair` 必须声明 target | error |
| R15 | 覆盖层文件的 `topic` 声明与目录、与每条 `featureId` 前缀一致 | error |
| R16 | `code` 与 `blocks` 二选一；多段每段必须有 `label` | error |
| R17 | 校对状态升级了却没留 `reviewedBy` / `reviewedAt` | **warn** |

R14 与 R16 落在 **schema 层**（`registrySchema.superRefine` 与 `refineSnippet`）—— 它们是单条数据自身的自洽性，不需要跨文件视野。

### 4.3 两条可执行断言

把「加 X 只加数据」从口号变成 CI 可断言的事实：

| 脚本 | 做法 |
| --- | --- |
| `npm run verify:ext` | 造一门临时语言 → 断言 `src/`（不含 generated）里没有任何代码提到它；扫描**真实启用语言 id** 的字面量（`if (baseline === 'javascript')` 这类写死基准的分支是它抓的）；再扫**面向用户的文案**（i18n 的值 + `.vue` 的 `<template>`）里有没有写死语言**显示名** —— 三门基准权重相同，`PitfallCard` 的徽章曾硬编码「JS 开发者必踩」，在 java2python 页面上照写 JS，就是这条抓的 |
| `npm run verify:sections` | 扫描 `src/` 里硬编码的板块 id 字面量（白名单每条写了理由）；断言 `sections.gen.ts` 与 `registry.yaml` 同步；断言每个 topic 的 section 都已注册 |

> 前两条扫描**刻意保持朴素**：不剥注释、不做语法分析 —— 剥离注释会引入「字符串里含 `//` 被当成注释吃掉」这类假阴性，而它们的全部价值就在「宁枉勿纵」。
> 第三条（文案里的显示名）反过来**必须剥注释**：代码注释里拿「从 JS 出发」举例是给维护者看的，不是文案。它因此把范围收窄到「会被用户读到」的两处（i18n 的值、`.vue` 的 `<template>`），代价是写在 `<script>` 里的字符串不在覆盖范围内。

## 5. 运行时架构

### 5.1 URL 规则

```
/compare/<基准>/<板块>              列表型；章节型的**入口**（守卫重定向到首章）
/compare/<基准>/<板块>/<章节 slug>   章节型
/compare/<基准>                     落到该基准下第一个有内容的板块，起点是 landing 板块
/lang/<语言>   /feature/<topicId>/<slug>
/search   /attributions
```

`/compare/<基准>` 的落点由 `compareEntryPath()`（`src/router/index.ts`）决定：
从 **landing 板块**（registry 里 `landing: true` 的「迁移学习路线」）起找，
找不到就顺着 order 往后走 —— 骨架期某个基准可能没有该板块的方向，
直接取会得到一页空白。顶栏「多语言对比」与首页的基准卡片**复用同一个函数**，
所以「点导航」和「敲地址」必然落到同一处。

注意它与 `firstChapterSection()`（`repository.ts`，按 order 取第一个 **chapter 型**板块）
是两件事：后者用于「切基准时保留章节语境」（`useBaselineSwitch`）与语言页的
「以它为基准浏览基础语法」入口 —— 那里的语义确实是「第一个有章节的板块」，
不是「站点落点」。这个区分是有意的，不要合并。

**地址里只有基准，没有目标语言。** 基准进 URL 是因为每个基准是一套独立内容（要能预渲染、能分享）；目标不进 URL 是因为它是「我现在想看哪个方向」，且写进去会让基础语法与对级板块出现两套互不相容的语义。

**旧地址**（`/compare/<topicId>/<slug>`、`/pitfalls`、`/roadmap/<lang>`）由守卫分流重定向，并预渲染出外壳（静态托管做不了 301）。

### 5.2 路由与板块分发

路由只有**两条**（章节型 / 列表型），板块是 `params.section`：

```
/compare/:baseline/:section/:chapterSlug   → SectionDispatchView
/compare/:baseline/:section                → SectionDispatchView（+ 板块入口 + 旧地址，由守卫分流）
```

`SectionDispatchView` 按板块注册表的 `shape` 与 `renderer` 选组件：

- `shape: chapter` → **默认** `ChapterCompareView`（新的章节型板块零代码复用）
- `shape: list` → 查 `RENDERERS` 映射表（`pitfalls` / `glossary` / `roadmap` 各一个）

列表型**刻意没有默认渲染器**：三种列表的交互差异很大（陷阱有搜索与严重度筛选、路线有进度持久化、词典是简单词条列表），硬套一个通用模板会把它们削平成最弱的那一个。

**守卫里有一条必须遵守的规则**：列表型分支必须 `return true`，不能返回 `sectionEntryPath(...)` —— 列表型板块的「入口地址」正是当前地址，返回它等于自我重定向，vue-router 会判定无限重定向并 abort 导航。

### 5.3 状态模型

| 状态 | 归属 | 持久化 | 说明 |
| --- | --- | --- | --- |
| `lastBaseline` | languageStore | ✅ | 只记「上次选的是谁」，供无基准的路由用 |
| `compareLangs` | languageStore | ✅ | 基础语法的**多选**列 |
| `preferredTarget` | languageStore | ✅ | 对级板块的方向，**跨板块共享** |
| `viewMode` / `density` / `theme` | uiStore | ✅ | 三个正交设置 |
| `routeBaseline` / `routeSection` | languageStore | ❌ | 由 App 的路由 watcher 写入 |
| 章节内容 | contentStore | ❌ | 路由驱动，切走即释放 |

持久化统一经 `usePersistedState`（基于 `@vueuse/core`），key 前缀 `pc:v1:`，版本不兼容即**直接丢弃**（单用户工具，迁移成本 > 收益）。

**两条容易踩的时序**：

1. **守卫里要算目标时必须传路由里的基准** —— 守卫跑在 App 的路由 watcher 之前，那时 `routeBaseline` 还是 null，`effectiveBaseline` 会落到 localStorage 的「上次选择」上，用错基准就会加载另一套分片，页面**静默变空白**
2. **换方向不产生导航** —— 目标不进 URL，路由守卫不会重跑。所以对级视图必须用 `usePairPayload` 或 `content.ensurePair` **按需加载**，只靠守卫的话页面同样会静默空白

### 5.4 差异机制（5 层，职责互斥）

| 层 | 机制 | 数据来源 | 时机 |
| --- | --- | --- | --- |
| L1 | 等价性四态徽章（颜色 + 图标 + 文字三重编码） | `snippet.equivalence`（手写） | — |
| L2 | 行级 diff 高亮 | 运行时 `diff.ts`（jsdiff） | 运行时 |
| L3 | 「只看有差异的项」过滤 | 由 `equivalence` 派生 | 运行时 |
| L4 | 行为差异内联注释（`@note`） | 构建期抽取 | 构建期 |
| L5 | 无等价说明（`absent` + 替代做法） | `snippet.body` | — |

**diff 刻意留在运行时**：基准可切换、对比列可多选、展示模式会变，预计算是几十种组合的浪费。用 `diffArrays` 逐行对齐，**不要换回 `diffLines`** —— 它会把相邻的删除+新增合并成块，让完全相同的行也被标成「不同」（有回归测试）。

**多段代码（`blocks`）逐段 diff**：每一段有自己的行号空间，拼接起来整体算的行号对不上任何一段（着色会整体错位）。所以两侧段数一致时按序号逐段算；段数不同时**不做 diff**并说明「分段结构不同，未做逐行对照」—— 宁可不着色，也不给出错误的对位。

### 5.5 代码展示

| 项 | 决策 |
| --- | --- |
| 高亮 | Shiki **构建期**预高亮，`css-variables` 主题（单份 HTML，明暗靠 CSS 变量切换）；Shiki 是 devDependency，不进客户端包 |
| 字重补偿 | 该主题不输出 font-style/font-weight，靠 CSS 属性选择器按 token 变量名补偿；补偿失效时 `render.ts` 自动降级为双主题 |
| 行级 diff | 客户端在渲染后按行号给 `.line` 补 class（预渲染出的 HTML 没有色块，但内容完整，不影响索引） |
| 复制 | 复制**原始 code**（非高亮 HTML），已剥离 `@note` 标记；高危注记的 `⚠` 在 code 内，会一并被复制 |
| 多段 | 每段一个代码块，段间细线分隔，段标签在块上方 |

## 7. 非功能要求

### 7.1 性能预算与实测

| 指标 | 预算 | 实测 |
| --- | --- | --- |
| 单章内容分片（gz） | ≤ 60 KB | **8–11 KB** |
| 搜索索引单分片（gz） | ≤ 90 KB | **249 KB —— 超预算**（三个基准分片全超线，见 §9） |
| 首屏 JS（gz，不含按需分片） | ≤ 180 KB | `vite build` 报告 |
| LCP / INP / CLS | 2.5s / 200ms / 0.1 | Lighthouse |
| 切语言列 / 基准 | ≤ 100 ms | Performance 面板 |

### 7.2 可访问性

不以颜色为唯一判据（四态徽章 = 颜色 + 图标 + 文字）；表格用真 `<table>` + `th[scope]`；横向滚动区 `role="region"` + 键盘可达；全站可 tab、`:focus-visible` 有可见焦点环；尊重 `prefers-reduced-motion`。目标 WCAG 2.1 AA 关键项。

### 7.3 安全

纯静态站点无后端 ⇒ 无认证/越权风险。真实威胁面是**内容注入**（LLM 产出 → Markdown/HTML → 渲染）：

- 富文本走 `markdown-it` 且 **`html: false`**（禁裸 HTML）
- `v-html` 的唯一合法输入是构建期产物（Shiki 输出与渲染后的 Markdown），集中约束在 2 个组件里
- CSP 用 `<meta http-equiv>` 兜底（GH Pages 无法下发响应头）；已知限制：meta CSP 不支持 `frame-ancestors`
- 不引入任何第三方 CDN / 字体 / 分析脚本

### 7.4 SEO

预渲染是**硬需求**（纯 CSR 对不执行 JS 的爬虫等价于空页面）：

- 每条路由产出含真实内容的静态 HTML（`vite-ssg`），CSR 仅作水合层
- `manifest.routes` 是**可索引路由的单点定义**，预渲染与 sitemap 共用 → 不可能不一致
- `prerenderExtra`（预渲染但**不进 sitemap**）：`/search`（结果是客户端渲染的，爬虫只会看到空输入框）、迁移方向的特性页（与章节页高度重叠）、旧地址外壳
- `dirStyle: 'nested'` 是**必须**的：默认 `flat` 产出 `.html` 后缀，而 GH Pages 不做无扩展名解析 → 只有首页能打开
- 构建最后一步逐路由**验收** HTML 里是否真含该页内容（空壳预渲染在这里失败）

### 7.5 i18n

UI 文案抽到 `content/i18n/zh-CN.yaml`，经 `t()` 取用；**内容本身不做多语言**（明确列为长期非目标）。注意 **i18n 文案是纯文本，不经过 Markdown 渲染**，写 `**强调**` 会原样显示。

**过程中确认的两条约束**（写在这里以免后来者重踩）：

  必须带章前缀（`types-intro` / `types-exercise`），否则 R8 报重复。

#### P12 · 搜索索引瘦身

**目标**：让每个分片回到 90 KB(gz) 红线内。

**现状（2026-10-02 全部内容补齐后）**：`javascript` **249** / `python` 145 / `java` 136 KB(gz)，
**三个分片全部超线，最大的一片是红线的 2.8 倍**。

三片从同一个模板生成，所以差距只反映**该基准下的内容总量**：
`javascript` 分片要装下 JS 基准的全部内容 —— 三套 `basics` 里它是自己的那一套、
三套 `concepts` 各有一份、再加上 **4 个 JS→X 迁移方向各 5 章**；
而 `python` / `java` 分片只装各自基准的那一套 `basics`、三套 `concepts` 里的份额、
以及 2 个迁移方向。

**这条曲线说明的是：索引体积与"该基准视角下的内容总量"成正比增长。**
每补一套基准级内容或一个迁移方向，对应分片就涨一块。
按现在的斜率，`javascript` 分片在 P12 动工之前还会继续涨。

| 工作 | 验收标准 |
| --- | --- |
| 把索引 `text` 从「全文」降级为 summary-only | 构建不再打印超预算告警 |
| 若仍超线 | 改按 section 域内检索（牺牲跨板块检索），并在 ADR 里记录这次反转 |

> **实测提醒**：全部注记文本仅 67 KB raw，占当时 javascript 分片 652 KB raw 的约 9%
> （补齐后为 718 KB raw）—— 单靠砍注记到不了红线，必须连 `feature.body` / `snippet.body`
> 一并处理。**内容补齐把这个问题的量级放大了**：当时只有 1 个分片超线、超 33%，
> 现在是 2 个分片超线、超约 60%。

| ADR-33 | 左栏在每个对级板块上显示**当前方向**；长章节加页内目录与锚点 | 目标语言不进 URL，而 6 个迁移方向的章节标题**完全同名**（都叫「1. 函数与参数传递」）—— 用户换方向后左栏一个字不变、只有正文换了，看起来像点错。页内目录同理：一章 9 个对照点实测 5600px 以上，左栏的章节级粒度帮不上 | 迁移方向之间出现不同名的章节（那时左栏本身就有区分度）；或章节短到一屏放得下 |
| ADR-34 | 可见列裁剪**不补位**：勾选的语言在本模块一门实现都没有时，只留基准列 | 曾经的兜底会从「全部已启用语言」里补一门有实现的当对比列，好让页面不退化成单列；代价是补出来那门用户既没勾、也去不掉（点它是「新增」而非「取消」），而选择条勾选态读 `compareLangs` —— 页面上并列着一列没勾上的语言，看着像控件失灵。`concepts-java` 让这层兜底**必现**：它只覆盖 js / java，默认对比语言 python 永不命中。覆盖面实情已由 `sections.scopeHint` 一句话交代 | 单列页被反馈成「像坏了」，且 scopeHint 不足以解释 → 改为在列头**标明补位来源**，而不是回到无提示的静默补位 |
| ADR-35 | **说明按列走**：多列板块（`columns: multi`）取消共享说明 `feature.body`，正文下沉到每列 `snippet.body` —— 基准列写本语言的客观事实，对比列写与基准的差别。`feature.body` 只留给单列板块（迁移教程，`exercise` 的题面也在那里）。事实性提醒改由代码内联 `@note` 承担，不再重复成段 | 一份横跨所有列的共享说明，在列数随勾选变化的板块里同时错三件事：① 盖不住各语言自己的事实，也放不下各自的差异；② 矩阵视图**根本没有渲染点**（`MatrixLayout` 不引用 `feature.bodyHtml`），同一份内容两种展示模式一个有一个没有；③ 矩阵恰恰是默认展示模式，于是**连迁移教程的共享说明在默认视图下也一直不可见**（本次顺带发现的既有缺陷，未一并修）。下沉后五门语言存储对称，渲染只剩 `CodeBlock` 一条路径 | 出现「需要一段跨语言共同导语」的多列板块 → 那时应在列上方**新增一个明确的共享位**，而不是把 `feature.body` 悄悄加回来 |
