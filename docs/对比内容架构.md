## 0. 一句话

**每门语言自带一份内容，内容是「本语言相对于三大基准语言的差异」。**
读者选一个基准，勾选若干对比语言，看到的是每一门「和基准差在哪」。

**章节分类也按基准各来一份**：用户熟悉的语言怎么组织知识，就怎么给他看左栏与矩阵的行（§2.5）。

三大基准：**JavaScript / Python / Java**，**固定不变**（即当前 `meta.yaml` 里 `baseline: true` 的三门）。

## 1. 设计出发点

### 1.1 定位：迁移者的地图，不是教材

本站**不承担「教会一门语言」的职责**。用户是已经会一门语言、要快速了解另一门语言的人，
目标是**建立地图**——知道对方语言长什么样、哪里和我的母语不一样、哪里会绊住我。
深入学习由用户去专门的教程站完成。

这个定位推翻了两个曾经的设计前提：

| 曾经的前提 | 现在 |
| --- | --- |
| 这个站是「顺序教程」，章节要有阅读顺序 | 它是**查阅型地图**，章节之间无强顺序 |
| 深度内容（长文、因果叙事）是护城河 | **广度与准确性**是护城河；深度让给教程站 |

它同时决定了内容形态：**矩阵（并排）优于文章**。概览要的就是一眼扫到全貌，
而文章是给「要学会」的人准备的。因此本架构**只有 1V多**（见 §2.2）。

### 1.2 旧架构的三个问题

1. **三块讲同一批东西。** `基础语法`（72 条）、`心智模型`（26 条）、`迁移教程`（6 方向 × 25 条）
   覆盖的是同一批语言模块（类型、容器、函数、错误、并发），只是各自换了个说法。
   读者面对同一主题有三个入口，而每一个都不完整。
2. **内容按方向组织，成本随语言数平方增长。** 加一门语言要建 N 个方向目录；
   6 个方向已经让 `migration` 板块有 6 份互相独立、会各自漂移的内容。
3. **「迁移」被做成了一个板块，而不是一种视角。** 结果另外两块（基础语法 / 心智模型）
   不得不用另一种口径写同一批内容，重复由此产生。

## 2. 核心模型

### 2.1 对比框：一个知识点在一门语言下的全部内容

**对比框（box）** 是本架构的最小单元 = **一个 feature × 一门语言**的格子。

一个框有三个槽位，**任意组合，全部可空**：

| # | 槽位 | 内容 | 载体 |
| --- | --- | --- | --- |
| ① | **代码** | 该语言在这个知识点上的写法 | `code` |
| ② | **注释** | 贴着某一行的提醒，写在代码行内 | 代码里的 `@note` / `@note!` |
| ③ | **说明** | 一段文字 | `baseline` 或 `vs.<基准>`（见 §2.2） |

- ① 和 ② 是耦合的：注释**内联在代码里**，不是独立字段（沿用 ADR-35，理由见旧文档 §2.6）。
  所以「有注释」隐含「有代码」。
- ③ 是**唯一一个按角色变化的槽位**，也是本架构与旧架构最大的差别。
- **三槽全空是合法的**，但必须显式声明 `absent: true`（见 §4.3）——
  否则视为「忘了写」，校验会报警。

### 2.2 两种角色：同一门语言，两种身份

这是本架构的枢纽。**同一门语言在不同时刻扮演不同角色，第 ③ 槽因此有两套内容。**

| 这门语言此刻是… | 第 ③ 槽写什么 | 字段 |
| --- | --- | --- |
| **基准列**（它就是被参照的那门） | **基础描述** —— 这门语言自己是什么 | `baseline` |
| **对比列**（读者从别处看过来） | **差异解释** —— 它和**当前基准**差在哪 | `vs.<基准 id>` |

**关键推论**：一门语言要为**每个基准**各准备一份差异解释。

```
Python 的内容里：
  baseline: |                     ← 当基准是 Python 时，Python 列显示这段
    Python 里没有 ===，== 是值比较…
  vs:
    javascript: |                 ← 当基准是 JS、Python 作对比列时，显示这段
      Python 没有严格相等，== 对值是值比较，对对象是引用比较…
    java: |                       ← 当基准是 Java、Python 作对比列时，显示这段
      与 Java 不同，Python 的 == 可以被 __eq__ 重载…
```

这三段文本是**同一件事的三种说法**，视角各不相同，无法互相推导 —— 所以必须分别撰写。
这是本架构最主要的内容成本（见 §7.1）。

**基准语言也有 `vs` 吗？** 有。JS 是基准，但当读者把基准切到 Python 时，JS 就成了对比列，
此时用 `vs.python`。所以 JS 的内容 = `baseline` + `vs.python` + `vs.java`。

### 2.3 组织单位是语言，不是方向

内容按**语言**存放。一门语言一个目录，自包含：

```
content/languages/javascript/     ← JS 的全部内容
content/languages/python/         ← Python 的全部内容
content/languages/rust/           ← Rust 的全部内容
```

**主内容里没有 `js2python/` 这样的方向目录。**
「从 JS 到 Python」不是一份内容，而是一次**查询**：基准取 JS 的内容作参照系，
对比列取 Python 内容里的 `vs.javascript`。
（唯一的例外是速查三兄弟，见 §4.5 —— 它们的主语本就是方向。）

由此：

- **加一门语言** = 加一个语言目录，`vs` 写满三门基准。线性成本。
- **基准固定为三门**（JavaScript / Python / Java），不增不减。这既是策展决定，
  也是成本决定 —— 加一个基准等于让**每一门语言各补一份 `vs`**，是 N 倍成本。
  定死之后，`vs` 的 key 集合是封闭的（至多三门），内容总量可预估（见 §7.1）。

### 2.4 板块

四个板块（第四版分类，按**迁移者先关心什么**重划）:

| id | 名称 | 章节 | 形态 |
| --- | --- | --- | --- |
| `express` | 基础表达 | 变量与绑定 / 类型与值 / 运算符与表达式 / 控制流 / 函数与参数 / 字符串与容器 | 1V多 |
| `model` | 数据与抽象 | 模块与导入 / 错误处理 / 集合与迭代 / 对象与类 | 1V多 |
| `mechanism` | 语言机制 | 泛型与接口 / 内存与所有权 / 并发 / 异步 | 1V多 |
| `practice` | 工程实践 | 包管理与依赖 / 构建与工具链 / 测试 | 1V多 |
| `pitfalls` `glossary` `roadmap` | 速查 | 陷阱 / 词典 / 路线 | **保留方向性** |

**分界依据**：`express` 是「能读懂对方在写什么」，`model` 是「能照着改写」，
`mechanism` 是「敢动它」（换语言必须重学的机制集中在这里），
`practice` 是「能落地」（换工具、但概念不变的部分）。

> **命名刻意是主题式的，不是「第一课 / 第二课」。** 本站是查阅型地图而非教程（§1.1），
> 四个板块表达的是**关注点**而非阅读顺序 —— 读者从任何一块进去都应当成立。
> 这条边界值得守：`先读懂 / 能改写 / 敢重构 / 能落地` 那样的措辞会把地图读成课程。

**速查三兄弟是唯一的例外**（见 §5.3）。它们天性是方向性的
（「从 JS 过来的人容易踩的坑」），无法按语言组织，因此保留 `scope: pair`。

### 2.5 章节分组按基准

内容按语言组织（§2.3），但**清单按基准各来一份**：Python 的视角下「变量与绑定」这一章
该带着 Python 的概念讲；Java 的视角下，同一批知识点按 Java 的心智模型重新分组。

实现上分两层：

| 层 | 文件 | 管什么 |
| --- | --- | --- |
| **feature 池** | `catalog/<板块>/features.yaml` | 这个板块有哪些知识点。**与基准无关，全站唯一** |
| **章节分组** | `catalog/<板块>/<基准 id>.yaml` | 该基准把池里的知识点分成哪几章、叫什么、什么顺序、取舍哪些 |

**关键性质（这是本轴的全部收益）**：池里的每个 feature 声明一个 `group`（**存放组**），
它是**内容的存放单位**，与展示无关。于是：

- 同一个 feature 在 JS 视角下可以落在「对象与原型」章、在 Python 视角下落在「类与继承」章，
  **而它的内容只写一份**，不会漂移。
- 加一门语言仍是线性成本（§7.1）；**分组的自由度不增加任何内容成本**。

代价是多了一层概念。作者要区分三件事：「这个知识点是什么」（池）、「它写在哪个文件里」（`group`）、
「它展示在哪一章」（每基准的章节分组）。前两件是写作时要想的，第三件是纯粹的策展工作 ——
它可以在内容写完之后再调，不动任何内容文件。

## 3. 目录结构

**清单与内容分离，存放与展示也分离。** 清单（有哪些知识点、怎么分组、什么顺序、叫什么）
集中在 `catalog/`；内容（每门语言怎么讲）按语言分散在 `languages/`。
改章节分组、调换顺序、改标题**只动 catalog，一个内容文件都不用碰**。

```
content/
├── registry.yaml                    # 站点级配置 + 板块注册表 + 语言启用开关
├── i18n/zh-CN.yaml
├── catalog/                         # ① 清单 —— 唯一真源，按板块一个目录
│   ├── express/
│   │   ├── features.yaml            #   池：知识点清单（与基准无关，全站唯一）
│   │   ├── javascript.yaml          #   该基准的章节分组
│   │   ├── python.yaml
│   │   └── java.yaml
│   ├── model/     （同构，S7 分批建）
│   ├── mechanism/
│   └── practice/
├── languages/                       # ② 内容 —— 按语言组织（1V多）
│   ├── _template/                   # 脚手架（私有目录，不参与构建）
│   ├── javascript/
│   │   ├── meta.yaml                # 语言元数据（baseline: true）
│   │   └── express/
│   │       └── bindings.yaml        #   文件名 = 池里的 group（存放组）
│   └── python/  java/  rust/  go/   （同构）
└── pairs/                           # ③ 内容 —— 按方向组织（唯一的 pair 级）
    ├── javascript2python/
    │   ├── pitfalls.yaml
    │   ├── glossary.yaml
    │   └── roadmap.yaml
    └── …其余方向

content.legacy/                      # 旧内容，构建与校验一律忽略
```

| 内容 | 路径 | 管什么 |
| --- | --- | --- |
| feature 池 | `catalog/<板块>/features.yaml` | 该板块有哪些知识点，每个属于哪个 `group` |
| 章节分组 | `catalog/<板块>/<基准 id>.yaml` | 该基准把池里的知识点分成哪几章、叫什么、什么顺序 |
| 一对多内容 | `languages/<语言>/<板块>/<group>.yaml` | 每门语言在各知识点上的内容 |
| 方向性内容 | `pairs/<基准>2<目标>/{pitfalls,glossary,roadmap}.yaml` | 速查三兄弟 |

四点约定：

1. **文件名不带序号** —— 序号会在增删章节时引发连锁改名（插一章，后面全体重命名），
   而顺序另有单一真源（章节分组里的数组顺序）。**章节 id 由章节分组自己声明**。
2. **板块从目录名取**，池与章节分组都不在文件内容里重复声明板块 —— 但**要声明自己的身份**
   （池声明 `section`，章节分组声明 `section` + `baseline`），因为它不再能只靠文件名唯一确定。
3. **一个板块的 `<基准 id>.yaml` 缺失 = 该基准在这个板块还没有章节**，视为未开工，
   左栏整组隐藏。占位文件不是必需的。
4. **`content.legacy/` 是归档的旧内容**，一律不参与构建与校验。旧架构里
   「`_` 前缀 = 私有目录」的约定保留，用于 `languages/_template/`。

## 4. 数据契约

### 4.1 清单：池 + 每基准的章节分组

**池** —— 这个板块有哪些知识点，与基准无关：

```yaml
# content/catalog/express/features.yaml
section: express
title: 基础表达

features:
  - id: var-declaration            # 板块内唯一（不是章内唯一 —— 章由基准决定）
    group: bindings                # 存放组 → languages/<语言>/express/bindings.yaml
    title: 变量声明
    kind: syntax
    summary: 如何声明一个变量
    tags: [comparison]
  - id: hoisting
    group: bindings
    title: 变量提升
    kind: behavior
```

**章节分组** —— 某个基准怎么把它们讲给读者听：

```yaml
# content/catalog/express/javascript.yaml
section: express
baseline: javascript

chapters:
  - id: bindings                   # 该基准下的章节 id，只在「该基准 × 该板块」内唯一
    title: 变量、作用域与提升
    summary: 声明、可变性、作用域与遮蔽
    features: [var-declaration, mutability, scope, hoisting, shadowing]
  - id: values
    title: 类型与值
    features: […]
```

- **顺序的唯一真源**：`chapters` 的数组顺序就是章节顺序，`features` 的数组顺序就是行顺序。
  没有 `order` 字段，也没有文件名序号。
- **`baseline` 显式声明身份**：章节分组不再能只靠文件名唯一确定自己是「谁在什么板块下的分组」，
  所以 `section` 与 `baseline` 都要写，且必须与目录名、文件名一致（R20c 校验）。
- **同一个 feature 可以出现在不同基准的不同章里**，这正是 §2.5 的目的。
- **池里的顺序不表达任何东西** —— 展示顺序全在章节分组里。池的顺序只求好读。
- **`kind` / `summary` / `tags` / `refFeatureId` 等「这条 feature 是什么」的属性放池里**，
  它是知识点自身的属性，与谁在看无关。

### 4.2 语言内容：`languages/<语言>/<板块>/<group>.yaml`

**路径的第三段是 `group`（存放组），不是章节。** 这是 §2.5 的直接后果：章节随基准变，
内容不能跟着它走，否则同一个 feature 要为每个基准各写一遍。

```yaml
# content/languages/python/express/bindings.yaml
# 池见 catalog/express/features.yaml 里 group: bindings 的那批 —— 这里只写内容

boxes:
  var-declaration:                 # key = 池里的 feature id
    code: |                        # 槽位 ①
      count = 0
    baseline: |                    # 槽位 ③-a：Python 作基准列时显示
      Python 赋值即声明，没有独立的声明关键字。
    vs:                            # 槽位 ③-b：Python 作对比列时，按当前基准取
      javascript: |
        JS 需要 let / const 显式声明，还有提升与暂时性死区；
        Python 的赋值语句本身就是声明。
      java: |
        Java 必须写出变量类型，Python 由赋值推断。
    equivalence:                   # 也按基准分，省略 = identical
      javascript: divergent
      java: divergent

  hoisting:                        # 显式声明「无此概念」，区别于「还没写」
    absent: true
    vs:
      javascript: |
        Python 没有变量提升这一概念。
```

- **文件里没有 `title` / `order` / `features` 数组** —— 全在 catalog。
- **key 与**池**里该 `group` 的 feature id 对齐**；没写的 key 表示这门语言在这个点上留空。
- **`code` / `baseline` / `vs` / `equivalence` / `absent` 等「这门语言怎么讲」的字段放这里。**
- **一个 feature 的 box 只有一个归属文件**（池里 `group` 指的那个）。它会被所有
  引用了这个 feature 的基准、在所有章节位置渲染 —— 但内容只此一份。

### 4.3 槽位与字段的对应

| | 槽位 / 属性 | 字段 | 放在哪 | 可空 |
| --- | --- | --- | --- | --- |
| ① | 代码 | `code`（或 `blocks` 多段） | 语言文件 | ✓ |
| ② | 注释 | 代码内联的 `@note` | 语言文件 | ✓ |
| ③-a | 基础描述（**基准**角色） | `baseline` | 语言文件 | 基准候选不可空 |
| ③-b | 差异解释（**对比**角色） | `vs.<基准 id>` | 语言文件 | ✓ |
| — | 知识点自身的属性 | `title` `summary` `kind` `tags` `refFeatureId` | **池** | — |
| — | 它存放在哪个文件 | `group` | **池** | 必填 |
| — | 它展示在哪一章 / 什么顺序 | `chapters[].features` | **该基准的章节分组** | 可取舍 |

**`equivalence` 按基准分**（`equivalence.<基准 id>`）——
「Python 的 `==` 对 JS 是 `divergent`、对 Java 是 `analogous`」这类事实必须能表达。
省略时默认 `identical`。基准列不渲染徽章（自指、零信息量）—— 沿用旧规则。

### 4.4 可空规则

1. **池里有、语言文件里没有这个 key → 空框**，合法。矩阵里该格留白。
2. **`absent: true`** 是「这门语言没有这个概念」的**显式声明**，区别于「还没写」，
   渲染为「本语言无此概念」。它可以同时给 `code`（表示「没有等价语法，这是惯用替代写法」），
   此时必须给一段说明。
3. **基准候选的 `baseline` 不可空**（R23）：基准列是参照系，不能空着。
   若某门基准语言在某个 feature 上真的无话可说，说明这条 feature 不该进清单。
   **判据只对「该基准的章节分组真正引用了的 feature」求值** —— 被某个基准刻意取舍掉的知识点
   （它不在那个基准的任何章里、读者根本看不到）不该被要求写基准描述。
4. **非基准语言的 `baseline` 可以省略** —— 它们永远不会被渲染成基准列。
5. **池里有、但没有任何基准的章节分组引用它 → 永远不展示**（R20e，warn）。
   这通常是「新加的知识点还没排进任何一章」，偶尔是「刻意先放着」。

### 4.5 方向性内容：`pairs/<基准>2<目标>/`

速查三兄弟是唯一的 pair 级内容，结构沿用旧契约（顶层数组）：

```yaml
# content/pairs/javascript2python/pitfalls.yaml
- id: mutable-default-arg
  title: 可变默认参数
  body: |
    …
```

文件名固定为 `pitfalls` / `glossary` / `roadmap`，板块注册表的 `dataKey` 指向它们。
**pair 归属由目录名反查 registry 得到**，不写进每条 YAML（沿用旧决策）—— 避免同一条陷阱
在多个方向各存一份、各自漂移。

## 5. 渲染与 URL

### 5.1 全 1V多

**本架构没有「对级」板块**（速查除外）。所有内容页都是矩阵：

```
列 = [基准列] + [读者勾选的对比语言…]
行 = 该章的 features
格 = 对比框（§2.1）
```

- **行**来自**当前基准的章节分组**：切基准时连章节列表、章节名、行集合都可能变（§2.5）。
- 基准列显示 `baseline` 描述，对比列显示 `vs.<基准>` 描述。
- 读者切换基准时，**全部列的来源都变**：原来是对比列的 JS 变成基准列（改用 `baseline`），
  而原基准列变成对比列（改用它的 `vs.javascript`）。这是同一份内容的重新取用，不是重新加载。
- **格子本身的来源不变** —— 它只由 (语言, feature) 决定，与基准无关。变的只是从哪个位置被读到。

### 5.2 URL

```
/compare/<基准>/<板块>/<章节>        # 章节页（章节 id 由该基准的章节分组定义）
/compare/<基准>/<板块>               # 板块入口（该基准在该板块的第一章）
/compare/<基准>                      # 落到落点板块
/feature/<板块>/<feature>            # 知识点详情（两段，与基准无关）
```

**对比语言不进 URL** —— 沿用旧决策（ADR-26/27）。理由不变：它是「我现在想看哪几门」，
是一个可变的视图偏好，写进地址会让同一份内容散成几十个地址。
多选状态存在 store 里（`compareLangs`），与旧架构一致。

**章节 id 带基准**：`/compare/javascript/express/bindings` 与
`/compare/python/express/bindings` 是两份**可能完全不同**的章节 —— 同名不代表同义。
这正是 §2.5 想要的效果，但它要求章节 id 只在「该基准 × 该板块」内唯一（而不是全站唯一）。

**全局 feature id 是两段** `<板块>/<feature>`：feature 属于**池**，池与基准无关，
所以它的 id 里不能有章节（章节随基准变）。详情页地址因此稳定、可分享、与当前基准解耦。

新增章节 = 在**某个基准的章节分组**里加一条，引用池里已有的 feature id ——
不动任何内容文件，**不会因为插在中间而让后续章节全体改名**（这正是去掉序号的收益）。

### 5.3 速查板块保持方向性

`pitfalls` / `glossary` / `roadmap` 是唯一保留 `scope: pair` 的板块：

```
/compare/<基准>/pitfalls     方向由页内选择条决定
```

理由：这三类内容的主语是**方向**，不是语言。「带着 JS 习惯写 Python 会踩的坑」
换成「Python 的坑」就丢掉了最有价值的那半句。

## 6. 构建与校验规则

沿用旧的管线（`content:validate` → `content:build`），规则集需要重写。

| 规则 | 内容 | 级别 |
| --- | --- | --- |
| **R20a 引用完整性** | 章节分组引用的 feature id 必须在池里 | error |
| **R20b 池内自洽** | 同一板块内 feature id 唯一；每个 feature 都声明了 `group` | error |
| **R20c 文件名自洽** | 池的 `section` = 目录名；章节分组的 `section` + `baseline` = 目录名 + 文件名 | error |
| **R20d 孤儿内容** | 语言目录里的内容文件，其 `group` 不在池里（拼写错误或孤儿文件） | error |
| **R20e 永不展示** | 池里某 feature 不在**任何**基准的章节分组里 | warn |
| **R20f 悬空 group** | 池里有 feature 声明了某个 `group`，但没有任何语言写这个文件 | warn |
| **R20g 覆盖率缺口** | (基准 B, B 的章 C, 已启用语言 L)：L 完全没有 C 引用的任何 `group` 的内容 | warn |
| **R20h 同基准重复** | 同一 feature 在同一基准下出现在多个章里 | warn |
| **R21 key 合法性** | 内容文件里的 box key 必须属于**池中该 `group` 的** feature 集合 | error |
| **R22 `vs` 完整性** | 基准候选写除自己外 2 门、非基准写全 3 门 | warn |
| **R23 基准列非空** | 基准候选在**被它引用的** feature 上必须有 `baseline` | warn |
| **R24 存疑的空框** | 被某基准引用、语言文件缺 key、且未 `absent` → 疑似漏写 | warn |
| **R25 说明的基准归属** | `vs.<基准>` / `baseline` 里的文本点名屏幕外的语言（幽灵语言） | warn |
| **R26 `absent` 需说明** | `absent: true` 且给了 `code`（惯用替代写法）→ 必须有说明 | warn |
| **R27 基准列空洞** | 某章引用了 `group` G，但该基准缺 G 的内容 → 基准列会出现空格 | warn |

**R22 / R23 / R24 的求值集合从「全清单」变成了「该基准真正引用的集」** ——
这是 §2.5 带来的必要修正：一个 feature 被某个基准的章节分组刻意取舍掉之后，
它在那位读者的屏幕上根本不存在，再要求它写 `vs` 或 `baseline` 就是凭空造债。

**R24 刻意是 warn**：空框本身合法（§4.4），需要人确认它是「刻意留空」还是「忘了写」。
等内容稳定后可以按板块收紧成 error。

**R25 是旧 R12 的延续**：`vs.javascript` 是「写给 JS 基准的读者」的，
在那里提 Java 就是屏幕外的幽灵语言。

**校验规则减少的部分**：旧架构里大量规则服务于「三轴 + 两种 scope」
（R2 覆盖率按 `languages` 范围、R14 板块成员资格、R18/R19 多列板块的正文归属、
R11 差异有说明、R8 命名约定……）。新架构只有一种形态、一种组织方式，
且清单与内容分离（顺序不再由文件名表达），这些规则大半可以删除。

## 7. 内容成本与重写路径

### 7.1 成本账（这是本架构最大的代价，必须如实说明）

| 语言 | `baseline` | `vs` 份数 | 合计 |
| --- | --- | --- | --- |
| JavaScript（基准） | 1 | vs Python、vs Java | 3 |
| Python（基准） | 1 | vs JS、vs Java | 3 |
| Java（基准） | 1 | vs JS、vs Python | 3 |
| Rust | — | vs JS、vs Python、vs Java | 3 |
| Go | — | vs JS、vs Python、vs Java | 3 |

**12 份差异说明 + 3 份基础描述。** 基准固定为三门之后，这个数字是**封顶的** ——
以后加语言只按「每门语言 3 份」线性增加，不会因基准变动而重算。

按旧内容规模估算（基础语法 72 feature + 语言之内约 60 + 语言之外约 30 ≈ 160 个知识点），
每个知识点每门语言要为每个基准写一段 → 量级 **2000+ 条**，而旧架构全站是 1326 条实现。

**缓解措施**（§4.3 的可空规则）：只在不同处写，相同处留空。
但「为每个基准各写一份」这件事本身无法回避 —— 这是选「每门语言为每个基准各写一份」的必然代价。

**§2.5 的章节分组不在这笔账里。** 它只决定「同一个 feature 摆在哪个位置」，
既不新增内容、也不新增 `vs` 份数。换句话说：**分组自由度是免费的，视角成本才要钱。**
这条性质很重要 —— 它意味着以后调整章节分类、给某个基准换一套组织方式，
都不需要重写任何一格内容。

### 7.2 重写路径

旧内容（444 feature / 1326 实现）**推倒重写**，不迁移。`content/` 已归档为 `content.legacy/`
（保留在仓库而非删除，是为了填新内容时还能对照旧写法）。

之后的路径是：**立契约 → 立骨架 → 通管线 → 每基准章节分类 → 填内容**。
前四步已经走过或正在走，逐阶段的「做什么 / 改哪些文件 / 验收信号 / 坑」见
[内容架构迁移实施步骤.md](内容架构迁移实施步骤.md)。剩下的是**内容爬坡**：
按 §7.1 的成本逐知识点逐语言填框，每批跑一次校验看 warn 数下降。

**填内容的顺序建议**：先把一个板块（`express`）在一个基准（JS）下的章节填满，
跑通全站后再铺其余基准与板块 —— 骨架期能最快暴露「章节粒度定得对不对」这个问题。

## 8. 未决问题

1. **`model` / `mechanism` / `practice` 三个板块的池与章节分组还没建**（S7）。
   它们的知识点清单一旦列出来，「160 个知识点」这个估算就会被第一次真正检验。
2. **非基准语言的章节分组是否有意义**：Python 作为对比列出现在 JS 视角下时，
   用的是 JS 的章节分组。是否要为「以 Python 为基准」之外的角色也准备分组，
   目前判断是不需要 —— 分组只在「谁当基准」时生效。
3. **章节粒度的下限**：一章放几个 feature 合适。太粗则矩阵行太少、一页信息量不足；
   太细则左栏变成一张长表。现在只有试点一章（5 个 feature）可参照，铺开后再校准。

## 附录 A：关键决策记录

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| ADR-40 | 内容以**语言**为组织单位，取消方向目录 | 加语言从 N 倍降为常数；消除方向副本的漂移 |
| ADR-41 | 每门语言为**每个基准**各写一份差异解释 | 视角无法互相推导（§2.2）；准确的代价是可接受的 |
| ADR-42 | 全站 1V多，取消 `scope: pair`（速查除外） | 定位是「概览地图」，矩阵优于文章（§1.1） |
| ADR-43 | 对比框三槽位，两列皆可空；全空需 `absent` | 内容天然疏密不均；显式空与漏写必须可区分 |
| ADR-44 | 第 ③ 槽一个字段两种角色（`baseline` / `vs.<基准>`） | 沿用 ADR-35 的思路，但把「差异」按基准拆开 |
| ADR-45 | 速查三兄弟保留方向性 | 它们的主语是方向，不是语言（§5.3） |
| ADR-46 | 旧内容推倒重写 | 旧结构（三轴 + 两种 scope）与新模型不兼容，改造比重写更贵 |
| ADR-47 | 基准固定为 JS / Python / Java 三门，不再增减 | 加基准是 N 倍成本（所有语言各补一份 `vs`）；定死后 `vs` 的 key 集合封闭，总量可预估 |
| ADR-48 | 清单集中在 `content/catalog/`，与内容分离 | 增删章节、调换顺序、改标题都只动一处，**不动任何语言文件** |
| ADR-49 | 文件名不带序号，取消 `order` 字段 | 序号会在增删章节时引发连锁改名；顺序的唯一真源是 catalog 的数组顺序 |
| ADR-50 | 方向性内容独立到 `content/pairs/` | 速查三兄弟的主语是方向，塞不进任何单个语言目录；与 `languages/` 并列，职责一眼可辨 |
| ADR-51 | 内容的存放单位下位为 **`group`（存放组）**，与展示章解耦 | 章节随基准变（ADR-52），内容若跟着它走，同一个知识点就要为每个基准各写一遍 —— 那正是本架构要避免的平方成本 |
| ADR-52 | **章节分组按基准各一份**：清单分「池 + 每基准分组」两层 | 用户熟悉的语言怎么组织知识，就怎么给他看；而分组自由度**不增加任何内容成本**（ADR-51） |
| ADR-53 | 顶层板块换成四段：`express` / `model` / `mechanism` / `practice`，**主题式命名** | 按「迁移者先关心什么」重划（读懂 → 改写 → 敢动 → 落地）。命名刻意避开「先/能/敢」的课程口吻 —— §1.1 的定位是查阅型地图，不是教程 |
| ADR-54 | 全局 feature id 收缩为 `<板块>/<feature>` **两段** | feature 属于池、与基准无关，所以 id 里不能有章节（章节随基准变）；也不能有存放组 —— 它是界面上看不见的存放细节，进 URL 只会多一个读者对不上的段。详情页地址因此稳定、可分享、与当前基准解耦 |
