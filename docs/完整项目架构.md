## 0. 一句话

**每门语言自带一份内容，内容是「本语言相对于三大基准语言的差异」。**
读者选一个基准，勾选若干对比语言，看到的是每一门「和基准差在哪」。

**章节分类也按基准各来一份**：用户熟悉的语言怎么组织知识，就怎么给他看左栏与矩阵的行（§2.5）。

三大基准：**JavaScript / Python / Java**，**固定不变**（即 `meta.yaml` 里 `baseline: true` 的三门）。

```
顶栏：☰ · 站点名 · 首页 · 多语言对比 · 速查 · 内容来源 · 密度 · 主题
左栏：基准语言 [JS|Py|Java]（**吸顶，跟着菜单滚**）
      「多语言对比」的子菜单 —— 基础表达 → 数据与抽象 → 语言机制 → 工程实践
      每个板块下是**当前基准的**章节列表（章节随基准变）
页内：对比语言 [JS][Py][Java][Go][Rust] · 展示方式 [矩阵|卡片并排]   ← 章节型多选，速查三兄弟单选
```

| 维度 | 现状 |
| --- | --- |
| 板块 | 4 个章节型 + 3 个速查（**全是可注册的数据**，见 §2.4） |
| 基准语言 | JS（默认）/ Python / Java —— 三选一，**进 URL**，不增减（ADR-47）；**切换入口在左栏顶部、吸顶**（ADR-59） |

## 1. 设计出发点

### 1.1 定位：迁移者的地图，不是教材

本站**不承担「教会一门语言」的职责**。用户是已经会一门语言、要快速了解另一门语言的人，
目标是**建立地图**——知道对方语言长什么样、哪里和我的母语不一样、哪里会绊住我。
深入学习由用户去专门的教程站完成。

这个定位推翻了两个曾经的设计前提：

| 曾经的前提 | 现在 |
| --- | --- |
| 这个站是「顺序教程」，章节要有阅读顺序 | 它是**查阅型地图**，章节之间无强顺序 |
| 深度内容（长文、因果叙事）是护城河 | **广度与准确性**是护城河；深度让给教程站 |

它同时决定了内容形态：**矩阵（并排）优于文章**。概览要的就是一眼扫到全貌，
而文章是给「要学会」的人准备的。因此本架构**只有 1V多**（见 §5.1）。

### 1.2 旧架构（v1）的三个问题

1. **三块讲同一批东西。** `基础语法`（72 条）、`心智模型`（26 条）、`迁移教程`（6 方向 × 25 条）
   覆盖的是同一批语言模块（类型、容器、函数、错误、并发），只是各自换了个说法。
   读者面对同一主题有三个入口，而每一个都不完整。
2. **内容按方向组织，成本随语言数平方增长。** 加一门语言要建 N 个方向目录；
   6 个方向已经让 `migration` 板块有 6 份互相独立、会各自漂移的内容。
3. **「迁移」被做成了一个板块，而不是一种视角。** 结果另外两块（基础语法 / 心智模型）
   不得不用另一种口径写同一批内容，重复由此产生。

v2 的处置是推倒重写（ADR-46）：旧内容归档在 `content.legacy/`，不参与构建与校验，
只作填新内容时的写法对照。

## 2. 内容模型

### 2.1 对比框：一个知识点在一门语言下的全部内容

**对比框（box）** 是本架构的最小单元 = **一个 feature × 一门语言**的格子。

一个框有三个槽位，**任意组合，全部可空**：

| # | 槽位 | 内容 | 载体 |
| --- | --- | --- | --- |
| ① | **代码** | 该语言在这个知识点上的写法 | `code`（或 `blocks` 多段） |
| ② | **注释** | 贴着某一行的提醒，写在代码行内 | 代码里的 `@note` / `@note!` |
| ③ | **说明** | 一段文字 | `baseline` 或 `vs.<基准>`（见 §2.2） |

- ① 和 ② 是耦合的：注释**内联在代码里**，不是独立字段（沿用 ADR-35 的思路）。
  所以「有注释」隐含「有代码」。
- ③ 是**唯一一个按角色变化的槽位**，也是本架构与 v1 最大的差别。
- **三槽全空是合法的**，但必须显式声明 `absent: true`（见 §4.4）——
  否则视为「忘了写」，校验会报警。

### 2.2 两种角色：同一门语言，两种身份

这是本架构的枢纽。**同一门语言在不同时刻扮演不同角色，第 ③ 槽因此有两套内容。**

| 这门语言此刻是… | 第 ③ 槽写什么 | 字段 |
| --- | --- | --- |
| **基准列**（它就是被参照的那门） | **基础描述** —— 这门语言自己是什么 | `baseline` |
| **对比列**（读者从别处看过来） | **差异解释** —— 它和**当前基准**差在哪 | `vs.<基准 id>` |

**关键推论**：一门语言要为**每个基准**各准备一份差异解释。

```
Python 的内容里：
  baseline: |                     ← 当基准是 Python 时，Python 列显示这段
    Python 里没有 ===，== 是值比较…
  vs:
    javascript: |                 ← 当基准是 JS、Python 作对比列时，显示这段
      Python 没有严格相等，== 对值是值比较，对对象是引用比较…
    java: |                       ← 当基准是 Java、Python 作对比列时，显示这段
      与 Java 不同，Python 的 == 可以被 __eq__ 重载…
```

这三段文本是**同一件事的三种说法**，视角各不相同，无法互相推导 —— 所以必须分别撰写。
这是本架构最主要的内容成本（见 §12）。

**基准语言也有 `vs` 吗？** 有。JS 是基准，但当读者把基准切到 Python 时，JS 就成了对比列，
此时用 `vs.python`。所以 JS 的内容 = `baseline` + `vs.python` + `vs.java`。

**双角色取值的唯一落点是 [src/content/boxView.ts](../src/content/boxView.ts)**
（`explanationOf` / `badgeOf`）。矩阵、并排、特性页三处都调它 ——
各写一遍的话「基准列显示成对比说明」这种错会只在其中一处出现，且不报错。

`badgeOf` 的三条规则**顺序不能换**：基准列 → `null`（自指、零信息量）；
`absent` → `'absent'`（**必须短路掉 `equivalence` 的缺省值**，否则灰格会顶着一枚 `=`）；
其余取 `equivalence[基准] ?? 'identical'`。

### 2.3 组织单位是语言，不是方向

内容按**语言**存放。一门语言一个目录，自包含：

```
content/languages/javascript/     ← JS 的全部内容
content/languages/python/         ← Python 的全部内容
content/languages/rust/           ← Rust 的全部内容（22 个存放组；对比列语言，无 baseline）
```

**主内容里没有 `js2python/` 这样的方向目录。**
「从 JS 到 Python」不是一份内容，而是一次**查询**：基准取 JS 的内容作参照系，
对比列取 Python 内容里的 `vs.javascript`。
（唯一的例外是速查三兄弟，见 §4.5 —— 它们的主语本就是方向。）

由此：

- **加一门语言** = 加一个语言目录，`vs` 写满三门基准。线性成本。
- **基准固定为三门**（JavaScript / Python / Java），不增不减。这既是策展决定，
  也是成本决定 —— 加一个基准等于让**每一门语言各补一份 `vs`**，是 N 倍成本。
  定死之后，`vs` 的 key 集合是封闭的（至多三门），内容总量可预估（见 §12）。

### 2.4 板块

四个章节型板块（第四版分类，按**迁移者先关心什么**重划），加速查三兄弟：

| id | 名称 | 存放组 | 知识点 | 形态 |
| --- | --- | --- | --- | --- |
| `express` | 基础表达 | bindings / values / operators / control-flow / functions / strings / containers | 27 | 1V多 |
| `model` | 数据与抽象 | modules / errors / collections / iteration / objects / abstraction | 31 | 1V多 |
| `mechanism` | 语言机制 | types / generics / memory / concurrency / async / meta | 29 | 1V多 |
| `practice` | 工程实践 | packages / toolchain / testing | 17 | 1V多 |
| `pitfalls` `glossary` `roadmap` | 速查 | 陷阱 / 词典 / 路线 | — | **保留方向性** |

**上表列的是存放组，不是章节** —— 章节是**每个基准各一份**的（§2.5），
所以它没有一张全站通用的表。真实的章节表见 §2.6 与 `content/catalog/<板块>/<基准 id>.yaml`。

**分界依据**：`express` 是「能读懂对方在写什么」，`model` 是「能照着改写」，
`mechanism` 是「敢动它」（换语言必须重学的机制集中在这里），
`practice` 是「能落地」（换工具、但概念不变的部分）。

> **命名刻意是主题式的，不是「第一课 / 第二课」。** 本站是查阅型地图而非教程（§1.1），
> 四个板块表达的是**关注点**而非阅读顺序 —— 读者从任何一块进去都应当成立。
> 这条边界值得守：`先读懂 / 能改写 / 敢重构 / 能落地` 那样的措辞会把地图读成课程。

**`practice` 板块的诚实定位**：它是四个板块里**跨基准差异最小**的一个 ——
「概念不变、只换工具」正是它的定义。因此它的 `vs` 文本普遍比 `mechanism` 短，
`absent` 也更常见（Java 没有打包器、没有事件循环）。这不是内容偷懒，
是这个板块的性质；把它写成「处处不同」反而是失真。

**速查三兄弟是唯一的例外**（见 §5.4）。它们天性是方向性的
（「从 JS 过来的人容易踩的坑」），无法按语言组织，因此保留 `scope: pair`。

### 2.5 章节分组按基准

内容按语言组织（§2.3），但**清单按基准各来一份**：Python 的视角下「名称、绑定与可变性」
这一章该带着 Python 的概念讲；Java 的视角下，同一批知识点按 Java 的心智模型重新分组。

实现上分两层：

| 层 | 文件 | 管什么 |
| --- | --- | --- |
| **feature 池** | `catalog/<板块>/features.yaml` | 这个板块有哪些知识点。**与基准无关，全站唯一** |
| **章节分组** | `catalog/<板块>/<基准 id>.yaml` | 该基准把池里的知识点分成哪几章、叫什么、什么顺序、取舍哪些 |

**关键性质（这是本轴的全部收益）**：池里的每个 feature 声明一个 `group`（**存放组**），
它是**内容的存放单位**，与展示无关。于是：

- 同一个 feature 在 JS 视角下可以落在「变量、作用域与提升」章、在 Java 视角下落在
  「方法、作用域与闭包」章，**而它的内容只写一份**，不会漂移。
- 加一门语言仍是线性成本（§12）；**分组的自由度不增加任何内容成本**。

代价是多了一层概念。作者要区分三件事：「这个知识点是什么」（池）、「它写在哪个文件里」（`group`）、
「它展示在哪一章」（每基准的章节分组）。前两件是写作时要想的，第三件是纯粹的策展工作 ——
它可以在内容写完之后再调，不动任何内容文件。

| `mechanism` | java | `types`「类型系统」6 · `generics`「泛型与类型擦除」4 · `memory`「JVM 与内存模型」5 · `concurrency`「线程与并发工具」5 · `async`「异步」5 · `meta`「注解与反射」4 |

三条从表里读得出来的结论：

1. **同一批知识点真的落到了不同的章。** `mechanism/generics` 在 Python 视角下被并进
   `typing`（Python 的类型标注与泛型本来就同源），在 JS / Java 视角下各自独立成章。
   `express/bindings` 在 Java 视角下被**劈成两半** —— 声明类落 `types`、作用域类落 `methods`。
2. **章数不必相等。** `express` 下 JS 6 章、Python 7 章、Java 6 章。这与「每个基准讲自己的故事」一致。
3. **取舍是真的在发生。** `express/hoisting`（变量提升）**只存在于 JS 的章节分组里** ——
   Python 与 Java 都没有这个概念，硬塞给它们只会让读者以为「他们也关心这件事」。
   它仍然在池里（所以 JS 视角下正常展示），只是不被那两个基准的章节分组引用。

> **一个知识点的可见性由「有没有出现在该基准的章节分组里」决定**，
> 而不是由「它在不在池里」决定。这是 §2.5 分层的直接结果，也是池可以比任何单份分组都大得多的原因。

## 3. 目录结构

**清单与内容分离，存放与展示也分离。** 清单（有哪些知识点、怎么分组、什么顺序、叫什么）
集中在 `catalog/`；内容（每门语言怎么讲）按语言分散在 `languages/`。
改章节分组、调换顺序、改标题**只动 catalog，一个内容文件都不用碰**。

```
content/
├── registry.yaml                    # 站点级配置 + 板块注册表 + 语言启用开关
├── i18n/zh-CN.yaml
├── catalog/                         # ① 清单 —— 唯一真源，按板块一个目录
│   ├── express/
│   │   ├── features.yaml            #   池：27 个知识点（与基准无关，全站唯一）
│   │   ├── javascript.yaml          #   该基准的章节分组
│   │   ├── python.yaml
│   │   └── java.yaml
│   ├── model/                       #   同构：features 31
│   ├── mechanism/                   #   同构：features 29
│   └── practice/                    #   同构：features 17
├── languages/                       # ② 内容 —— 按语言组织（1V多）
│   ├── _template/                   #   脚手架（私有目录，不参与构建）
│   │   ├── meta.yaml
│   │   ├── express/bindings.yaml
│   │   ├── model/errors.yaml
│   │   ├── mechanism/types.yaml
│   │   └── practice/testing.yaml
│   ├── javascript/                  #   4 板块 × 各存放组，共 22 个内容文件
│   │   ├── meta.yaml                #   语言元数据（baseline: true）
│   │   ├── express/bindings.yaml    #   文件名 = 池里的 group（存放组）
│   │   └── …（model / mechanism / practice 同构）
│   ├── python/  java/               #   同构，各 22 个内容文件
│   └── rust/  go/                   #   同构 —— **对比列语言**：只写 vs、不写 baseline
├── pairs/                           # ③ 内容 —— 按方向组织（唯一的 pair 级）
│   ├── javascript2python/           #   3 个基准 × 4 门其他启用语言 = 12 个方向（ADR-65）
│   │   ├── meta.yaml                #   来源与校对留痕（ADR-66）
│   │   ├── pitfalls.yaml            #   12 条，顶层是数组
│   │   ├── glossary.yaml            #   10 条
│   │   └── roadmap.yaml             #   5 个阶段
│   └── …其余 11 个方向（javascript2java / javascript2go / javascript2rust /
│       python2javascript / python2java / python2go / python2rust /
│       java2javascript / java2python / java2go / java2rust）
└── …（另有 1 门只声明未启用的语言目录：php，
    只有 meta.yaml；typescript 与 arkts 已于 S11 轮 ① 补齐内容并启用）

content.legacy/                      # 旧内容（v1），构建与校验一律忽略
```

| 内容 | 路径 | 管什么 |
| --- | --- | --- |
| feature 池 | `catalog/<板块>/features.yaml` | 该板块有哪些知识点，每个属于哪个 `group` |
| 章节分组 | `catalog/<板块>/<基准 id>.yaml` | 该基准把池里的知识点分成哪几章、叫什么、什么顺序 |
| 一对多内容 | `languages/<语言>/<板块>/<group>.yaml` | 每门语言在各知识点上的内容 |
| 方向性内容 | `pairs/<基准>2<目标>/{pitfalls,glossary,roadmap}.yaml` | 速查三兄弟 |

四点约定：

1. **文件名不带序号** —— 序号会在增删章节时引发连锁改名（插一章，后面全体重命名），
   而顺序另有单一真源（章节分组里的数组顺序）。**章节 id 由章节分组自己声明**。
2. **板块从目录名取**，池与章节分组都不在文件内容里重复声明板块 —— 但**要声明自己的身份**
   （池声明 `section`，章节分组声明 `section` + `baseline`），因为它不再能只靠文件名唯一确定。
   语言内容文件则相反：一律由路径派生，**不重复声明**（`.strict()` 会让重复声明直接报错）。
3. **一个板块的 `<基准 id>.yaml` 缺失 = 该基准在这个板块还没有章节**，视为未开工，
   左栏整组隐藏。占位文件不是必需的。
4. **`content.legacy/` 是归档的旧内容**，一律不参与构建与校验。旧架构里
   「`_` 前缀 = 私有目录」的约定保留，用于 `languages/_template/`。

## 4. 数据契约

类型唯一真源是 [src/schemas/index.ts](../src/schemas/index.ts)（Zod）；
[src/types/index.ts](../src/types/index.ts) 只做 `z.infer` 再导出，**禁止手写 interface**。

### 4.1 清单：池 + 每基准的章节分组

**池** —— 这个板块有哪些知识点，与基准无关：

```yaml
# content/catalog/express/features.yaml
section: express
title: 基础表达

features:
  - id: declaration                # 板块内唯一（不是章内唯一 —— 章由基准决定）
    group: bindings                # 存放组 → languages/<语言>/express/bindings.yaml
    title: 变量声明
    kind: syntax
    summary: 如何在语言里引入一个名字
    tags: [comparison]
  - id: hoisting
    group: bindings
    title: 变量提升
    kind: behavior
```

**章节分组** —— 某个基准怎么把它们讲给读者听：

```yaml
# content/catalog/express/javascript.yaml
section: express
baseline: javascript

chapters:
  - id: bindings                   # 该基准下的章节 id，只在「该基准 × 该板块」内唯一
    title: 变量、作用域与提升
    summary: 声明、可变性、作用域与遮蔽
    features: [declaration, mutability, scope, hoisting, shadowing]
  - id: values
    title: 类型与值
    features: […]
```

- **顺序的唯一真源**：`chapters` 的数组顺序就是章节顺序，`features` 的数组顺序就是行顺序。
  没有 `order` 字段，也没有文件名序号。
- **`baseline` 显式声明身份**：章节分组不再能只靠文件名唯一确定自己是「谁在什么板块下的分组」，
  所以 `section` 与 `baseline` 都要写，且必须与目录名、文件名一致（R20c 校验）。
- **同一个 feature 可以出现在不同基准的不同章里**，这正是 §2.5 的目的。
- **池里的顺序不表达任何东西** —— 展示顺序全在章节分组里。池的顺序只求好读。
- **`kind` / `summary` / `tags` 等「这条 feature 是什么」的属性放池里**，
  它是知识点自身的属性，与谁在看无关。

### 4.2 语言内容：`languages/<语言>/<板块>/<group>.yaml`

**路径的第三段是 `group`（存放组），不是章节。** 这是 §2.5 的直接后果：章节随基准变，
内容不能跟着它走，否则同一个 feature 要为每个基准各写一遍。

```yaml
# content/languages/python/express/bindings.yaml
# 池见 catalog/express/features.yaml 里 group: bindings 的那批 —— 这里只写内容

boxes:
  declaration:                     # key = 池里的 feature id
    code: |                        # 槽位 ①
      count = 0
    baseline: |                    # 槽位 ③-a：Python 作基准列时显示
      Python 赋值即声明，没有独立的声明关键字。
    vs:                            # 槽位 ③-b：Python 作对比列时，按当前基准取
      javascript: |
        JS 需要 let / const 显式声明，还有提升与暂时性死区；
        Python 的赋值语句本身就是声明。
      java: |
        Java 必须写出变量类型，Python 由赋值推断。
    equivalence:                   # 也按基准分，省略 = identical
      javascript: divergent
      java: divergent

  hoisting:                        # 显式声明「无此概念」，区别于「还没写」
    absent: true
    vs:
      javascript: |
        Python 没有变量提升这一概念。
```

- **文件里没有 `title` / `order` / `features` 数组** —— 全在 catalog。
- **key 与池里该 `group` 的 feature id 对齐**；没写的 key 表示这门语言在这个点上留空。
- **`code` / `baseline` / `vs` / `equivalence` / `absent` 等「这门语言怎么讲」的字段放这里。**
- **一个 feature 的 box 只有一个归属文件**（池里 `group` 指的那个）。它会被所有
  引用了这个 feature 的基准、在所有章节位置渲染 —— 但内容只此一份。

### 4.3 槽位与字段的对应

| | 槽位 / 属性 | 字段 | 放在哪 | 可空 |
| --- | --- | --- | --- | --- |
| ① | 代码 | `code`（或 `blocks` 多段） | 语言文件 | ✓ |
| ② | 注释 | 代码内联的 `@note` | 语言文件 | ✓ |
| ③-a | 基础描述（**基准**角色） | `baseline` | 语言文件 | 基准候选不可空 |
| ③-b | 差异解释（**对比**角色） | `vs.<基准 id>` | 语言文件 | ✓ |
| — | 知识点自身的属性 | `title` `summary` `kind` `tags` | **池** | — |
| — | 它存放在哪个文件 | `group` | **池** | 必填 |
| — | 它展示在哪一章 / 什么顺序 | `chapters[].features` | **该基准的章节分组** | 可取舍 |

**`equivalence` 按基准分**（`equivalence.<基准 id>`）——
「Python 的 `==` 对 JS 是 `divergent`、对 Java 是 `analogous`」这类事实必须能表达。
省略时默认 `identical`。基准列不渲染徽章（自指、零信息量）—— 沿用旧规则。

**R16 在 schema 层**（`refineBox`）：`code` 与 `blocks` **至多一个**。
**「至少一个」被刻意删掉了** —— `absent: true` 的格子天然可以没有代码
（「本语言没有变量提升」），强制至少一个会让最典型的 absent 形态解析失败；
它的职责由 R24 / R26 承担。

### 4.4 可空规则

1. **池里有、语言文件里没有这个 key → 空框**，合法。矩阵里该格留白。
2. **`absent: true`** 是「这门语言没有这个概念」的**显式声明**，区别于「还没写」，
   渲染为灰格 +「本语言无此概念」+ ∅ 徽章。它可以同时给 `code`
   （表示「没有等价语法，这是惯用替代写法」），此时必须给一段说明（R26）。
3. **基准候选的 `baseline` 不可空**（R23）：基准列是参照系，不能空着。
   若某门基准语言在某个 feature 上真的无话可说，说明这条 feature 不该进清单。
   **判据只对「该基准的章节分组真正引用了的 feature」求值** —— 被某个基准刻意取舍掉的知识点
   （它不在那个基准的任何章里、读者根本看不到）不该被要求写基准描述。
4. **非基准语言的 `baseline` 可以省略** —— 它们永远不会被渲染成基准列。
   `rust` / `go` 就属于这一档：只写 `vs.javascript` / `vs.python` / `vs.java` 三份。
5. **池里有、但没有任何基准的章节分组引用它 → 永远不展示**（R20e，warn）。
   这通常是「新加的知识点还没排进任何一章」，偶尔是「刻意先放着」。

### 4.5 方向性内容：`pairs/<基准>2<目标>/`

速查三兄弟是唯一的 pair 级内容。**方向集合是封闭的 12 个**（ADR-65）：
3 个基准 × 4 门其他已启用语言。非基准语言之间不生成方向 —— 速查讲的是
「带着**基准**的习惯过去」，`go2rust` 没有主语。

一个方向一个目录，四份文件：

```
content/pairs/javascript2python/
├── meta.yaml       来源与校对留痕（ADR-66）
├── pitfalls.yaml   12 条，顶层是数组
├── glossary.yaml   10 条，顶层是数组
└── roadmap.yaml    5 个阶段，顶层是数组
```

```yaml
# content/pairs/javascript2python/pitfalls.yaml
- id: pitfall-is-identity
  title: 把 `===` 直译成 `is`，小数字碰巧对
  symptom: |          # 现象：读者会看到什么
  cause: |            # 为什么：语言机制上的原因
  fix: |              # 怎么改：可执行的动作
  severity: 2         # 3 = 静默失败或直接报错 / 2 = 有隐患 / 1 = 一般
  languages: [javascript, python]   # **恰好本方向两门**（ADR-68，error）
  fromBaseline: true
  featureId: express/equality        # 软引用，指向全局两段 id
  tags: [相等, 数值]
```

文件名固定为 `pitfalls` / `glossary` / `roadmap`，板块注册表的 `dataKey` 指向它们。
**pair 归属由目录名反查 registry 得到**，不写进每条 YAML（沿用旧决策）—— 避免同一条陷阱
在多个方向各存一份、各自漂移。目录名必须是**完整语言 id**（`javascript2python`，
不是 `js2python`），不允许别名。

> **`featureId` 是软引用**：它指向 `featureIndex` 里的全局 id，指向不存在的 id 时
> 只是那条反查链断掉，不影响陷阱本身渲染（R5 会汇总成一条 warn）。
> **12 个方向共 144 条已于 S10 全部指向真实存在的全局 id** ——
> 每条陷阱卡片底部的「相关特性」链接现在都指向真实的特性页。

> **散文没有规则看着**：R5 只管 `glossary.perLanguage` 的键与 `pitfalls.languages` 的值；
> `symptom` / `cause` / `fix` / `note` / `todo` 里的字没有任何校验在看。
> 「只讲本方向两门语言」与「提到的板块名必须真实存在」这两条口径由
> `tests/pipeline/content-contract.test.ts` 的常设断言守（§11.2）。

## 5. 渲染与 URL

### 5.1 全 1V多

**本架构没有「对级」板块**（速查除外）。所有内容页都是矩阵：

```
列 = [基准列] + [读者勾选的对比语言…]
行 = 该章的 features
格 = 对比框（§2.1）
```

- **行**来自**当前基准的章节分组**：切基准时连章节列表、章节名、行集合都可能变（§2.5）。
- 基准列显示 `baseline` 描述，对比列显示 `vs.<基准>` 描述。
- 读者切换基准时，**全部列的来源都变**：原来是对比列的 JS 变成基准列（改用 `baseline`），
  而原基准列变成对比列（改用它的 `vs.javascript`）。这是同一份内容的重新取用，不是重新加载。
- **格子本身的来源不变** —— 它只由 (语言, feature) 决定，与基准无关。变的只是从哪个位置被读到。
- **可见列裁剪不补位**（ADR-34 / ADR-63）：**一门对比语言都没有时只留基准列**。
  两条路径都算：读者一门都没勾（空集合是一种能表达的状态，不回落成默认语言），
  以及勾了的语言在本模块一门实现都没有。补出来的那门用户既没勾、也去不掉 ——
  点它是「新增」而不是「取消」，而选择条的勾选态读的正是 `compareLangs`。
- **「唯一的勾选就是本页基准」不是空集合**（ADR-69）：默认对比语言是 Python，读者点的
  又正是「我熟悉 Python」——那一勾此刻的身份是基准列，多选对比于是退化成只剩一列。
  `ensureCompareFor` 在进入某基准时把它换掉（优先默认对比语言，它就是基准时让位给
  书写序里的下一门），**写进 `compareLangs`** 而不是在渲染层补一列：写进集合的
  出现在勾选态里、点得掉，与 ADR-63 的默认值同一条路子；渲染层补出来的就是 ADR-34
  记的那个坑。读者主动清空（空集合）不在此列 —— 那是他表达过的「只看基准」。
  守卫与 App 的路由 watcher 各调一次（前者管按修正后的集合加载分片，后者管渲染它的
  那个 store 实例），函数幂等。

### 5.2 URL

```
/compare/<基准>/<板块>/<章节>        # 章节页（章节 id 由该基准的章节分组定义）
/compare/<基准>/<板块>               # 板块入口（该基准在该板块的第一章）
/compare/<基准>                      # 落到 compareEntryPath
/feature/<板块>/<feature>            # 知识点详情（两段，与基准无关）
/lang/<语言>   /search   /attributions
```

**对比语言不进 URL** —— 它是「我现在想看哪几门」，
是一个可变的视图偏好，写进地址会让同一份内容散成几十个地址。
多选状态存在 store 里（`compareLangs`，**可以为空 = 只看基准列**，ADR-63）。

**章节 id 带基准**：`/compare/javascript/express/bindings` 与
`/compare/python/express/bindings` 是两份**可能完全不同**的章节 —— 同名不代表同义。
这正是 §2.5 想要的效果，但它要求章节 id 只在「该基准 × 该板块」内唯一（而不是全站唯一）。

**全局 feature id 是两段** `<板块>/<feature>`：feature 属于**池**，池与基准无关，
所以它的 id 里不能有章节（章节随基准变），也不能有 `group`
（它是界面上看不见的存放细节，进 URL 只会多一个读者对不上的段）。
详情页地址因此稳定、可分享、与当前基准解耦。

**旧 URL 不保留重定向**，一律 404（ADR，见台账「已定前提」）——
静态托管做不了 301，为过渡地址预渲染一堆外壳是纯粹的负担。

新增章节 = 在**某个基准的章节分组**里加一条，引用池里已有的 feature id ——
不动任何内容文件，**不会因为插在中间而让后续章节全体改名**（这正是去掉序号的收益）。

### 5.3 可见性判据：只有一条

**「这个基准在这个板块有哪些章」不取决于章节分组写了什么，而取决于该基准自己写了多少内容。**

```ts
// src/content/repository.ts
hasChapterContent(lang, baseline, section, chapter)      // 单一判据
visibleChaptersOf(baseline, section)                     // 按判据过滤后的章节列表
```

判据是「该章引用的存放组里，这个基准至少写了一个 box」，而不是「池里声明了这个章」。
理由是**骨架先于内容**：S7.0 一次性落齐了 4 板块 × 3 基准的章节分类，而正文是分批填的。
若按「有没有章节分组」判可见，骨架一落地就会出现一整屏点进去 404 的死链。

这条判据必须在**所有列出章节的地方**同判据使用（否则那处就是死链或虚高计数）：

| 位置 | 用途 |
| --- | --- |
| [04-build.ts](../scripts/pipeline/04-build.ts) | 决定该基准×板块产出哪些路由（路由是 `manifest.routes` 的唯一来源） |
| [router/index.ts](../src/router/index.ts) 的守卫 | 决定访问不存在的章是否 404 |
| [SideNav.vue](../src/components/ui/SideNav.vue) | 左栏二级项 |
| [HomeView.vue](../src/views/HomeView.vue) | 首页卡片与计数 |
| [repository.ts](../src/content/repository.ts) 的 `siblingsOf` | 章节页的上一章 / 下一章 |
| `sectionEntryPath` / `compareEntryPath` | 板块入口落点 |

`tests/unit/section-model.test.ts` 有一条专门的断言守着「章节可见性与路由同源」：
没内容的章不产出路由，反之亦然。

### 5.4 速查板块保持方向性

`pitfalls` / `glossary` / `roadmap` 是唯一保留 `scope: pair` 的板块：

```
/compare/<基准>/pitfalls     方向由页内选择条决定（单选，preferredTarget 跨板块共享）
```

理由：这三类内容的主语是**方向**，不是语言。「带着 JS 习惯写 Python 会踩的坑」
换成「Python 的坑」就丢掉了最有价值的那半句。

## 6. 校验规则集

规则全部集中在 [scripts/lib/analyze.ts](../scripts/lib/analyze.ts)，`validate` 与 `build`
**共用同一份 `analyzeContent()`** —— 改校验逻辑只需改这一处。

### 6.1 v2 新增：R20–R27

| 规则 | 内容 | 级别 |
| --- | --- | --- |
| **R20a 引用完整性** | 章节分组引用的 feature id 必须在池里 | error |
| **R20b 池内自洽** | 同一板块内 feature id 唯一；每个 feature 都声明了 `group` | error |
| **R20c 文件名自洽** | 池的 `section` = 目录名；章节分组的 `section` + `baseline` = 目录名 + 文件名；章内 id 唯一 | error |
| **R20d 孤儿内容** | 语言目录里的内容文件，其 `group` 不在池里（拼写错误或孤儿文件） | error |
| **R20e 永不展示** | 池里某 feature 不在**任何**基准的章节分组里 | warn |
| **R20f 悬空 group** | 池里声明的某个 `group` 没有任何启用语言写它 | warn |
| **R20g 覆盖率缺口** | 「某语言 × 某章」一个存放组都没写（整列留白），按 (语言, 板块) 汇总 | warn |
| **R20h 同基准重复** | 同一 feature 在同一基准下出现在多个章；章内 feature 重复 | error / warn |
| **R21 key 合法性** | 内容文件里的 box key 必须属于**池中该 `group` 的** feature 集合 | error |
| **R22 `vs` 完整性** | 基准候选写除自己外 2 门、非基准写全 3 门 | **error** |
| **R23 基准列非空** | 基准候选在**被它引用的** feature 上必须有 `baseline` | **error** |
| **R24 存疑的空框** | 被某基准引用、语言文件缺 key、且未 `absent` → 疑似漏写 | warn（**刻意**） |
| **R25 说明的基准归属** | `vs.<基准>` / `baseline` 里的文本点名屏幕外的语言（幽灵语言），按 (语言, 板块) 汇总成一条。**同族语言除外**（ADR-71） | warn |
| **R26 `absent` 需说明** | `absent: true` 且给了 `code`（惯用替代写法）→ 必须有说明 | warn |
| **R27 基准列空洞** | 某章引用了 `group` G，但该基准缺 G 的内容 → 基准列会出现空格，按 (基准, 板块) 汇总 | warn |

**R22 / R23 / R24 的求值集合是「该基准真正引用的集」，不是全清单** ——
这是 §2.5 带来的必要修正：一个 feature 被某个基准的章节分组刻意取舍掉之后，
它在那位读者的屏幕上根本不存在，再要求它写 `vs` 或 `baseline` 就是凭空造债。

**R25 直接复用 [scripts/lib/lang-mention.ts](../scripts/lib/lang-mention.ts) 的
`detectForeignLanguageMentions`，不要重写。** 它是大小写敏感 + ASCII 边界的匹配：
`JavaScript` 里含 `Java`（靠边界排除）、`Go` 撞英文动词（靠大小写与词边界排除）。
单测见 `tests/unit/lang-mention.test.ts`。

**R25 有一个例外：`registry.yaml` 的 `mentionGroups` 里同组的语言互相点名不算幽灵**
（ADR-71，当前只有 JavaScript ↔ TypeScript）。判据按**两门**算 —— 一格里提到 M 合法，
只要 M 与「本语言」或「该格面对的基准」同族，见 `isKindredMention`。
之所以要按两门算：一格的说明描述的是**那一列**，`vs.javascript` 讲的就是 JavaScript
那一列，读者从哪门语言进来都一样。`registry.yaml` 的注释里写了为什么 ArkTS
**不在**这个组里 —— 它不是 JavaScript 的超集，是一门独立的语言。

### 6.3 规则的级别（S8 定稿）

**R22 / R23 已翻成 error**：内容补齐期间它们是 warn（那时把构建变红，会把「还没写完」
和「写错了」混成一个信号）；账目归零后翻级。两者都是**硬契约** ——
`vs` 缺一份读者永远看不到，基准列空着就是坏页，不存在「合法地留空」。

**R24 刻意保持 warn**，没有跟着翻。它判的是「键缺失、且没标 `absent`」，
可是**空框本身是合法的**（§4.4）：内容天然疏密不均，某门语言在这个知识点上
无话可说很正常，不必为此撒一个 `absent: true`（那是另一个意思）。
翻成 error 会逼作者在「还没写」与「本来就没有」之间二选一 ——
而那正是这个字段设计出来要区分的两件事。**它是一条提醒人去确认的规则，
不是一条可以自动判定对错的规则。**

**R22 的求值域含「已启用但还没写内容」的语言** —— 新启一门语言会立刻红。
这是刻意要的：宁可让人在 registry 里显式写 `enabled: false`，也不要上一列空白。

R22 / R24 / R20g / R27 都按 `(语言|基准, 板块)` **汇总成一条**输出（逐条会刷屏）；
逐条待办在 `npm run content:report` 的**逐存放组账本**里。

## 7. 数据流与分层

### 7.1 五个层次

```
L4 呈现层   views/ + components/
             只依赖 ContentRepository 接口与生成的静态注册表
L3 应用层   stores/ + composables/
             用户设置、当前基准/语言集、派生视图态
L2 领域层   content/repository.ts  content/boxView.ts
             取数契约 + 双角色取值（纯函数，可单测）
L1 内容产物 src/generated/*（构建期生成，只读，不手改）
L0 内容源   content/**（YAML，唯一人工编辑入口）
```

依赖方向严格单向：L4 → L3 → L2 → L1 →（构建期）L0。
**禁止**：L4 / L3 直接读 YAML；手改 L1；`content/` 里出现可执行代码。

### 7.2 构建期（唯一的内容真源路径）

```
content/**/*.yaml
   │
   ├─▶ [1] validate    R1–R27 规则集，error 级非零退出（CI 阻断闸门）
   │
   ├─▶ [2] generate    sections.gen.ts（SectionId）→ registry.gen.ts（LanguageId + 常量）
   │
   ├─▶ [3] highlight   Shiki 构建期预高亮（css-variables 主题，单份 HTML）
   │
   └─▶ [4] emit
         src/generated/content/<语言>/<板块>/<存放组>.json   一个存放组一个分片
         src/generated/static/<基准>--<目标>.json            对级：陷阱 / 词典 / 路线
         src/generated/search-index/<语言>.json              搜索倒排索引，**按语言分片**
         src/generated/catalog.json                          池 + 每基准章节分组（小、eager import）
         src/generated/manifest.json                         ★ 路由 / SEO / 板块 / pairs 的单点来源
         src/generated/registry.gen.ts  sections.gen.ts  i18n.json  attributions.json
         public/sitemap.xml（需 PC_SITE_URL）

   └─▶ [5] prerender   （vite-ssg，`npm run build` 的一部分）
         dist/<route>/index.html     含真实内容的静态 HTML
         dist/404.html               GH Pages 的 SPA fallback
```

**`src/generated/` 是唯一的分界点**：左边是作者的世界（YAML），右边是程序的世界（JSON / TS）。
跨越只能由 `npm run content:build` 单向完成 —— 这消灭了「改了 YAML 但忘了重建」导致的幽灵内容。

**`manifest.json` 是多处单点来源**：`routes`（预渲染与 sitemap 共用）、
`pairs`（左栏与死链防护共用）、`sections`（板块属性）、
`seo`（静态注入与运行时 `usePageMeta` 共用同一份文案）。

**`catalog.json` 与 `manifest.json` 的分工**：前者是内容清单（章节、feature、
`featureIndex`），后者是站点元信息（路由、SEO、板块）。`catalog.json` 小且被急切导入 ——
左栏、面包屑、计数都要它，晚一步就是一片「加载中」。

### 7.3 运行期

```
App boot
  └─ manifest.json + catalog.json + registry.gen.ts（随主包）
       ├─ 恢复用户设置（pc:v1:*）
       └─ router 解析
            └─ 守卫：解析板块 → 按需 import 分片（**所有可见列都要 await 完**）→ 视图同步渲染
                 ├─ SectionDispatchView 按板块的 shape / renderer 选组件
                 └─ 交互 → usePersistedState 回写
```

**守卫里完成取数**（而不是组件内 `await` / `<Suspense>`），是为了让 SSG 与 CSR 走同一条路径 ——
否则预渲染出的 HTML 与客户端渲染结果会不一致。

**守卫里要把所有可见列的分片都 `await` 完**：对比语言不进 URL，
所以换勾选不产生导航、守卫不会重跑；而 SSG 是同步渲染的 ——
只等基准列的话，其余列还停在「加载中」，预渲染出来就是空壳。
`finalize-dist` 有一条专门的探针抓这个。

## 8. 运行时架构

### 8.1 路由与板块分发

路由只有**两条**（章节型 / 列表型），板块是 `params.section`：

```
/compare/:baseline/:section/:chapter   → SectionDispatchView
/compare/:baseline/:section            → SectionDispatchView（+ 板块入口，由守卫分流）
```

`SectionDispatchView` 按板块注册表的 `shape` 与 `renderer` 选组件：

- `shape: chapter` → **默认** `ChapterCompareView`（新的章节型板块零代码复用）
- `shape: list` → 查 `RENDERERS` 映射表（`pitfalls` / `glossary` / `roadmap` 各一个）

列表型**刻意没有默认渲染器**：三种列表的交互差异很大（陷阱有搜索与严重度筛选、
路线有进度持久化、词典是简单词条列表），硬套一个通用模板会把它们削平成最弱的那一个。

**守卫里有一条必须遵守的规则**：列表型分支必须 `return true`，不能返回
`sectionEntryPath(...)` —— 列表型板块的「入口地址」正是当前地址，
返回它等于自我重定向，vue-router 会判定无限重定向并 abort 导航。

**`compareEntryPath()` 与 `firstChapterSection()` 是两件事，不要合并**：
前者是「站点落点」（从 registry 里 `landing: true` 的板块起找，骨架期找不到就顺着 order 往后走），
顶栏「多语言对比」与首页基准卡片**复用同一个函数**，所以「点导航」和「敲地址」必然落到同一处；
后者是「第一个有章节的板块」，用于切基准时保留章节语境与语言页的入口。

### 8.2 状态模型

| 状态 | 归属 | 持久化 | 说明 |
| --- | --- | --- | --- |
| `lastBaseline` | languageStore | ✅ | 只记「上次选的是谁」，供无基准的路由用 |
| `compareLangs` | languageStore | ✅ | 章节型板块的**多选**列 |
| `preferredTarget` | languageStore | ✅ | 速查三兄弟的方向，**跨板块共享** |
| `viewMode` / `density` / `theme` | uiStore | ✅ | 三个正交设置（`viewMode` 只有矩阵 / 卡片并排两态，ADR-61） |
| `routeBaseline` / `routeSection` | languageStore | ❌ | 由 App 的路由 watcher 写入 |
| 章节内容 | contentStore | ❌ | 路由驱动，切走即释放 |

持久化统一经 `usePersistedState`（基于 `@vueuse/core`），key 前缀 `pc:v1:`，
版本不兼容即**直接丢弃**（单用户工具，迁移成本 > 收益）。

**两条容易踩的时序**：

1. **守卫里要算目标时必须传路由里的基准** —— 守卫跑在 App 的路由 watcher 之前，
   那时 `routeBaseline` 还是 null，`effectiveBaseline` 会落到 localStorage 的「上次选择」上，
   用错基准就会加载另一套分片，页面**静默变空白**
2. **换对比语言不产生导航** —— 对比语言不进 URL，路由守卫不会重跑。
   所以守卫必须在首次进入时就把所有可见列加载完（§7.3）。

### 8.3 差异机制（3 层，职责互斥）

| 层 | 机制 | 数据来源 | 时机 |
| --- | --- | --- | --- |
| L1 | 等价性四态徽章（颜色 + 图标 + 文字三重编码） | `equivalence.<基准>`（手写） | — |
| L2 | 行为差异内联注释（`@note`） | 构建期抽取 | 构建期 |
| L3 | 无等价说明（`absent` + 替代做法） | `baseline` / `vs.<基准>` | — |

**曾经还有两层运行时机制，S9 一并删掉**（ADR-61）：行级 diff 高亮（运行时 jsdiff）与
「只看有差异的项」过滤。两者都挂在同一个「基准差异」展示模式上，而那个模式要回答的问题
L1 已经回答了 —— 等价性徽章说的就是「差在哪、差多少」，而**逐行着色**回答的是
「这两段代码的字面差异」，那是编辑器/`git diff` 的职责，不是一张跨语言对照表要回答的。
代价也不小：它让每个对比框都带一份按 (feature, 基准, 语言) 缓存的运行时状态，
再叠一个只在某种模式下才存在的渲染分支。删除后 `diff` 依赖也从 `dependencies` 移除。

**这一层是刻意留下的空白**：如果将来真的需要行级对照，正确的做法是**构建期**为
每个 (基准, 目标) 对预计算 —— 那个组合数是封闭的（3 × 4），不像当初设想的「几十种」。

### 8.4 代码展示

| 项 | 决策 |
| --- | --- |
| 高亮 | Shiki **构建期**预高亮，`css-variables` 主题（单份 HTML，明暗靠 CSS 变量切换）；Shiki 是 devDependency，不进客户端包 |
| 字重补偿 | 该主题不输出 font-style / font-weight，靠 CSS 属性选择器按 token 变量名补偿；补偿失效时 `render.ts` 自动降级为双主题 |
| 复制 | 复制**原始 code**（非高亮 HTML），已剥离 `@note` 标记；高危注记的 `⚠` 在 code 内，会一并被复制 |
| 多段 | 每段一个代码块，段间细线分隔，段标签在块上方 |

**`@note` 内联标记**：差异说明写在代码注释里，不用行号锚定（行号会随编辑静默漂移）。
标记必须出现在**该语言自己的行注释前缀**（`meta.comment.line`）之后：
`x = 1  # @note 赋值即声明`。构建期 [extractNotes](../scripts/lib/core.ts) 抽取时
**只剥掉标记本身**，`@note` 与 `@note!` 的说明**都留在代码行内**；
`@note!` 的差别只是说明前多一个 `⚠`（随 `code` 一起被复制）。
搜索索引收的是 `allNotes`（全部注记），别只取 `notes`（仅高危）。

> **前缀写错是静默失败**：`@note` 前面没有该语言的行注释前缀时，
> 该注记既不报错也不渲染 —— 只是从页面上消失。R4 / R9 会抓这种情况，
> 但只在它确实构成一条「标记」时；写错成别的注释形态（如 HTML 注释 `<!-- @note -->`）
> 就完全在规则视野之外。填内容时照着 `meta.yaml` 的 `comment.line` 抄。

### 8.5 搜索

**分词**：MiniSearch 基于空格分词，中文会**静默失效**。`Intl.Segmenter` 实测不可靠
（`'数组与列表'` → 丢掉「数组」），因此走 **bigram**（unigram + 相邻二元组），
查询侧 `combineWith: 'AND'`。[search-tokenize.ts](../src/content/search-tokenize.ts)
**构建期与客户端共用同一份** —— 两边分叉会导致同一个静默失败。

**分片**：索引按**语言**分片（`src/generated/search-index/<语言>.json`），
客户端加载**当前可见的那几门**，于是「搜到的」与「屏幕上能看到的列」天然一致，
查询侧不需要再过滤。速查三兄弟归入**目标语言**的分片。
索引收的是注记 + 说明文本，**不含代码原文**。

### 8.6 两个层级、两处控件

语言这件事在界面上分成两层，**控件放在哪一层不是排版偏好，而是它们的作用域决定的**（ADR-59 / ADR-60）：

| | 基准语言 | 对比语言 |
| --- | --- | --- |
| 位置 | **左栏顶部，吸顶**（`SideNav.vue` → `BaselineTabs`） | 页内选择条（`CompareLanguageBar`） |
| 控件 | `.pc-btn` chip（标签 + 一排按钮，方框外观） | `.pc-btn` chip（同一套） |
| 作用域 | 整页的参照系，**换它 = 换一整套内容与地址** | 页内看到的列，只重画当前页 |
| 变化时 | **导航**（`useBaselineSwitch` → `router.push`） | 只改本地状态，不产生导航 |
| 存在范围 | **全站**（首页 / 速查 / 内容来源都有） | 只有对比页（首页等页面没有列） |

**两者是同一套 chip、同一个方框外观**，区别只由位置与行为表达。曾经刻意分成两种
控件语法（连体分段控件 = 页面本身、独立 chip = 页内的列），想靠「实心 vs 浅色」说明
层级 —— 实测那个信号太隐晦：读者看到的是两排长得不一样的东西，而两排各是什么仍然
要靠标签去读，形态没省下那句说明，只多了一种要学的样式。

**两个吸顶件等高，且是「右向左看齐」**：它们上下相邻地贴在顶栏下沿（`--pc-header-h`），
高度不一致就会看出参差。做法不是把左栏那个拉高去凑页内那条的实测高度
（`--pc-lang-bar-h`）—— 那会让左栏方框明显发虚，而且页内那条一折行就把值带跑；
而是**两边共用同一套 chip 与同样的纵向内边距 6px**，于是都由 `.pc-btn` 的 29.6px
决定，高度恒为 43.6px。改任一侧的纵向 padding 必须同时改另一侧。

**吸顶后两者都与顶栏留同样一截间隙**（`--pc-sticky-gap`，8px）。留的方式是给
**吸顶块本身**加 `padding-top` + 不透明底色，而不是把方框往下挪：sticky 约束的是块的
**边框盒**，块吸在滚动口上沿后，方框由这段上内边距往下推 —— 那 8px 于是是「带状底」
而不是缝，滚上去的菜单项 / 正文标题从它底下过，不会透出来。页内那条为此拆成两层
（外层吸顶留间隙、内层 `.pc-lang-bar-box` 是方框）：边框与圆角都在方框上，
合在一层的话那 8px 会落进边框里，看起来只是内边距变大。实测两边方框上沿都落在
y=60（顶栏下沿 52 + 8）、高都 43.6px。

**矩阵表头不吸顶**（ADR-70）：`table.pc-matrix thead th` 只有 `position: sticky` 而没有
`top`，随页面一起滚。曾经它钉在 `calc(顶栏 + --pc-lang-bar-h)`，与页内那条一起构成
「滚动时始终可见的两条」；去掉之后，`--pc-lang-bar-h` 仍然要实测，但读者只剩一处 ——
`.pc-anchored` 的 `scroll-margin-top`（锚点跳转时标题不能被页内那条盖住）。
页内那条的下间隙因此不再牵动任何别的东西，就只是「方框与表格之间留多少」这一个旋钮，
**不参与**左右对齐（上间隙参与，它决定两个方框的上沿）。

- **基准在左栏顶部且吸顶**：它是整页的参照系，而首页、速查、内容来源这些
  **没有对比列**的页面同样需要它 —— 放在页内那条选择条上时，这三页就没有入口
  （P7 到 S9 之间一直如此）。放进左栏是因为两者本来就是一件事的两面：
  左栏是**当前基准的**目录，参照系与目录放在一起，读者不必在两处之间来回确认
  「我现在以谁为基准在看谁」。吸顶是必须的：左栏自己就是滚动区，三个按钮若跟着
  长菜单一起滚上去，读到「工程实践」时就看不出当前基准是谁了。
  **代价**：左栏收起时它一起消失（基准切换因此只在菜单展开时可用），
  且窄屏（≤900px）下左栏是正文上方的普通块、不吸顶 —— 那两处都与左栏本身的形态一致。

- **对比语言全量列出、不可用的置灰**：候选是**全部已启用语言**，按 registry 的声明序
  （JS / Python / Java / Go / Rust）。两类灰的**理由不同、title 也不同**：
  ① 它正是当前基准（已经在最左那一列了）；② 本模块 / 本章没有这门语言的内容。
  曾经的做法是把当前基准直接**藏掉**、缺内容的照旧可点 —— 前者让人以为这门语言
  不在对比里，后者点完毫无反应，看着像控件坏了。

- **可见性判据与列裁剪同源**：章节型板块的「不可用」判据是 `hasChapterContent`
  （与路由、与列裁剪同一个函数），由 `ChapterCompareView` 按**本章**算好传进来；
  速查三兄弟的判据是 `pairTargetsOf`（该方向有没有内容）。

## 9. 可扩展性

### 9.1 三条承诺（都有可执行断言）

| 操作 | 改动面 | 断言 |
| --- | --- | --- |
| **加一门语言** | 数据目录 + `registry.yaml` 注册 | [`verify:ext`](../scripts/verify-extensibility.ts) |
| **加一个板块（`shape: chapter`）** | `registry.yaml` 的 `sections` 段 + 内容目录 | [`verify:sections`](../scripts/verify-section-extensibility.ts) |
| **加一个知识点 / 章节** | 只加 YAML | `content:validate` |

`verify:ext` 有三道断言：① 造一门临时语言，断言 `src/` 里没有任何代码提到它；
② 扫描**真实启用语言 id** 的**带引号字面量**（`if (baseline === 'javascript')` 这类写死基准的分支是它抓的）；
③ 扫描**面向用户的文案**（i18n 的值 + `.vue` 的 `<template>`，先摘掉 `<script>` 与 HTML 注释）
里有没有写死语言**显示名** —— 三门基准权重相同，
`PitfallCard` 的徽章曾硬编码「JS 开发者必踩」，在 java2python 页面上照写 JS，就是这条抓的。

> 前两道**刻意保持朴素**：不剥注释、不做语法分析 —— 剥离注释会引入
> 「字符串里含 `//` 被当成注释吃掉」这类假阴性，而它们的全部价值就在「宁枉勿纵」。
> 第三道反过来**必须剥注释**：代码注释里拿「从 JS 出发」举例是给维护者看的，不是文案。

`verify:sections` 也有三道断言：① 扫描 `src/` 里硬编码的板块 id 字面量
（白名单每条写了理由）；② 断言 `sections.gen.ts` 与 `registry.yaml` 同步；
③ 断言 `content/catalog/` 的板块目录与注册表**双向一致**，且每个目录都有池。

> 第 ③ 条是 S8 换的判据 —— 它原来查「每个 topic 的 section 都注册过」，
> 靠的正是被删掉的 `registry.topics`。**v2 取消了 topic 概念，但同一类错误换了形态仍在**：
> 建了内容目录却忘了注册（整个目录被静默忽略），或注册了却没有目录（该板块永远没内容）。
> 判据只对 `shape: chapter` 的板块成立 —— 速查三兄弟是 `shape: list`，
> 内容在 `content/pairs/`，本来就没有池。这条边界是写断言时被它自己抓出来的。

> **新增 `src/` 代码时的连带约束**：注释与 message 一律用
> `<section>/<chapter>/<feature>` 这类占位式措辞，可同时过两个脚本的字面量检查。

### 9.2 加板块的边界（诚实版）

- `shape: chapter` → **零代码**
- `shape: list` 且复用已有渲染器 → **零代码**（注册表里写已有的 `renderer` 名）
- `shape: list` 且是全新交互 → 需新增一个渲染器组件并在 `SectionDispatchView` 注册。
  **那是新 UI，本就不该免**

### 9.3 预留能力与触发条件

| 能力 | 预留形式 | 启动触发条件 |
| --- | --- | --- |
| 在线运行代码 | `Runner` 接口（全部 `kind: 'none'`） | 至少 1 门语言有稳定的 WASM 运行时，且用户明确要求 |
| 内容 i18n | UI 文案走 `t()` | 出现非中文读者（内容 i18n 成本 ≈ 全部内容工作量 × 语言数） |
| PWA / 离线 | 无 | 用户明确要求 |
| 行虚拟化 | 用 `content-visibility` 替代 | 单章 Feature > 150 |

## 10. 非功能要求

### 10.1 性能预算与实测

| 指标 | 预算 | 实测（2026-10-03） |
| --- | --- | --- |
| 单章内容分片（gz） | ≤ 60 KB | **3–7 KB** |
| 搜索索引单分片（gz） | ≤ 280 KB（承认现状的上调，见 §7.4） | js 99 / java 126 / python 126 / go 130 / rust 133 —— **全部在预算内** |
| 首屏 JS（gz，不含按需分片） | ≤ 180 KB | `vite build` 报告 |
| LCP / INP / CLS | 2.5s / 200ms / 0.1 | Lighthouse |
| 切语言列 / 基准 | ≤ 100 ms | Performance 面板 |

### 10.2 可访问性

不以颜色为唯一判据（四态徽章 = 颜色 + 图标 + 文字）；表格用真 `<table>` + `th[scope]`；
横向滚动区 `role="region"` + 键盘可达；全站可 tab、`:focus-visible` 有可见焦点环；
尊重 `prefers-reduced-motion`。目标 WCAG 2.1 AA 关键项。

### 10.3 安全

纯静态站点无后端 ⇒ 无认证 / 越权风险。真实威胁面是**内容注入**（LLM 产出 → Markdown → 渲染）：

- 富文本走 `markdown-it` 且 **`html: false`**（禁裸 HTML）
- `v-html` 的唯一合法输入是构建期产物（Shiki 输出与渲染后的 Markdown），
  集中约束在 2 个组件里
- CSP 用 `<meta http-equiv>` 兜底（GH Pages 无法下发响应头）；
  已知限制：meta CSP 不支持 `frame-ancestors`
- 不引入任何第三方 CDN / 字体 / 分析脚本

### 10.4 SEO

预渲染是**硬需求**（纯 CSR 对不执行 JS 的爬虫等价于空页面）：

- 每条路由产出含真实内容的静态 HTML（`vite-ssg`），CSR 仅作水合层
- `manifest.routes` 是**可索引路由的单点定义**，预渲染与 sitemap 共用 → 不可能不一致
- `prerenderExtra`（预渲染但**不进 sitemap**）现在只有 `/search`
  （结果是客户端渲染的，爬虫只会看到空输入框）
- `dirStyle: 'nested'` 是**必须**的：默认 `flat` 产出 `.html` 后缀，
  而 GH Pages 不做无扩展名解析 → 只有首页能打开
- 构建最后一步 [finalize-dist.ts](../scripts/build/finalize-dist.ts) 做两件验收：
  ① 每条路由的 HTML 含该页真实内容；② **不含「加载中…」**
  （「页面结构在、内容没渲染出来」这类空壳的探针）
- **探针的正则必须跟着路由形状改** —— feature 路由从 2 段变 3 段时漏改一处，
  验收就静默失效（正则不匹配 → 返回 null → 跳过检查）

SEO 文案里出现的**目标语言是按运行时同一套规则算出来的默认方向**（速查板块），
构建期与运行时必须同判据。

### 10.5 i18n

UI 文案抽到 `content/i18n/zh-CN.yaml`，经 `t()` 取用；**内容本身不做多语言**
（明确列为长期非目标）。注意 **i18n 文案是纯文本，不经过 Markdown 渲染**，
写 `**强调**` 会原样显示。

面向用户的文案里**不许写死语言名**：语言名一律从 meta 取，
i18n 里走 `{baseline}` / `{compared}` / `{target}` 这类占位符。

## 12. 内容成本账与爬坡

### 12.1 成本账（本架构最大的代价，必须如实说明）

| 语言 | `baseline` | `vs` 份数 | 合计 |
| --- | --- | --- | --- |
| JavaScript（基准） | 1 | vs Python、vs Java | 3 |
| Python（基准） | 1 | vs JS、vs Java | 3 |
| Java（基准） | 1 | vs JS、vs Python | 3 |
| Rust | — | vs JS、vs Python、vs Java | 3 |
| Go | — | vs JS、vs Python、vs Java | 3 |

**12 份差异说明 + 3 份基础描述。** 基准固定为三门之后，这个数字是**封顶的** ——
以后加语言只按「每门语言 3 份」线性增加，不会因基准变动而重算。

按 v1 规模估算（基础语法 72 + 语言之内约 60 + 语言之外约 30 ≈ 160 个知识点），
每个知识点每门语言要为每个基准写一段 → 量级 **2000+ 条**，而 v1 全站是 1326 条实现。

> **这个估算已被 S7.0 的实践检验：实际落在 104 个知识点，比估算低 35%。**
> 原因是 v1 的口径把「每门语言各一份的实现数」当成了知识点数 ——
> 旧 `basics` 72 条里有大量是同一知识点的三种写法。压缩比与 `express`
> 在试点时的表现一致（旧 72 条 → 新 27 条）。

**缓解措施**（§4.4 的可空规则）：只在不同处写，相同处留空。
但「为每个基准各写一份」这件事本身无法回避 —— 这是选「每门语言为每个基准各写一份」的必然代价。

**§2.5 的章节分组不在这笔账里。** 它只决定「同一个 feature 摆在哪个位置」，
既不新增内容、也不新增 `vs` 份数。换句话说：**分组自由度是免费的，视角成本才要钱。**
这条性质很重要 —— 它意味着以后调整章节分类、给某个基准换一套组织方式，
都不需要重写任何一格内容。

### 12.2 爬坡的形状

旧内容推倒重写，不迁移。路径是：**立契约 → 立骨架 → 通管线 → 每基准章节分类 → 填内容**。
**五步都已完成**（S7.4 写完三个基准，S7.5 补完 rust / go 对比列，S7.6 重指速查）。
当时的爬坡方式是按 **板块纵深** 分批，
**一批 = 一个 (板块, 存放组)，批内写三份基准文件**（每份含 `baseline` + 另外两份 `vs`）。

这么排的理由：

- 板块完成时**三个基准视角同时成立**，不会有「某个基准点进去是空的」这种中间态；
- **永不回填** —— 若先把 JS / Python 铺满再引入 Java，就得回头给已有文件补 `vs.java`。

**每批的验收**：

```bash
npm run content:validate     # error 必须 0
npm run content:report       # 逐存放组账本：have/N 与「vs 全」
```

重点看 **R23 / R24**（该写的说明还没写）、**R20e**（池里有 feature 没被任何基准引用）、
**R27**（基准列空洞）。**注意 R22 / R23 现在是 error**（§6.3）——
内容没写全时构建会直接失败，这是刻意的。

**rust / go 放在最后**：两门都不是基准候选，只写 `vs.{javascript,python,java}` 三份、
不写 `baseline`。**纯新增，不触发任何回填** —— 这一步已经走完（S7.5，22 批）。

后续若要再加一门语言，成本账与分批方式同上：**线性成本，不触发回填**（§12.1）。

### B.2 v2 重构起（ADR-40 – ADR-71）

| ADR-48 | 清单集中在 `content/catalog/`，与内容分离 | 增删章节、调换顺序、改标题都只动一处，**不动任何语言文件** |
| ADR-49 | 文件名不带序号，取消 `order` 字段 | 序号会在增删章节时引发连锁改名；顺序的唯一真源是 catalog 的数组顺序 |
| ADR-50 | 方向性内容独立到 `content/pairs/` | 速查三兄弟的主语是方向，塞不进任何单个语言目录；与 `languages/` 并列，职责一眼可辨 |
| ADR-51 | 内容的存放单位下位为 **`group`（存放组）**，与展示章解耦 | 章节随基准变（ADR-52），内容若跟着它走，同一个知识点就要为每个基准各写一遍 —— 那正是本架构要避免的平方成本 |
| ADR-52 | **章节分组按基准各一份**：清单分「池 + 每基准分组」两层 | 用户熟悉的语言怎么组织知识，就怎么给他看；而分组自由度**不增加任何内容成本**（ADR-51） |
| ADR-53 | 顶层板块换成四段：`express` / `model` / `mechanism` / `practice`，**主题式命名** | 按「迁移者先关心什么」重划（读懂 → 改写 → 敢动 → 落地）。命名刻意避开课程口吻 —— §1.1 的定位是查阅型地图，不是教程 |
| ADR-54 | 全局 feature id 收缩为 `<板块>/<feature>` **两段** | feature 属于池、与基准无关，所以 id 里不能有章节（章节随基准变）；也不能有存放组 —— 它是界面上看不见的存放细节。详情页地址因此稳定、可分享、与当前基准解耦 |
| ADR-55 | **章节可见性只认内容**（`hasChapterContent`），不认「有没有章节分组」 | 骨架先于内容（S7.0 落齐 12 份分组、正文分批填）。若按分组判可见，骨架一落地就有一整屏 404 死链。判据收敛成一个函数，并由 `tests/unit/section-model.test.ts` 守着「与路由同源」 |
| ADR-56 | **过渡期规则只翻 R22 / R23 成 error，R24 永久保持 warn** | 三者都源于「补齐期一律 warn」，但性质不同：R22 / R23 是硬契约（`vs` 缺一份读者永远看不到、基准列空着就是坏页），不存在「合法地留空」；R24 判的是「键缺失且没标 `absent`」，而**空框本身合法**，翻成 error 会逼作者在「还没写」与「本来就没有」之间二选一 —— 那正是 `absent` 这个字段要区分的两件事。它是提醒人确认的规则，不是能自动判定对错的规则 |
| ADR-57 | **v1 的 schema 全部删除**（S8） | `featureSchema` / `chapterSchema` / `topicConfigSchema` / `snippet*` / `RenderedSnippet` 等在 v2 下**一个消费者都没有**（逐个统计过），留着只会让后来者以为还有两条路。`registrySchema.topics` 与 `registry.yaml` 的 `topics: {}` 占位一并删 —— 那个字段的存在只是为了喂一个已死的 schema |
| ADR-58 | **语言的显示顺序 = `registry.yaml` 里 `languages:` 段的书写顺序**（S9） | 顺序会直接出现在界面上（基准选择器、对比语言条、矩阵列、首页三张基准卡），而「哪门在前更好读」是内容判断，不是文件系统的属性。按目录名字母序的结果是 Java / JS / Py、Go 排在 Python 前面 —— 读起来是随机的。**不另设 `order` 字段**：那个字段与顺序本身是一对会漂移的真源（ADR-49 的同一个理由） |
| ADR-59 | **基准语言的选择入口在左栏顶部并吸顶**，对比语言留在页内（S9） | 基准是整页的参照系，而首页 / 速查 / 内容来源这些**没有对比列**的页面同样需要它 —— 挂在页内那条选择条上时这三页没有入口。放进左栏是因为左栏正是**当前基准的**目录，参照系与目录本就该在一起；吸顶（`position: sticky; top: 0`）则是因为左栏自己是滚动区，不吸顶就会被长菜单顶走。代价是**左栏收起时基准入口一并消失**，且窄屏（≤900px）下左栏是正文上方的普通块、不吸顶。两处入口用的是**同一套 chip 控件**（连体分段控件那条路已废弃：形态想表达的层级太隐晦，见 §8.6），区别只由位置与行为表达。两侧吸顶后各留一截同样的离顶间隙（`--pc-sticky-gap` = 8px，在**吸顶块自己**的 `padding-top` 上，因此那截是带状底而不是缝） |
| ADR-60 | **对比语言全量列出，不可用的置灰**（S9） | 候选 = 全部已启用语言，按 ADR-58 的顺序。两类灰理由不同：① 它正是当前基准；② 本模块 / 本章没有它的内容（判据 `hasChapterContent` / `pairTargetsOf`，与列裁剪同源）。曾经把当前基准**藏掉**、缺内容的照旧可点 —— 前者让人以为这门语言不在对比里，后者点完毫无反应、看着像控件坏了 |
| ADR-61 | **删除「基准差异」展示模式、「只看有差异的」过滤与运行时 diff 引擎**（S9） | 两者挂在同一个模式上，而那个模式要回答的问题 L1（等价性徽章）已经回答了。**逐行着色**回答的是「两段代码的字面差异」，那是编辑器 / `git diff` 的职责，不是一张跨语言对照表要回答的；而它的代价是每个格子都带一份按 (feature, 基准, 语言) 缓存的运行时状态，再叠一个只在某种模式下存在的渲染分支。留下的两个模式（矩阵 / 卡片并排）是纯粹的排版选择。`diff` 依赖随之从 `dependencies` 移除 |
| ADR-62 | **卡片并排的横向溢出给显式提示**（S9） | 一排卡片每列最小 340px，五门语言在常见宽度下必然溢出，而滚出去的几列在视觉上**完全不存在** —— 细滚动条太安静，读者不会想到右边还有。做法是两侧渐隐遮罩（安静的那一半：告诉你有东西被挡住）＋ 一句文字（说得出口的那一半：告诉你可以拖），两者都在拖到那一头后自己消失。纯 CSS 做不到「有溢出才显示」（`scroll-state()` 未落地，`:has()` 问不出布局），所以量 `scrollWidth` |
| ADR-63 | **一门对比语言都不勾 = 只看基准列**，空集合不回落成默认语言（S9） | 此前有一整套方向一致地**反对空集合**的兜底：初始化时把空集合写回默认对比语言、`compareMeta` 回落到第一门非基准语言、`ensureCompareColumn` 再把回落值写回存储、`toggleCompare` 用 `set.size <= 1` 拦住最后一门的取消、路由守卫与视图各按同一套回落算可见列。代价与 ADR-34 那层兜底完全一样：补出来的那门**用户既没勾也去不掉**（界面上它显示为已勾，点它是「新增」而不是「取消」），而读者真正想表达的「我只要看基准」反而无从表达。这套逻辑一起删（store / 守卫 / 视图同口径），换来的是一条更简单的规则：**勾选集合是什么，就渲染什么列**。首访默认（`defaultCompareLanguage`）与 `reset()` 仍给出一门对比语言 —— 那是**默认值**不是兜底：它出现在勾选态里，用户看得见、取消得掉 |
| ADR-64 | **删掉正文上方那三块说明**：等价性徽章说明、覆盖范围提示、章节页的草稿数行（S9） | 三块都曾以「宁可多一句说明，也不要一个看起来失灵的控件」为由存在，但各自的前提已经不在：① **等价性徽章说明**（`EquivalenceBaselineNote`）在每一页正文之前重复一遍四个符号的含义，而「（基准）」列标与左栏的基准选择器已经回答了「以谁为参照系」；② **覆盖范围提示**用「当前可见列」去比「已启用语言」，于是只显示基准列时会说出「本模块目前只对照 JavaScript」这种错话 —— 五门内容已 100% 铺满，它本来就再不会说对话；③ **章节页草稿数**（「本节有 N 条实现尚未经过人工校对」）在 520 条全 draft 时每章都出现，逐格的「未经人工校对」徽章已经把同一件事说得更准（哪一格没校对，而不是这一章有几格）。三处都是**删干净**：模板、脚本里只服务于它的声明、以及只被它引用的 i18n key 一并去掉 —— 注释掉模板而留着声明，会让 `typecheck` 挂着一串 TS6133，下一个人不知道那是待恢复还是待删除 |
| ADR-65 | **速查三兄弟扩到 12 个方向**（3 基准 × 4 目标，S10） | 此前只有 6 个（JS 视角齐全 + python/java 各一个）—— 把基准切到 Python 或 Java，速查的目标选择条上就只有一个选项，而旁边四门语言明明都有内容。补齐后与 ADR-47「基准固定三门」配套：总量封闭、可预估（12 × 27 = 324 条），新增成本只随**启用语言数**线性增长。非基准语言之间不生成方向 —— 速查的主语是「带着基准的习惯过去」，没有基准就没有方向 |
| ADR-66 | **速查的来源留痕放 `pairs/<方向>/meta.yaml`**，三个内容文件保持顶层数组（S10） | 顶层是数组的文件没有地方放 `review`。改成 `{ review, items }` 会打破沿用至今的旧契约（loader / schema / 18 个文件一起动），所以与 `languages/<语言>/meta.yaml` 同构、一个方向一份。**它刻意不接入校验规则**：R3 / R6 / R17 仍只管 `languages/` 的对比框。但字段必须写进 schema —— 三个 pairs schema 都不是 `.strict()`，没声明的字段会被**静默丢弃**，那才是真正会骗人的形态 |
| ADR-67 | **速查的方向顺序与默认回落按语言书写序**（ADR-58），不是目录名字典序（S10） | 顺序是**可见的**：左栏的方向列表，以及 `resolvePairTarget` 在「勾选里没有该基准可用的目标」时回落的 `available[0]` —— 于是它同时决定了「以 Python 为基准的读者打开速查默认看到哪个方向」。字典序在补齐 12 个方向后会选中 `go`，书写序选 `javascript`。这条规则有**四处判据**：loader 的排序（`manifest.pairs`）、构建期 SEO 选向（`pickPairTarget`）、预渲染探针（`finalize-dist` 的 `pickPair`）、运行时解析（`pairTargetsOf`）—— 构建期那两处是运行时规则的副本，分叉了不会报错，只会让静态文案与页面说的方向不一致 |
| ADR-68 | **R5 收紧：`pitfalls.languages` 也必须 ⊆ 本方向两门**（S10） | 此前它只校验「语言存在」，于是一条 `javascript2python` 的陷阱可以把 `rust` 写进 `languages` 而完全不被发现；而 `glossary.perLanguage` 早就有这条硬约束。同一条口径在一边靠机器、一边靠人，等于没有。收紧后两侧都是 error。**散文部分仍然够不到**（`symptom` / `cause` / `fix` 里的字）—— 那由常设断言守，见 §11.2 |
| ADR-69 | **进入某基准时，把「唯一的那一勾被基准吃掉」换一门**（`ensureCompareFor`） | 默认对比语言是 Python，而首页那张卡片写的正是「我熟悉 Python」—— 点进去，唯一的勾选此刻的身份是基准列，多选对比退化成只剩基准一列，页面上看不出任何异常（守卫、校验、类型检查全都不报）。修的是**勾选集合本身**（优先默认对比语言，它正是基准时让位给书写序里的下一门），不是渲染层补一列 —— 后者就是 ADR-34 记的坑：那列不在 `compareLangs` 里，会被画成「已勾」却点不掉。与 ADR-63 不冲突：空集合（读者表达过的「只看基准」）一律不碰，触发条件严格是「集合非空、且去掉基准后为空」。函数幂等，守卫与 App 的路由 watcher 各调一次 —— 前者管**按修正后的集合加载分片**（晚一步就是「加载一列、渲染另一列」，预渲染直接空壳），后者管**渲染它的那个 store 实例**：实测整页加载那一路两者会分叉（localStorage 里已是修正后的值，页面上仍是旧列），只留守卫一处修不好 |
| ADR-70 | **矩阵表头不吸顶** | 表头曾钉在 `calc(--pc-header-h + --pc-lang-bar-h)`，与页内语言条一起构成「滚动时始终可见的两条」—— 长表格往下翻时列名一直挂在那里。**代价（也是这次取舍的另一面）**：滚过表头后就只能靠列里的内容认列。去掉 `top` 之后 `--pc-lang-bar-h` 仍要实测，但它的读者只剩一个：`.pc-anchored` 的 `scroll-margin-top`（锚点跳转时标题不能被语言条盖住），语言条的下间隙也不再牵动任何别的东西。`position: sticky` 保留、`left` 不动 —— 横向的列冻结与纵向吸顶是两条独立的轴，去掉的是后者 |
| ADR-71 | **R25 增一条「同族豁免」：`registry.yaml` 声明 `mentionGroups`，组内语言互相点名不算幽灵语言**（当前只有 JavaScript ↔ TypeScript） | R25 问的是「这一格的说明讲了屏幕外的语言吗」。可 JavaScript 与 TypeScript 在读者眼里是同一套生态的两面 —— 「JavaScript 自己没有泛型，要靠 TypeScript（或那门语法超集）」这句话里，TypeScript 不是屏幕上冒出来的第三门语言，而是**那一列本身的两个层次**。2026-10-03 实测：启用 TypeScript 时既有五门语言的内容里报出 **53 处 R25**（19 条聚合行），全是这一类句子；改写成「另一门静态超集」不会让读者更明白，只会让说明变含糊。**判据按两门算**：一格里提到 M 合法，只要 M 与「本语言」或「该格面对的基准」同族 —— 因为一格的说明描述的是**那一列**，`vs.javascript` 讲的就是 JavaScript 那一列，读者从哪门语言进来都一样（实测：只看本语言只能消掉一半，Python/Java/Go/Rust 的 `vs.javascript` 格仍会报）。**配置进 `registry.yaml` 而不是写死在分析器里**，与「加语言只加数据」同一条理由；R8 核对组内成员确实已登记（写错的豁免会静默失效）。**代价**：这是 R25 从「逐字点名」退到「按族点名」的一步，判据多了一层间接 —— 所以它**只有一处**，且刻意**不**把 ArkTS 放进去（它不是 JavaScript 的超集，是独立的语言，讲 JavaScript 时提到它确实是屏幕外的另一门）。速查三兄弟那一条同名判据（`content-contract.test.ts` 的「只讲本方向的两门语言」）**未同步**：它读的是 `pairs/` 的散文，当前 324 条里一处都没点名 TypeScript，等真要写 JS→TS 方向时再一并考虑 |
