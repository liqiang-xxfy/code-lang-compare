## 0. 三条命令

```bash
npm run dev              # 内容编译 + 开发服务器（改了 content/ 必须重跑，否则页面还是旧内容）
npm run content:validate # 只跑校验。这是 CI 的阻断闸门，error 级问题非零退出
npm run content:report   # 覆盖率 / 审阅状态 / 逐存放组账本 / 待校对清单
```

改完内容至少跑一次 `content:validate`（`content:build` 会自动先校验）。
`content:report` 在 error 非零时也会退出 1，不要拿它当纯报告挂在 `&&` 链中间。

## 1. 目录地图

内容分三层，**清单与内容分离，存放与展示也分离**：

```
content/
├── catalog/<板块>/                 ① 清单
│   ├── features.yaml               · 池：这个板块有哪些知识点（**与基准无关，全站唯一**）
│   └── <基准 id>.yaml              · 章节分组：该基准怎么把它们讲给读者听
├── languages/<语言>/<板块>/
│   └── <存放组>.yaml               ② 内容：boxes，key = 池里的 feature id
└── pairs/<基准>2<目标>/            ③ 方向性内容（速查三兄弟，唯一保留方向的组织方式）
```

| 名字 | 是什么 | 谁决定 |
| --- | --- | --- |
| **feature** | 一个知识点，id 只在**板块内**唯一 | 池 |
| **group**（存放组） | 内容文件的名字，**与基准无关** | 池里每个 feature 声明 |
| **chapter**（展示章） | 左栏与矩阵的行怎么分组、叫什么、什么顺序 | 每个基准各一份 |

**三者的关系是本架构的全部要点**：同一个 feature 在 JS 视角下可以落在 A 章、
在 Python 视角下落在 B 章，**而它的内容只写一份**（因为在池里绑定了 `group`，
内容按 group 存放）。所以——

- **改章节名 / 换顺序 / 重新分组 / 取舍知识点：只动 `catalog/<板块>/<基准>.yaml`，一个内容文件都不用碰。**
- **加一个知识点：要同时动池、分组、每门语言的内容文件**（下面第 2 节）。

> 全局 feature id 是**两段** `<板块>/<feature>`（如 `express/declaration`）。
> 里面没有章节 —— 章节随基准变，详情页地址却要稳定、可分享。

## 2. 加一个知识点（最高频）

### 第一步：在池里加一条

`content/catalog/<板块>/features.yaml`：

```yaml
features:
  - id: naming-convention        # 板块内唯一，kebab-case
    group: bindings              # 存放组 → languages/<语言>/<板块>/bindings.yaml
    title: 命名约定
    kind: concept                # syntax | concept | behavior | mapping | exercise
    summary: 名字怎么写只是风格，还是会影响可见性
    tags: [comparison]           # 可选，默认 []
```

`kind` 的取法：`syntax` 是「怎么写」、`behavior` 是「会怎样」、`concept` 是「是什么」。
`refFeatureId`（可选）是**跨板块的软引用**，写全局 id（`<板块>/<feature>`），用来把
「这里讲的东西其实就是那边的某个知识点」串起来。池里的**顺序不表达任何东西**。

### 第二步：在**想展示它的**基准的章节分组里引用它

`content/catalog/<板块>/<基准 id>.yaml`：

```yaml
chapters:
  - id: bindings
    title: 变量、作用域与提升
    features: [declaration, mutability, scope, hoisting, shadowing, naming-convention]
```

**只想在某个基准下展示就只改那一份分组** —— 这正是分层的目的。
被所有基准都取舍掉的知识点会被 R20e 提醒（「永不展示」）。

### 第三步：给每门语言各加一格

`content/languages/<语言>/<板块>/<group>.yaml`（本例是 `bindings.yaml`）：

```yaml
boxes:
  naming-convention:
    code: |
      const userName = "Ada";      // @note 变量 camelCase，常量 SCREAMING_SNAKE_CASE
    baseline: |                    # 本语言作**基准列**时显示
      JS 的命名只是约定，解释器不看名字。
    vs:                            # 本语言作**对比列**时，按当前基准取
      python: |
        Python 同样是约定，但社区规范更强（PEP 8）。
      java: |
        Java 也全是约定：类 `User`、方法 `getUser`、常量 `MAX_RETRY`。
    equivalence:
      python: analogous            # 缺 key = identical
```

### 第四步：看缺口

```bash
npm run content:validate    # error 必须为 0
npm run content:report      # 逐存放组账本：哪门语言哪一组还欠着
```

> 守护：R20a（引用不存在的 feature）、R20b（id 重复）、R21（box key 不属于该组）、
> R20e（永不展示）、R24（存疑空框）

## 3. 加一个存放组

存放组是「内容文件的单位」，粒度由作者定：**一个存放组 = 一个可以独立成立的知识块**。

1. 在池里给若干 feature 写上同一个新 `group` 名（kebab-case，即文件名）
2. 给每门语言建 `content/languages/<语言>/<板块>/<新组名>.yaml`
3. 在**想展示它的**基准的章节分组里把这些 feature 排进某一章
   —— 一章**可以跨多个存放组**（`express` 的「字符串与容器」章就同时引用 `strings`
   与 `containers` 两组）；存放组**也可以被拆到不同的章**（Python 视图把同一批
   知识点拆成「字符串」与「序列与映射」两章）

**存放组与展示章不必一一对应**，这是两者解耦的直接好处。池里声明了、却没有
任何启用语言写它的组会被 R20f 提醒。

> 守护：R20f（悬空存放组）、R21

---

## 3.1 加一个章节 / 调整章节分类

只改 `content/catalog/<板块>/<基准 id>.yaml`：加一条 `chapters` 项、改 `title`、
挪动数组位置（**顺序的唯一真源就是数组顺序**，没有 `order` 字段也没有文件名序号）、
把一个 feature 从一章挪到另一章、或者干脆不引用它（**取舍**）。

- 章节 id 只在「该基准 × 该板块」内唯一 —— **跨板块同名是合法的**
  （`express/collections` 与 `model/collections` 是两回事）。
- 同一个 feature 在同一基准下出现在两章会收到 R20h 提醒（多半是误操作）。
- 改完跑 `content:validate`：R20a 会拦住「引用了池里不存在的 id」。

> **取舍是正当手段**：Python 视角下不展示 `hoisting`（Python 没有变量提升，
> 以 Python 为参照系时这一行不该出现）。取舍之后，那一行对 Python 基准的
> `baseline` 说明也不再被要求（R23 的求值域只覆盖「该基准真正引用了的知识点」）。

> 守护：R20a、R20c（文件名与 `section`/`baseline` 字段一致）、R20h

## 4. 加一个板块

1. `content/registry.yaml` 的 `sections:` 段加一条（`shape` / `scope` / `columns` /
   `seo` 模板），并按需要声明 `landing: true`
2. 建 `content/catalog/<板块>/{features.yaml,<基准 id>.yaml}`

`shape: chapter` 的**零代码**（自动复用章节矩阵），`shape: list` 的复用已有渲染器也零代码。
`npm run registry` 会刷新 `sections.gen.ts`；`npm run verify:sections` 是这条承诺的可执行断言。

**注意 `seo` 模板里的 YAML 引号**：以 `{` 开头的普通标量会被解析成流式映射，
必须写 `title: "以 {baseline} 为基准 · {chapterTitle}"`。

> 守护：R20c（板块必须在注册表里）、R8（注册表自检）

## 5. 加一门语言

```bash
cp -r content/languages/_template content/languages/<新语言 id>
```

1. 填 `meta.yaml`：`id` 必须等于目录名；`comment.line` 驱动 `@note` 解析
   （写错会让注记**静默丢失**）；`shikiLang` 决定高亮；`baseline` 保持 `false`
2. 按板块填内容：`content/languages/<id>/<板块>/<存放组>.yaml`
   （文件名取自池里的 `group`，只写想清楚的那些组即可）
3. `content/registry.yaml` 的 `languages` 段登记，**先留 `enabled: false`**
4. 按板块填内容（写法见 §5.1）—— 22 个存放组写满之后，再把 `enabled` 翻成 `true`
5. `npm run content:build && npm run verify:ext && npm test`

**不需要改任何组件、类型或路由代码。** 基准固定为 JS / Python / Java 三门
（ADR-47），所以新语言**一律是对比列语言**：`vs` 要写全三门，`baseline` 可以省
（那是「本语言作基准列时」的说明，只有三大基准用得上）。

**为什么先 `false` 后 `true`**：`enabled: false` 期间这门语言**完全不参与校验**
（R20g / R22 / R24 的求值域都是「已启用语言」），可以一组一组地写、每写完一组就提交，
仓库始终是绿的。翻成 `true` 那一刻它才进入统计 —— 所以**必须等 22 个存放组都写完再翻**：
R22 是 error，写了 box 却漏掉某一份 `vs`，会让 `content:validate` / `content:build` /
契约测试三处同时红。

> **代价是写的时候机器不检查 `vs` 完整性** —— R22 只在启用后求值。所以写了几组之后，
> 可以临时把 `enabled` 翻成 `true`、跑一次 `content:validate`，记下结果再翻回 `false`。
> 这叫**受控试启**，比等 22 组全写完才发现某一格漏了 `vs.python` 划算得多。
> 要看的就一件事：**error 是否仍为 0**（`vs` 缺一份是 error 级的 R22）。
> 试启时 R20g / R24 会报「还没写的板块」，那是预期的噪声，忽略即可。

> 私有目录约定：以 `_` 开头的语言目录默认不参与构建与校验。
> `_template/` 是供复制的脚手架；CI 的临时语言也用这个前缀，这样即便脚本被中断
> 留下残留，也不会让整个仓库的校验失败。

> 守护：R8（目录 vs 注册表）、R21（box key 必须是池里该存放组的成员）、
> R22（写了的格子必须写全三门 `vs`）。
> **另有三处硬编码要同步**，漏了不会报错、只是静默失守：
> `tests/unit/pool-loader.test.ts` 里「非基准语言没有 baseline、三份 vs 写全」的
> 语言名单与 `metaOnly` 探针，以及 `tests/pipeline/content-contract.test.ts` 的已启用集合断言。

### 5.1 对比列语言的 `vs` 怎么写

1. **三份都写。** `vs.javascript` / `vs.python` / `vs.java` 一份不能少 ——
   视角无法互相推导，「与 Python 相比」总结不出「与 Java 相比」。
2. **每一份的读者是「熟悉那个基准的人」。** 落点写**本语言的行为**，
   不要去复述对方是怎么做的 —— 读者已经会那门语言了。
   在 `vs.python` 里花半段解释 Python 的 `None` 是浪费。
3. **一份 `vs` 里尽量只出现两门语言**（本语言 + 那个基准）—— 但这条**已经不是硬规则**。
   R25（幽灵语言）已随 ADR-72 废除：S12 写速查时发现「目标语言的定义天然依赖第三门」
   是一整类合法内容，同样的道理也适用于对比框（讲 Go 的错误处理时提一句 Rust 的 Result，
   对读者是有信息量的）。**判断标准交回给作者**：提第三门是为了说明差异，还是跑题。
   > 曾经的参照：R25 会把「提到了屏幕外语言」的格子按 (语言, 板块) 汇总成一条 warn，
   > 唯一的豁免是 JavaScript ↔ TypeScript（ADR-71）。这条规则连同它的检测器一起删除了。
4. **术语取该语言的官方叫法**，并在术语表里登记一次、之后全站沿用 ——
   同一门语言在 104 个格子里用同一个词，读者才建立得起映射。
5. **`absent` 与「还没写」是两回事**：本语言真的没有这个概念时写 `absent: true`
   （三槽可以全空，但要有一段说明交代「那你们怎么办」）；只是暂时没想好就留空。
   读者看到留白会理解成「这两门语言在这里没有差异」，而那是另一种意思。
   判不准时留空，别为了填满而标 `absent`。
6. **`equivalence` 按基准给**（缺 key = `identical`）。它的用途是给矩阵着色，
   不是给自己打分，判据落在**机制**上而不是「谁更先进」：
   - `identical`：两边行为相同，几乎没有可说的
   - `analogous`：两边都有这个机制，只是写法或细节不同
   - `divergent`：一边有、另一边没有，或者原理不同（擦除 vs 单态化这类）
   - `absent`：本语言没有这个概念（与 `absent: true` 配套）

   注意同一门语言在不同知识点上的判断是**互相独立**的：
   在「结构化与名义类型」这一格上，Kotlin 对 Java 是 `analogous`（两者都是名义类型），
   而 Go 对 Java 是 `divergent` —— 两者都对，因为比的是**各自与 Java 的关系**，
   不是语言的绝对属性。同一门语言对同一件事的判断不该随批次变化；拿不准时选 `analogous`。

## 6. 加一个「方向」（速查三兄弟）

速查三兄弟（`pitfalls` / `glossary` / `roadmap`）是**唯一保留方向性**的内容 ——
它们的主语是方向，不是语言（「带着 JS 习惯写 Python 会踩的坑」换成「Python 的坑」
就丢掉了最有价值的那半句）。

**方向集合是「3 个基准 × 每一门其他已启用语言」**：截至 S12 是 **33 个**（3 × 11 门），
随启用语言数线性增长（S10 铺 12 个，S12 补齐 7 门新语言后到 33 个）。
非基准语言之间**不生成方向**（没有 `go2rust`）—— 速查讲的是「带着基准的习惯过去」。

### 6.1 目录与文件

```
content/pairs/<基准>2<目标>/
├── meta.yaml        来源与校对留痕（每方向一份）
├── pitfalls.yaml    12 条
├── glossary.yaml    10 条
└── roadmap.yaml     5 个阶段
```

- 目录名必须是**完整的语言 id**（`javascript2python`，不是 `js2python`）——
  归属由目录名反查，不允许别名。
- **三个内容文件的顶层是数组**，`meta.yaml` 是映射。留痕之所以单独放一份，
  是因为数组没有文件级的位置；把顶层改成 `{ review, items }` 会打破这个沿用至今的契约。
- **`meta.yaml` 不接入任何校验规则**（ADR-66）：R3 / R6 / R17 只管 `languages/` 的对比框。
  里面的 `state` 是如实标注，不是发布门槛 —— 但它也不该因此写虚。

### 6.2 三个文件各自的写法

**陷阱（12 条）**

```yaml
- id: pitfall-integer-division          # 文件内唯一
  title: 除号的结果反过来了
  symptom: |                            # 现象：读者会看到什么
    ...
  cause: |                              # 为什么：语言机制上的原因
    ...
  fix: |                                # 怎么改：可执行的动作
    ...
  severity: 3                           # 3 = 静默失败或直接报错；2 = 结果对但有隐患；1 = 一般
  languages: [python, go]               # **恰好本方向两门**（R5，error）
  fromBaseline: true                    # 陷阱是「带着基准习惯」才成立时为 true
  featureId: express/arithmetic         # 软引用，指向 catalog 的全局 id
  tags: [数值, 运算符]
```

**词典（10 条）**

```yaml
- term: 接口
  aliases: [interface, protocol]        # 读者会去搜的词
  perLanguage:
    python: ...                         # **恰好两门 key**（R5，error）
    go: ...
  note: 同名不同义在哪里
```

**路线（5 阶段）**

```yaml
- id: python2go-1-anchor                # 前缀 = 目录名，接序号与短名
  order: 1
  title: 先接受「没有异常、没有类、没有 None」
  durationHint: 2-3 小时
  todo: [...]
  acceptance: [...]                     # 前端可勾选
  resources:                            # 每项 { label, url }，url 必须 https（R7，error）
    - label: Go 官方教程（中文）
      url: https://go.dev/tour/welcome/1
```

### 6.3 三条只有人能守的口径

R5 只管得住 `perLanguage` 的键；`symptom` / `cause` / `fix` / `note` / `todo` / `acceptance`
里的**散文没有任何规则在看**。这三条由 `tests/pipeline/content-contract.test.ts` 的
「速查正文的写作口径」守着：

1. **只讲本方向的两门语言。** 在 `javascript2python` 的词典里提 TypeScript、
   在 `javascript2go` 里提 Java，读者会以为那个方向也会踩到同样的坑 —— 而这条内容根本没在讲那个方向。
   连「三个语言里……」这种不点名的说法也要避免：它同样指向屏幕外。
2. **提到的板块名必须是注册表里真实存在的。** 曾经有一批从 v1 搬过来的路线写着
   「通读本工具**「心智模型」板块**」「按**「基础语法」板块的 8 个章节**逐格对比」——
   这两个板块在 v2 里都不存在，而 `express` 各基准只有 6–7 章，「8」是 v1 的数字。
   **别写死章节数量**，它随基准变。
3. **`featureId` 必须指向 `catalog.json` 的 `featureIndex` 里真实存在的两段全局 id。**
   它是软引用（断了只影响「相关特性」那条链，R5 汇总成一条 warn），
   但悬空会让读者点进 404。

### 6.4 两个 YAML 陷阱（写 pairs 时必踩）

- **`aliases` 里的裸 `null` 会变成空值**：`aliases: [none, null, undefined]` 解析失败
  （`Expected string, received null`）。写 `'null'`。同理 `~`、`yes`、`no`、`on`、`off`。
- **`'` 开头的标量会打开一个引号**：`aliases: [lifetime, 'a]` 报
  「missed comma between flow collection entries」—— 那个 `'a` 是个没闭合的字符串。

> 守护：R5（`perLanguage` / `languages` 只讲本方向两门）、R7（资源 URL 必须 https）、
> `tests/pipeline/content-contract.test.ts` 的「速查正文的写作口径」（提到的板块名必须真实存在）

## 7. 对比框：三个槽位

**一个 feature × 一门语言 = 一个对比框**，三个槽位，全部可空：

| # | 槽位 | 字段 | 说明 |
| --- | --- | --- | --- |
| ① | 代码 | `code`（或 `blocks`） | 这门语言自己的写法，**与读者基准无关** |
| ② | 注释 | 代码内联的 `@note` | 不是独立字段，就在 `code` 里 |
| ③ | 说明 | `baseline` / `vs.<基准 id>` | **唯一按角色变化的槽位** |

第 ③ 槽是本架构的枢纽：

- 这门语言**作基准列**时读 `baseline`（它自己是什么）
- 这门语言**作对比列**时读 `vs.<当前基准 id>`（它和当前基准差在哪）

**视角无法互相推导，所以每门语言要为每个基准各写一份。** 这是本架构的主要成本，
也是它准确的原因。基准语言也有 `vs`：JS 是基准，但读者把基准切到 Python 时，
JS 就成了对比列，用 `vs.python`。

**旧内容里的 `body`（一列一段、不分基准）不能整段搬过来** —— 它必须被**拆成**
`baseline` 与 `vs.<基准>` 两套说法，逐条改写视角。

`code` 与 `blocks` **至多给一个**（都不给也可以，那是 `absent` 或「还没写」）。

> 守护：R16（`code` / `blocks` 至多一个，在 schema 层）

## 8. 代码里怎么标记差异：`@note`

差异说明**写在代码里**，不用行号锚定（行号会随编辑静默漂移）。

```js
const user = { name: "Ada" };
user.name = "Grace";   // @note! 允许：const 冻结的是绑定，不是对象内容
```

```python
count = 0            # @note 赋值即声明，没有 let / const 这类关键字
```

| 写法 | 含义 | 页面上长什么样 |
| --- | --- | --- |
| `@note 说明` | 一般差异 | 说明**留在代码注释里**，贴着那一行读 |
| `@note! 说明` | 高危陷阱 | 同样留在行内，只是说明前多一个 `⚠` |

标记必须出现在**该语言自己的行注释前缀之后**（`meta.comment.line`），位置不限：

```js
let x = 1;        // @note 说明                        ← 标记后就是说明
Boolean([])       // true —— @note! 空数组是真值         ← 注释有正文，标记追加说明
```

抽取时**只剥掉标记本身**，说明文本原样留在行内，**行数绝不能变**。

**什么时候用 `@note!`**：后果是**静默失败**（不报错但结果不对）或**直接报错**的行为差异。
标多了会稀释它的警示价值。它属于 `code` 的一部分，复制代码时会一并带走。

**`@note` 与第 ③ 槽的分工**：贴着某一行的注意事项写 `@note`；一列整体上是什么、
和对面差在哪写 `baseline` / `vs.<基准>`。

> 守护：R4/R9（标记前缀与解析，error）

## 9. `equivalence` 四态（**按基准分**）

```yaml
equivalence:
  javascript: divergent     # 缺 key = identical
  java: analogous
```

| 值 | 含义 | 界面 |
| --- | --- | --- |
| `identical` | 同构，语义与写法几乎可直接迁移 | `=` 绿 |
| `analogous` | 形似，结构相近但有关键差异 | `≈` 琥珀 |
| `divergent` | 语义不同，看起来像但行为不同（陷阱高发） | `≠` 红 |
| `absent` | 该语言没有这个概念 | `∅` 灰 |

**`analogous` 与 `divergent` 的分界**：问「照着基准的写法直接搬过去，会得到正确结果吗」——
会，但有需要知道的差别 → `analogous`；不会（行为变了）→ `divergent`。

**相同处留空**：缺 key 就是 `identical`，不必逐条写出来。

**基准列自己**不渲染徽章（那枚 `=` 是自指、零信息量）—— 双角色取值的唯一落点是
`src/content/boxView.ts`，三处视图都调它，不要在组件里各写一遍。

> 守护：`tests/unit/section-model.test.ts` 钉住「基准列 null 徽章 / `absent` 短路 / 缺 key 才是 identical」三条

## 9.1 `absent` 与「还没写」是两回事

| 写法 | 含义 | 页面 |
| --- | --- | --- |
| **键缺失**（boxes 里没有这个 key） | 还没写 | 更淡的留白 |
| **`absent: true`** | 这门语言**没有这个概念** | 灰格 +「本语言无此概念」+ `∅` 徽章 |

少了这个区分，读者会把「语言之间没有这个差异」误读成「这里内容缺失」。

`absent` **可以**同时给 `code`（表示「没有等价语法，这是惯用替代写法」），
但那时**必须**给一段说明（`baseline` 或任一 `vs`）—— 否则读者只看到一段
不知所谓的代码。三槽全空是合法的，且只有 `absent` 能这样。

> 守护：R26（`absent` + 代码却没有说明）、R24（被引用、缺 key、又没 `absent` → 疑似漏写）

## 9.2 多段代码：`blocks`

需要「会出错的写法 / 正确写法」这类逐段对照时用它，每段必须有 `label`：

```yaml
boxes:
  map-dict:
    blocks:
      - label: 会 panic 的写法
        code: |
          var m map[string]int
          m["a"] = 1
      - label: 正确写法
        code: |
          m := make(map[string]int)
          m["a"] = 1
```

- `label` 必填、非空 —— 它是并排视图里唯一能说明「第 2 段在跟哪一段比」的东西
- 两侧段数一致时**按序号逐段 diff**；段数不同时界面显示「分段结构不同，未做逐行对照」，
  **不会**降级成一份错位的着色
- `@note` 照常可用，注记跟着它所在的那一段

> 守护：R16（`code` / `blocks` 至多一个）、`tests/unit/blocks.test.ts`

## 10. `review` 与 `provenance`

每一格都要有审阅记录。**同一批生成的格子通常共用一份，写到文件级即可**
（某一格要单独标注时，在那一格里再写一个 `review` 覆盖它）：

```yaml
review:                      # 文件级默认
  state: draft
  provenance:
    origin: llm
    model: <模型名>
    promptTemplateId: <模板 id>
    generatedAt: '2026-01-01'
boxes:
  declaration:
    code: |
      ...
```

### 三个状态

| state | 含义 |
| --- | --- |
| `draft` | 未经人工校对（默认）。页面显示「未经人工校对」标记 |
| `reviewed` | 已人工校对 |
| `verified` | 已实跑验证 |

**升级 state 必须同时填 `reviewedBy` 与 `reviewedAt`**（R17）—— 否则那个标记失去可追溯性。

### provenance 的两种写法

```yaml
# 模型产出：**刻意不填 license** —— 模型输出不产生可署名许可，
# 强填 MIT / GFDL 是错误陈述，比留空更危险（ADR-08）
provenance:
  origin: llm
  model: ...
  promptTemplateId: ...
  generatedAt: ...

# 原创：填 license
provenance:
  origin: manual
  license: CC-BY-4.0
```

**校对不是走形式**：首轮校对实测在 7 条 LLM 产出里查出 1 处断言完全写反。
方法是**把每条断言的代码真的跑一遍**，而不是重读一遍。
`origin` 如实标 `llm` —— 校对改的是 `review.state`，不篡改来源。

> 守护：R3（provenance 完整性）、R10（许可台账）、R17

## 11. 一格里的语言提及（R25 已废除）

> **这一节原本讲 R25「幽灵语言」**：`vs.javascript` 是写给以 JS 为基准的读者的，
> 在那里提 Java 就是「幽灵语言」（他这一屏上没有 Java 列）。规则会把它按
> (语言, 板块) 汇总成一条 warn，并在 `registry.yaml` 的 `mentionGroups` 里给
> JavaScript ↔ TypeScript 开了一个同族豁免（ADR-71）。

**R25 已随 ADR-72 废除（S12），`mentionGroups` 与检测器一并删除。** 原因是它撞上了一整类
合法内容：「目标语言的定义天然依赖第三门」—— `python2typescript` 得讲「TS 给 JavaScript
加类型」、`python2arkts` 得讲「ArkTS 是 TypeScript 的受限子集」、`javascript2kotlin`
得讲「Kotlin 跑在 JVM 上与 Java 互操作」。按逐字点名去拦，只能把这些句子逼成含糊的
「另一门静态超集」，而逐个加豁免等于承认规则的主要产出就是豁免。

**留下的判断标准**（交回给作者）：提第三门是为了说明差异，还是跑题。
并排的列去呈现差异永远更清楚；但为了讲清一门语言的机制而引一个参照物，
读者不会因此迷路。**缩写同样算提及**（写「JS」就是提 JavaScript）—— 只是没人再检查了。

**唯一还活着的相关规则是 R5**：`glossary.perLanguage` 的键与 `pitfalls.languages`
的值必须恰是本方向两门（error）—— 那是渲染契约（词典只画两列），不是散文口径。

## 12. 常见错误（会静默失败的那些）

这些都不会让构建失败，但页面会错：

| 症状 | 原因 | 怎么避免 |
| --- | --- | --- |
| **整页空白，还不报错** | 分片路径两侧拼得不一致（构建期 emit ↔ `repository.boxShardPathOf`） | 别手拼；`tests/unit/section-model.test.ts` 钉住了这条 |
| 内容改了但页面没变 | 没重跑 `content:build` | 改完 `content/` 就跑一次 |
| 某一格永远空着 | `boxes` 的 key 拼错（不属于该存放组） | R21 是 error，`content:validate` 会当场拦住 |
| 整章解析失败 | YAML 普通标量以**保留指示符**开头：`` ` `` `{` `@` `%` `&` `*` `!` `\|` `>` `[` `]` `,` | 加引号：`title: "{x} 是什么"`、`summary: '@Test 注解…'` |
| `aliases: [null]` 变成空值 | 写了裸 `null` | 用 `~` 或加引号 |
| 文件解析直接抛错 | 顶层多写了 `section` / `group` / `language`；或 box 里多写了字段 | 三样都由**路径派生**，schema 是 `.strict()` |
| 注记没被抽出来 | 标记没跟在该语言的行注释前缀之后 | 检查 `meta.yaml` 的 `comment.line` |
| 左栏显示裸 key | 板块名写进了 i18n 而不是注册表 | 板块名声明在 `registry.yaml` 的 `sections` 段 |
| 左栏/首页计数虚高、点进去 404 | 章节分类先于内容落库（骨架期） | 判据一律走 `hasChapterContent`；见 `SideNav.vue` / `HomeView.vue` |
| 切了基准，我在的那一章不见了 | 章节分类每个基准各一份，同名不代表同义 | 回落逻辑在 `useBaselineSwitch.ts`，会退到该基准的首个可用章 |

**批量给 YAML 标量加引号的脚本会误伤块标量**（`code: |` 内部是代码原文）。改内容请手改。

## 13. 规则总表

| 规则 | 管什么 | 级别 |
| --- | --- | --- |
| R20a | 章节分组引用的 feature id 必须在池里 | error |
| R20b | 同一板块内 feature id 唯一；每个 feature 都声明了 `group` | error |
| R20c | 文件名 / 目录名与 `section` / `baseline` 字段一致；章内 id 唯一 | error |
| R20d | 语言内容文件的 `group` 不在池里（拼错或孤儿文件） | error |
| R20e | 池里某 feature 不被任何基准的章节分组引用（永不展示） | warn |
| R20f | 池里声明的 group 没有任何启用语言写它 | warn |
| R20g | (语言, 板块)：某些章它一个存放组都没写（整列留白） | warn |
| R20h | 同一 feature 在同一基准下出现在多个章；章内 feature 重复 | warn / error |
| R21 | `boxes` 的 key 必须属于**池中该存放组**的 feature 集合 | error |
| R22 | `vs` 完整性：基准候选写除自己外 2 门、非基准写全 3 门 | **error**（S8 翻级） |
| R23 | 基准候选在**被它引用的** feature 上要有 `baseline` | **error**（S8 翻级） |
| R24 | 被某基准引用、文件缺 key、且未 `absent` → 疑似漏写 | warn（**刻意不翻**） |
| R26 | `absent: true` 且给了 `code` → 必须有说明 | warn |
| R27 | 某章引用了 group G 但该基准缺 G 的内容（基准列空洞） | warn |
| R1 / R3 / R4·R9 / R5 / R6 / R7 / R8 / R10 / R17 | 结构解析 / provenance / `@note` / 引用完整性 / 发布门槛 / https / 注册表自检 / 许可台账 / 校对留痕 | error（R17、R5 的部分为 warn） |

**R5 覆盖速查三兄弟的两处**：`glossary.perLanguage` 的键与 `pitfalls.languages` 的值，
都必须 ⊆「本方向的两门语言」（都是 error）。陷阱的**散文部分** R5 够不到 ——
`symptom` / `cause` / `fix` / `note` / `todo` 里的字没有任何规则在看，
那一层由 §6.3 的常设断言守。

**R24 / R20g / R27 是过渡期规则**（warn）：内容补齐前把构建变红，
会把「还没写完」和「写错了」混成一个信号。它们的求值域是「**该基准真正引用了的知识点**」
—— 被某个基准刻意取舍掉的 feature 不该被要求写 `vs` / `baseline`。
三条都按 `(语言|基准, 板块)` **汇总成一条**输出（逐条会刷屏），逐条待办在
`npm run content:report` 的**逐存放组账本**里。

> **R22 / R23 已在 S8 翻成 error**：它们是硬契约 —— `vs` 缺一份读者永远看不到、
> 基准列空着就是坏页，不存在「合法地留空」。
> **R24 刻意保持 warn**：它判的是「键缺失且没标 `absent`」，而**空框本身合法**，
> 翻成 error 会逼作者在「还没写」与「本来就没有」之间二选一 ——
> 那正是这个字段要区分的两件事。它是一条提醒人确认的规则，不是能自动判定对错的规则。

**两个可执行断言**（不是规则，是脚本）：

- `npm run verify:ext` —— 加语言只加数据；且文案里没有写死语言名（三门基准权重相同）
- `npm run verify:sections` —— 加板块只加数据；且 `sections.gen.ts` 与 `registry.yaml` 同步
