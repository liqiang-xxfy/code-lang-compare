## 第 1 章 · 迁移的形状

为什么不能一步到位、又为什么必须有一个原子时刻：

```
增量期(可构建)  →  原子切换(唯一破坏性时刻)  →  内容爬坡(每批可构建)  →  收尾
```

- 增量期之所以可构建：旧 loader 只扫 `content/topics/` 与 `languages/<id>/snippets/`，
  新增的 `catalog/`、`languages/<id>/<section>/`、`pairs/` 对它**不可见**，旧管线原样跑绿。
- 原子时刻之所以不可拆：`RenderedSnippet` / `RenderedChapter` 的形状变了，而 `repository.ts` 的
  `import.meta.glob` 立即按新形状消费；`analyzeContent()` 又是 validate / build / tests 的共用入口。
  任何一步单独落地，项目既读不了新内容也读不了旧产物。
- **主干策略下的含义**：虽然是分步提交，但「规则 + 构建产物 + 运行时」三步必须落在**同一个提交**里。
  此处会有一段时间构建红，已接受。

**实际执行（三处与原计划的差）**：

1. **`express` 池在 S7.1 被修订了一次**：26 → **27** 个 feature、6 → **7** 个存放组 ——
   把 `strings` 拆成 `strings`（string-literals / string-common-ops）与 `containers`（arrays / maps），
   并新增 `naming-convention`（存放组 `bindings`）。理由是试写正文时发现「字符串」一章
   把数组与映射一起讲，读者对不上号。**这次修订没有动任何内容文件** ——
   正是「池与分组可以自由增删改」（骨架先行的意义）的一次实证。
2. **Java 视角的章节分类改过一次**：原计划的独立 `naming`（命名与可见性）章被撤掉，
   `naming-convention` 并入 `types` 章。触发原因是发现**写错了事实** ——
   草稿称「Java 靠首字母大小写决定可见性」，那是 **Go 的规则**（`Name` 导出 / `name` 包内可见）；
   Java 的命名是纯约定，可见性靠 `public` / `private`。修正落在三处：池的 summary、
   `catalog/express/java.yaml`、`docs/内容书写标准.md` 的示例。
3. **`_template` 从 1 个内容文件变成 4 个**：`express/bindings` + `model/errors` +
   `mechanism/types` + `practice/testing` —— 每个板块一个代表，这样新语言脚手架的
   目录形状与真语言完全同构，不会因为「某个板块还没建」而看起来像缺文件。

**计划外的发现（已修）**：骨架落库**本来会产生一整屏 404 死链**。
有四处列章节的地方只查「有没有章节分组」，没查「有没有内容」：
`SideNav` 的二级项、`HomeView` 的卡片与计数、`siblingsOf` 的上一章 / 下一章、`sectionEntryPath`。
骨架一落地它们就会把 12 份分组里的每一章都列出来 —— 而其中大部分点进去是 404。
处置：把判据收敛成一个函数 `hasChapterContent(lang, baseline, section, chapter)`，
并加 `visibleChaptersOf(baseline, section)` 供「列该基准自己的章」的四处统一调用；
`tests/unit/section-model.test.ts` 新增一条断言守着「章节可见性与路由同源」。
（这条判据后来升格为架构文档 §5.3，并记作 ADR-55。）

## 第 6 章 · 接下来的步骤

### 6.1 S7.5 · rust / go 作为对比列 ✅

**做什么**：给 `rust` 与 `go` 各写 22 个存放组的内容文件，
每格只写 `vs.javascript` / `vs.python` / `vs.java` 三份，**不写 `baseline`**。

**为什么放最后**：两门都不是基准候选（`meta.yaml` 里没有 `baseline: true`），
所以**纯新增、不触发任何回填** —— 任何先做它的顺序都会让「已经写完的三个基准」
看起来像没写完。反过来，先做完三个基准，再补这两门，每一步都是加法。

**为什么值得写**：三个基准候选之间**都是 GC + 动态/半静态语言的组合**，
有些格子天然写不出差异（`mechanism/memory` 的 `ownership-borrow` / `lifetime`
在 JS / Python / Java 下全是 `absent`）。rust 与 go 一进来，
这些格子立刻变成站上信息量最大的地方 ——
Rust 的 `ownership-borrow` 是 `identical`（它就是本体），Go 的是 `absent` 但有一套替代做法。
Java 视角下 `bundler` / `event-loop` / `async-await` / `dynamic-eval` 那几行的四门分布同理。

**工作量**：104 知识点 × 2 门 = **208 格**（每格 3 份 `vs`）。

**实际采用的分批**：**按 (板块, 存放组) 一批、批内两门一起写** —— 共 22 批，
与 S7.1–S7.4 的节奏一致。计划里原本建议「按语言分两批」，
执行时改成按存放组，理由是**对照着写质量更高**：
同一个知识点在 rust 与 go 下的差异往往正好是互补的
（比如「没有继承」这一格，Rust 的答案是 trait、Go 的答案是嵌入），
放在一起写能立刻发现「这一格到底在比什么」。代价是上下文切换多，
但每批只有 2 个文件。

**完成信号**不是「某个板块写完」（这两门没有基准视角），
而是「该语言的 4 个板块的 R24 / R20g 归零」。

**进度**：**22/22 批已完成**，两门各 104/104。

**验收**：

```bash
npm run content:validate     # rust / go 的 16 条 R24+R20g 已全部归零（账只剩 R5 / R6）
npm run content:report       # 这两门的覆盖率从 0/104 涨到 104/104
npm run build && npx vitest run
```

**已发现的四条差异重心**（下一批写 `mechanism` / `practice` 时会反复用到）：

| 重心 | Rust | Go |
| --- | --- | --- |
| 可变性 | `let` 默认不可变，`mut` 是加出来的许可；不可变是**深**的 | 没有「不可改绑的变量」，`const` 是编译期常量 |
| 空值 | 既无 `null` 也无 `undefined`，用 `Option<T>` | 无 `undefined`，用**零值**；`nil` 只对引用类类型有意义 |
| 复用 | 无继承，trait（**显式实现**）+ 组合 | 无继承，嵌入 + 接口（**隐式满足**）—— 但不是子类型关系 |
| 集合语义 | 切片是**借用视图**；`Vec` 不可变时连 `push` 都不行 | 切片**共享底层数组**；结构体是**值类型**（赋值真的复制） |
| 内存 | **无 GC**：所有权 + 借用规则，释放点由编译器插入 | **有 GC**；但值/引用语义的显式选择承担了一部分「想清别名」的职责 |
| 并发 | 数据竞争是**编译错误**（`Mutex<T>` 把数据装在锁里） | goroutine + channel + `select`；锁与数据分离，靠 `-race` 兜底 |
| 异步 | 有 `async`/`await`，但**没有内建事件循环**（要 tokio）；取消 = drop | **没有异步函数这一层**：阻塞即正常，并发靠 `go`；取消靠 `context` |
| 元编程 | 编译期宏（无运行时反射、无 eval） | 有运行时 `reflect`，但只到导出成员；无注解，靠标签 + 代码生成 |

**要注意**：`go` 与 `rust` 目前**已经启用**（`registry.yaml` 里 `enabled: true`），
所以在左栏的对比语言选择条里已经可见 —— 勾上它们会得到整列留白。
这在内容补齐前是可接受的（R20g 就是为这个状态设计的 warn），
但如果要临时藏起来，把那两行改成 `enabled: false` 即可，**不需要改任何代码**。

### 6.2 S7.6 · 速查三兄弟的 `featureId` 重指 ✅

**现状**：`content/pairs/*/pitfalls.yaml` 共 6 个方向、**72 条** `featureId`
仍指向 v1 的旧 id（如 `basics-javascript/truthiness`），按方向汇总成 6 条 R5 warn。

**做什么**：把每条 `featureId` 改指到新架构的全局 id `<板块>/<feature>`
（如 `express/operators` 或 `mechanism/types`）。id 清单见
`content/catalog/<板块>/features.yaml` 与 `build` 产物 `src/generated/catalog.json` 的
`featureIndex`（它是**与基准无关**的 `<板块>/<feature>` 索引，正是为此而生）。

**为什么它现在无害**：`featureId` 只用于「陷阱 → 特性」这一条反查链，
指向不存在的 id 时只是那条链断掉，不影响陷阱本身渲染 —— 所以能一直挂到现在。

**验收**：6 条 R5 warn 归零。

**实际执行**（`warn 7 → 1`）：

- **72 条全部改写**（6 个文件 × 12 条），映射按**每条陷阱的主题**定，不是按旧 id 的字面
  —— 旧 id 属于 v1 的 topic 体系，与新 feature 不是一对一。举几个需要判断的：
  | 陷阱 | 旧 id | 新 id | 为什么 |
  | --- | --- | --- | --- |
  | `__hash__` 契约导致 set 去重失效 | `concepts-python/class-inheritance` | `model/set` | 症状在集合去重，不在继承 |
  | `var` 在循环里泄漏成闭包共享 | `basics-javascript/var-scope` | `express/closures` | 同一条旧 id 的另一半（块作用域）才是 `express/scope` |
  | 遍历时改集合编译不过 | `basics-javascript/array-iterate` | `mechanism/ownership-borrow` | 讲的是借用规则，不是迭代 |
  | `defer` 写在循环里 | `basics-javascript/array-iterate` | `model/finally-cleanup` | 讲的是资源释放时机 |
- **映射脚本先自检**：把 72 个目标 id 逐个拿去 `catalog.json` 的 `featureIndex` 里查，
  有一个不存在就整体不写盘（第一次跑就抓出 `model/objects` —— 那是**存放组**不是 feature，
  改用了 `model/set`）。
- **验证的是真链路**：`dist/compare/javascript/pitfalls/index.html` 里
  「相关特性」链接已全部指向 `/feature/express/arithmetic` 这类**真实存在**的 v2 路由。
- **顺带纠正了一处文档错误**：新架构的反查方向是**陷阱 → 特性**
  （`PitfallCard` 渲染一个「相关特性」链接），**特性页不列陷阱**。
  旧文档里「可从特性页反查」是 v1 的说法，已改掉（架构文档 §4.5 与 §13 Q3）。

**第 3 项 · 校对升级（当前位置，人工活）**

`review.state` 从 `draft` 升到 `reviewed` 并补 `reviewedBy` / `reviewedAt`（R17）。
**当前 520 条全 draft**，是 S8 里唯一一件事只能靠人做的。

方法是**把每条断言的代码真的跑一遍**，不是重读 ——
首轮实测在 7 条 LLM 产出里查出 1 处断言完全写反。

（整组一起升级），个别格子单独标注时在那一格再写一个 `review` 覆盖它。

### 6.4 每批的固定验收动作


## 第 7 章 · 风险与回退

三个代价最大的点，各自给缓解手段：

| 风险 | 缓解 | 实际 |
| --- | --- | --- |
| **catalog 粒度定错**（feature 太粗 → 信息量不足；太细 → 成本爆炸） | 每开一个新板块先只写**池**（纯设计、不写正文），池一列出来工作量就可见了；粒度可在铺开前免费调 | ✅ 生效：`express` 池在 S7.1 从容地改过一次（26→27、6→7 组），未动任何内容文件 |
| **双角色契约设计错**（`baselineHtml` / `vsHtml` 形状没定死） | S1 就把形状写进契约；S5 若再改，repository / 视图 / `finalize-dist` 会一起返工 | ✅ 未触发 |
| **R22 / R23 分级未定就开写** | 迁移期一律 warn，内容稳定后按板块收紧成 error | ✅ 三个基准的聚合行已归零，翻转留 S8 |
| **S6.5c 里「章 → group → 分片键」在四处各拼一遍** | 收敛成单一函数 `groupsOfChapter(基准, 板块, 章节)`；加构建测试断言「每个 emit 出的分片路径 ↔ `boxShardPathOf` 的键逐字相等」 | ✅ 已由 `tests/unit/section-model.test.ts` 守着 |
| **`featureIndex` 的来源只翻一半** | 契约测试断言「`featureIndex` 大小 == 池的 feature 数」+「每个 catalog 引用都能在池里解析」 | ✅ |
| **`finalize-dist` 探针静默失效** | 把 `probeTextFor` 改成「凡是识别出的路由，探针必须返回非 null，否则计失败」，并打印实际检查条数 | ✅ |
| **章节可见性判据漏改一处** | 收敛成 `hasChapterContent` + `visibleChaptersOf`，并由测试断言「与路由同源」 | ✅ **S7.0 实测四处全中**（`SideNav` / `HomeView` / `siblingsOf` / `sectionEntryPath`），已修 |

**回退策略**：归档不删 → `git revert` 可整体退回；`src/generated/` 全部可再生。

## 第 8 章 · 执行前必须拍板的清单

- **R22（`vs` 完整性）/ R23（基准列非空）在迁移期的级别** ——
  沿用旧 R18/R19 的过渡期策略：**warn，内容稳定后按板块收紧成 error**。（已定：warn）
- **新模型下搜索分片的键** —— 已定：**按语言分片**（`search-index/<语言>.json`），
  pair 文档归入**目标语言**分片。章节按基准分组不影响它 —— 索引收入的是注记与说明文本，
  不含章节标题。
- **初始启用集合与爬坡阶梯** —— 已定：初始只启用 JS/Python/Java/rust/go 五门。
- **`_template` 脚手架在新目录结构下的形态** —— 已定：`languages/_template/<板块>/<group>.yaml`，
  与真语言同构（脚手架不参与构建，因此不会因为板块还没建而报缺）。
  **实际落成了 4 个文件**（每板块一个代表）。
- **`absent` / 三槽全空在矩阵里的渲染形态** —— 已定（S6）：`absent` 渲染灰格 +
  「本语言无此概念」+ ∅ 徽章；键缺失渲染更淡的留白。两者刻意分开。
- **章节 id 是否要在基准间保持可读的对应关系**。← **未决**：同名章节不代表同义，
  但完全不对应会让「切基准后我在哪一章」这件事失去连续性（`useBaselineSwitch` 的回落逻辑因此变复杂）。
  倾向：**尽量复用 id 表达相近的意思，但不强制**。（已同步到架构文档 §13 Q4。）
