> 这份文档服务于 **S11**（新增 7 门对比列语言，见[台账](项目步骤规划与进度台账.md) §6.7）。

> ① 这门语言管这个东西叫什么？② 这个知识点在这门语言里到底有没有？③ 样张暴露了哪些结构问题？

## 1. 术语表

每门语言用它自己官方文档里的叫法，全站统一。**写作时先查这里，不要临时换词** ——

**几处值得先记下来的**：

- **`generics` 对 PHP 是 `∅`** —— PHP 没有泛型，只有文档注解（`@template`）。这一格会是纯粹的 `absent` + 「那你们怎么办」的说明。
- **`memory` 对 TS / ArkTS 是 `∅`** —— 有 GC 但语言层不暴露，写不出与基准的实质差异。而 C++ 与 Swift 在这一组是 ●（手动管理 / ARC），是它们最有价值的格子。
- **`concurrency` 对 PHP 是 `∅`** —— 共享无状态的请求模型，一次请求一个进程，没有语言级并发原语。
- **`meta` 对 ArkTS 可能是 ●** —— 装饰器（`@State` / `@Prop` / `@Link`）是它写 UI 的核心手段，比在 TypeScript 里更中心。
- **C++ 的 ● 密度最高**，且集中在 `model` 与 `mechanism` 两组 —— 它离三个基准都远，可写的东西最多，也最贵。

## 3. 样张暴露的问题

### 3.1 `equivalence` 的口径必须成文（已在 §5.1 补）

写样张时，同一个知识点在不同语言下出现了分歧判断：**`structural-nominal` 这一格，
Kotlin 对 Java 记 `analogous`（两者都是名义类型），而 Go 对 Java 记 `divergent`**。
两者都对 —— 判的是「各自与 Java 的关系」，不是语言的绝对属性。
但边界不写清楚，跨批次就会出现同一格判断不一致。判据已补进 §5.1 第 6 条。

### 3.2 ArkTS 与 TypeScript 的同质化（陪跑样张的结论）

`express/bindings` 陪跑样张的结果：**6 格里有 5 格对 TypeScript 侧的判断是
`identical` 或 `analogous`，真正有差异的是 `hoisting`**（ArkTS 的静态检查直接
否掉了依赖提升的写法）。其余几格的 `vs` 只能落在「ArkTS 的检查更严」这一句上。

这印证了按对比轴配对（轮 ① 把 TS 与 ArkTS 放一起）而非按谱系分的判断：
ArkTS 的价值集中在少数几组（`practice/*`、`mechanism/concurrency`、
`mechanism/meta`、`model/modules`），**其余组应当如实标 `identical` + 一句短说明，
不要为了填满而灌水**。矩阵里 ArkTS 的 △ 就是这些格子。

### 3.3 知识点切分：`types` 组目前不必动

主样张 `mechanism/types` 的 6 格在 7 门语言里都成立，没有出现
「两格在每门语言里说的都是同一句话」的过切分信号。
`static-vs-dynamic` 与 `type-annotation` 相邻但不重复（前者问「什么时候查」，
后者问「怎么写」），`type-narrowing` 与 `type-assertion` 也分得开。
**结论：池不动。**

### 3.4 一处写作纪律（已补进 §5.1 第 3 条）

样张写作中真的踩到了 R25：在 `vs.python` / `vs.java` 里为了做三方对比
把 JavaScript 拉了进来。**一份 `vs` 只许出现两门语言**，这一条在写「A 与 B 差在哪」
时特别容易破 —— 因为解释差异时天然想引第三个参照物。

## 4. 工时账

样张实测（可作为全量的换算基准）：

| 项 | 量 |
| --- | --- |
| 单格 YAML 平均行数 | 约 35–40 行（`code` 8–15 行 + 三份 `vs` 各 4–6 行 + `equivalence`） |
| 样张总量 | 12 格 × 7 门 = 84 格，约 2200 行 |
| 全量换算 | 728 格 ≈ **2.6–2.9 万行 YAML**，是样张的 13.5 倍 |

按每轮 44 个文件（2 门 × 22 组）计，**轮 ① 的粗略体量与现存 5 门语言之一相当**。
真正决定节奏的是 `●` 密度：C++（轮 ③）与 PHP（轮 ④）的格子写法最重，
但 PHP 有大量 `∅`（`generics` / `concurrency` / 部分 `memory`），实际不一定更慢。

### 5.1 ArkTS：八条会成为高频判据的事实

| 事实 | 出处 |
| --- | --- |
| `as` **不做**运行时检查、不转换值；断言错了**静默不生效**（不抛异常） | 官方 FAQ |
| 但**编译期管得死**：毫无继承关系的类型之间不许断言；且禁 `any`/`unknown`，`x as unknown as T` **写不出来** | `arkts-no-any-unknown` + 迁移指南 ArkTS 侧示例 |
| **默认严格空安全**，`?.` / `??` 可用 | 语言导览 |
| `let x;`（无初值也无标注）是**编译错误** | 语言导览 |
| **构造函数支持重载签名**（多个签名头 + 一个实现体） | 语言导览「Constructor overload signature」 |
| `Record<K,V>` 是官方给的动态键形态，索引读出的类型**含 `undefined`**；`Object.fromEntries` 反而被禁 | `arkts-no-utility-types` / `arkts-limited-stdlib` |
| 函数**参数**类型必须有；**返回类型可推断但受限**；**回调参数类型由上下文推断、可以省** | `arkts-no-implicit-return-types` + official more-cases 示例 |
| 只能抛 `Error` 及其子类 —— 是**硬性编译规则**不是惯例 | `arkts-limited-throw` |

另外这批内容用到的禁用项（都已核到规则名）：函数表达式、生成器、解构（声明/赋值/参数
三条）、`for...in`、`var`、`Symbol`（仅 `Symbol.iterator` 可用）、展开（只许传给剩余参数
与复制数组）、`Object.fromEntries` / `Object.assign` / 原型改写、`as const`、
`let v!: T`（这条是 **warning** 级，不是 error）。

### 5.2 写反过的（同类错误最值得警惕）

- **ArkTS 的 `as`**：一度写成「会做运行时检查」，与事实正相反（见 5.1 第一条）。
- **`slice` 的负下标**：写成「`slice` 不支持、只有 `at()` 认」—— 实际 `slice` 与 `at` 都认，
  不认的是 `substring`。
- **函数表达式**：当作 ArkTS 的合法写法列进「三种写法」，实际 `function (x) {}` 是编译错误。
- **构造函数**：写成「没有重载」，实际有重载签名。
- **动态键**：写「只能改用 `Map`，中间那条路被堵死」，漏了 `Record`。
- **`throw`**：写成「抛 `Error` 是惯例」，实际是编译期硬规则。
- **迭代协议**：把「解构、展开都认 `Symbol.iterator`」一并写了，实际两者在 ArkTS 都不支持。
- **`let z;`**（TS 侧）：写成「检查从这里断掉」，实际是 evolving any —— 赋值前访问会被拦下，
  赋值后按所赋的类型检查。
- **`??`** 的编译检查（TS 侧）：写成「左边类型不含 null 就提醒」，实际**只看语法**。
- **未处理的 promise 拒绝**（TS 侧）：写成「只是警告，程序不会停」——
  **Node 自 v15 起默认终止进程**，而 TS 的主力服务端运行时正是 Node。

### 5.3 证据不足、已删掉的断言

凡是官方文档里找不到依据的，一律删掉而不是留着 —— 这一批删了五处：
ArkTS 的**穷尽性检查**（`never` / `assertNever` 那套）、`catch { }` **省略绑定**、
`import './polyfill'` **纯副作用导入**、**函数声明提升**的具体行为、
以及「老项目里 `?.` 更多」这类**风格年龄相关性**判断。

### 5.4 轮 ① 第 3 批（`mechanism`）的调研结论

**最重要的发现：ArkTS 有两份互相矛盾的文档，只许引用其中一份。**

| 文档 | 描述的语言 | 与仓库的关系 |
| --- | --- | --- |
| **app 开发文档**（`quick-start/`、`arkts-utils/`） | API 12 / HarmonyOS NEXT 的 `.ets`：**actor 模型、内存隔离** | ✅ **仓库的目标版本，只引它** |
| **ArkTS 静态语言规范 1.2**（`arkcompiler_runtime_core/…/ets/doc/`） | 技术预览：有 `int` / `tuple` / **共享内存** / 声明处型变 `in`·`out` | ❌ 与上一行**直接冲突** |

冲突实例：app 文档说运行时是「actor model with memory isolation」，静态规范说
「program memory is shared between all C_JOBS」。按后者写，写出来的东西**不属于目标版本**。

| 主题 | 只引 app 文档时能写的事实 | **无官方依据 → 不写** |
| --- | --- | --- |
| `concurrency` | actor 模型 + 内存隔离；TaskPool / Worker 两套；跨线程三条路（Structured Clone 深拷贝 / ArrayBuffer·Transferable / **`@Sendable` 在共享堆按引用传递**）；**只有异步锁** `AsyncLock`（非阻塞，必须 `await`），另有 `ConditionVariable`；`SharedArrayBuffer` + `Atomics`；数据竞争是**开发者责任**，编译器不管 | 内存序（memory order）；「编译器会检测数据竞争」 |
| `async` | Promise / async-await；microtask 事件循环；未处理拒绝有 `globalUnhandledRejectionDetected` 全局事件；**TaskPool 的任务可取消，Worker 不可**（只能销毁线程） | **`AbortController` / `AbortSignal`**（DOM 式）；`setTimeout` 与 Web 的语义一致性 |
| `generics` | `extends` 约束、默认类型实参；禁条件类型（含 `infer`）/映射类型/交叉类型/索引访问/索引签名/类型查询/`this` 类型；工具类型只留 `Partial`·`Required`·`Readonly`·`Record`；**推断受限**（不能只靠返回类型推断出 `T`） | **型变**、**类型擦除** —— app 文档零覆盖 |
| `memory` | number / string 是基本类型（值语义），object / array / function 是引用类型；**没有用户自定义 struct**（`struct` 是 ArkUI 组件语法）；**tracing GC，明确不用引用计数**（理由是会漏循环引用），分代 young/old、有阈值与堆上限 | **`WeakRef` / `WeakMap` / `WeakSet` / `FinalizationRegistry`** —— 既不在禁用名单里，也没有文档保证可用 |
| `meta` | **反射基本被禁**：`eval`、`Object.getPrototypeOf`、`Proxy` 的 **13 个 trap 全禁**、`Symbol`、`globalThis`、`delete`、`in`；官方承认的替代是 **dynamic import**（原话是「达到类似 `Class.forName()` 的效果」）；ArkUI 的 `@State` / `@Prop` / `@Link` 等属 **ArkUI 框架**，语言层只有 `@Sendable` / `@Concurrent` | 运行时拿类型信息；自定义装饰器的运行时元数据；`Proxy` 的官方替代品 |

> **两格要特别处理**：`variance` 与 `type-erasure` 在 ArkTS 侧**没有官方依据**。
> 它们**不标 `absent`**（ArkTS 有泛型，不是「本语言没这个概念」），而是如实写明
> 「官方文档没有定义这件事」—— 对读者来说，「这门语言不提供这个工具」本身就是有用的事实。

### 5.5 一条流程纪律

核实里有一半以上的错误属于**「想当然」**：把 TypeScript 的行为套到 ArkTS 上、
把 JavaScript 的细节记混（`slice` 负下标）、把「惯例」当「规则」。
**写「另一门语言怎么做」时，落笔前先查官方文档** —— 这类断言错得越自然，
读者越不会怀疑。TS 侧的 `code` 块尤其要**真的编译一遍**：
被标成正面示例的行如果根本编译不过，比写错一句话更伤读者。
