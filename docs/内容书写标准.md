## 0. 三条命令

```bash
npm run dev              # 内容编译 + 开发服务器（改了 content/ 必须重跑，否则页面还是旧内容）
npm run content:validate # 只跑校验。这是 CI 的阻断闸门，error 级问题非零退出
npm run content:report   # 覆盖率 / 审阅状态 / 待校对清单
```

改完内容至少跑一次 `content:validate`。`npm run content:build` 会自动先校验。

**提交前请跑完整链**：

```bash
npm run content:validate && npm run typecheck && npm test && npm run verify:ext && npm run verify:sections
```

## 1. 目录地图

```
content/
├── registry.yaml                          ← 全局开关：板块注册表、语言启用、topics 三轴声明
├── topics/<topicId>/                      ← 章节型内容
│   ├── 01-variables.yaml                  ←   一个文件 = 一章（顶层是**对象**）
│   └── pitfalls.yaml / glossary.yaml / roadmap.yaml   ← 列表型资源（顶层是**数组**）
├── languages/<id>/
│   ├── meta.yaml                          ← 语言元信息（注释符、高亮语言、基准候选资格）
│   └── snippets/<topicId>/<NN>-<chapter>.yaml   ← 该语言对某个 topic 的实现
└── i18n/zh-CN.yaml                        ← 界面文案（**不是内容**）
```

> 心智模型曾经是 `content/concepts/concepts.yaml` 这样一份与基准无关的全局文件。
> 自 ADR-31 起它就是一个普通板块：内容在 `content/topics/concepts-<基准>/`，
> 实现照常写在 `content/languages/<语言>/snippets/concepts-<基准>/`。
> 那个旧文件已无人读取，保留在仓库里只是历史痕迹，不要往里加东西。

**章节与列表怎么区分**：看 YAML 顶层是对象还是数组。对象 = 章节，数组 = 列表资源。
（这条约定由 loader 执行，写反了会被 R1 拦住。）

**`src/generated/` 是构建产物，永远不要手改。** 跨过分界线只能由 `npm run content:build` 单向完成。

> 守护：R1（结构）、R15（覆盖层归属）

## 2. 加一个 feature（最高频）

一个 feature = 「一个语言特性」或「一个迁移要点」。它由**一处骨架 + 每门语言一份实现**组成。

**说明写在哪一层，取决于板块的 `columns`：**

| 板块 | 说明写在哪 | 渲染位置 |
| --- | --- | --- |
| `columns: multi`（基础语法 / 心智模型） | **每门语言各写各的** → `snippet.body` | 本列代码**下方** |
| `columns: single`（迁移教程） | 一份共享说明 → `feature.body` | 所有列**上方** |

多列板块曾经也有那份共享说明，2026-10 取消了。那里的列是用户勾选的 1~5 门语言，
一份写在基准视角下的说明既盖不住各语言自己的事实，也放不下各自的差异，
而且在矩阵视图里**根本没有渲染点**。R19 会拦住它。

### 第一步：在章节里加一条 feature

`content/topics/<topicId>/<NN>-<chapter>.yaml`：

```yaml
features:
  - id: basics-javascript/var-hoisting        # 前缀必须等于 topicId（R13）
    title: 变量提升
    kind: behavior                             # syntax | concept | behavior | mapping | exercise
    summary: 一句话说明（用于列表与 SEO description）
    # columns: multi 的板块到此为止 —— 说明写在每门语言的覆盖层里，不要在这里写 body
    body: |
      ← 只有 columns: single（迁移教程）才写这里：全板块共享的权威说明。
        受限 Markdown（**禁裸 HTML**）。
```

### 第二步：给覆盖范围内的**每门语言**各加一条实现

`content/languages/<lang>/snippets/<topicId>/<NN>-<chapter>.yaml`：

```yaml
topic: basics-javascript                       # 必须与目录名、与每条 featureId 前缀一致（R15）
snippets:
  - featureId: basics-javascript/var-hoisting
    equivalence: divergent                     # 见 §8
    code: |
      console.log(x);   // @note! 输出 undefined 而不是报错
      var x = 1;
    body: |
      ← columns: multi 的板块在这里写**这一列**的说明（受限 Markdown），
        渲染在本列代码下方。
```

**`body` 是一个字段、两种角色**，由「这一列是不是基准列」决定：

| 列 | 写什么 |
| --- | --- |
| 基准列（`lang === topic.baseline`） | **本语言的客观事实** |
| 对比列 | **与基准语言的差别对比** |

两条写法上的分寸：

- **`body` 讲整体** —— 这一列整体上是什么、和对面差在哪。
- **贴着某一行的注意事项走代码里的 `@note`**，不要重复写进 `body`。
  两者的内容常常重合，重合时以 `@note` 为准：它贴着那一行，读者不用来回跳。
- `body` 是可选的。基准列没有「与自己的差别」这回事，对比列若确实没有差别也可以空着。
  但它不是可以偷懒的地方 —— 一列说明缺席时，读者看到的就是一段没有解释的代码。

> `code` 与 `blocks` **必须恰好给一个**（R16），这条没有例外 —— 概念类条目也一样。
> 别指望用 `body` 顶替代码：「每格都有实现」是这个站的核心承诺，
> 而且少了代码就同时丢掉高亮、复制与行级 diff。

### 第三步：看缺口

```bash
npm run content:report      # 覆盖率
npm run content:validate    # 缺哪一门会明确列出来
```

> **覆盖范围**由 `registry.yaml` 里该 topic 的 `languages` 决定；缺省 = 全部已启用语言。
> 缺一格就是 error 级阻断 —— 「还没写」和「这门语言没有这个概念」必须区分开：
> 后者要显式写 `equivalence: absent` + `body` 说明替代做法。
>
> ⚠️ **`languages: []` 不是「暂不要求覆盖」** —— 空数组走的是同一条缺省分支，
> 等价于「全部已启用语言」。想先窄后宽，就明确写出要覆盖的那几门（如 `[javascript, python]`），
> 并在同一批里把这几门的实现补齐：**加一门语言与补它的全部格子必须同批完成**，
> 否则 R2 立刻变红。

> 守护：R2（覆盖率）、R13（featureId 前缀）、R15（覆盖层归属）、
> R18（多列板块每格应有 body）、R19（多列板块不得有 feature.body）

## 4. 加一个 (基准, 目标) 方向

三件事：建目录、登记、写内容。

**① 建目录** `content/topics/<baseline>2<target>/`，写迁移教程章节 + 三份列表资源：

```
js2go/
├── 01-functions.yaml    迁移教程（章节，顶层对象）
├── pitfalls.yaml        迁移陷阱（顶层数组）
├── glossary.yaml        速语词典（顶层数组）
└── roadmap.yaml         迁移学习路线（顶层数组）
```

**② 在 `registry.yaml` 的 `topics` 段登记**：

```yaml
js2go:
  enabled: true
  title: JavaScript → Go
  kind: migration
  section: migration          # 必须是 sections 段里已注册的板块（R14）
  baseline: javascript
  target: go
  languages: [javascript, go] # R2 的覆盖率范围，通常就是这两门
```

**③ 构建**：`npm run content:build` —— 左栏、路由、sitemap 全部自动跟上。

> **列表资源的 pair 归属由目录名反查 registry 得到，不写进每条 YAML。**
> 同一条陷阱可能在多个方向成立，逐条写 pair 字段会产生会各自漂移的副本。

### 陷阱 / 词典 / 路线，谁负责讲什么

三份列表资源与「心智模型」板块有天然重叠，分工必须写死，否则同一批事实会被抄进
五个方向的词典里、各自漂移：

| 内容 | 写在哪 | 判据 |
| --- | --- | --- |
| **语言属性的全貌**（「接口在各语言里分别是什么」） | 「心智模型」板块 | 它讲的是**语言**，与方向无关 —— 一套内容服务所有方向 |
| **该方向下的同名异义**（「这个词在这个方向为什么会骗到你」） | 方向词典的 `note` | 换一个方向就不成立 |
| 方向词典的 `perLanguage` | 只写**叫法 + 最短的必要事实** | 完整说明归心智模型板块；这里写长了就是第二份会漂移的副本 |

同理，**路线里不要复述板块内容**，直接写「答案在「心智模型」板块里」并给出问题清单。
判定方法很简单：**把这句话换到另一个方向上还成立吗？** 成立 → 它属于板块级内容，
不属于这个方向。

> 实测（2026-10）：四条「接口」词典条目的 `note` 各自是方向特有的（JS↔Java 讲
> `implements`、JS↔Go 讲隐式满足的同构性），**不是副本**；真正重复的是每条里
> 描述**基准侧**的那半句 —— 它在每个含该词的词典里各写了一遍。
>
> **对级板块的陷阱/词典/路线只能讲本方向的两门语言**（R5）——
> 多写一门第三语言，读者会以为带着当前基准的习惯在那个方向也会踩到同样的坑。

> 守护：R5（引用完整性）、R8、R14

## 5. 加一个板块

**这是本项目「加 X 只加数据」承诺里最新的一条。** 完整步骤只有两步。

**① 在 `registry.yaml` 的 `sections` 段声明**：

```yaml
sections:
  advanced:
    order: 7
    label: 高级语法            # 左栏短名
    title: 高级语法对比        # 页面标题
    shape: chapter            # chapter（有章节）| list（一页列表资源）
    scope: baseline           # baseline（以基准为参照、可多门并列）| pair（锁定「基准→目标」两门）
    columns: multi            # multi（多选并排）| single（单选，一篇文章）
    seo:
      # 占位符：{baseline} {target} {direction} {chapterTitle} {compared} {count} {sample}
      # scope: baseline 时没有 target，{direction} 会退化成只有基准名 —— 用 {baseline} / {compared}
      title: "以 {baseline} 为基准 · {chapterTitle}"
      description: "{chapterTitle}：{sample} —— 以 {baseline} 为参照系。"
```

**`order` 决定左栏顺序，也决定 `/compare/<基准>` 落到哪**（见下面的 `landing`）。
`order` 是策展决策，与文件里的书写顺序无关 —— 但注册表里仍然按 order 书写，便于阅读。

**落点板块**：想让某个板块成为 `/compare/<基准>` 与顶栏「多语言对比」的落点，
在它上面加 `landing: true`：

```yaml
  roadmap:
    order: 1
    landing: true            # 至多一个板块声明它；一个都没有时回落到「第一个章节型板块的首章」
```

写成数据而不是在路由里点名板块，是为了**换一个只改一行**，也不必给
`verify:sections` 的白名单加一条「这里为什么可以出现板块名」的注解。

**② 建内容目录**并在 `topics` 段登记一个属于它的 topic：

```yaml
advanced-javascript:
  enabled: true
  title: 高级语法
  kind: concept
  section: advanced
  baseline: javascript
  languages: [javascript]
```

**③ 构建**：`npm run content:build`。左栏、路由、SEO、搜索索引全部自动生成。

### 什么时候需要写代码

| 新板块的形态 | 需要做什么 |
| --- | --- |
| `shape: chapter`（章节型） | **零代码** —— 自动复用 `ChapterCompareView` |
| `shape: list` + 交互可复用现有渲染器 | 零代码 —— 注册表里 `renderer` 写已有的名字（`pitfalls` / `glossary` / `roadmap`） |
| `shape: list` + 全新交互 | 新增一个渲染器组件，并在 `SectionDispatchView.vue` 的 `RENDERERS` 里注册一行 |

**全项目通用的纪律**：`src/` 里**不得出现任何板块 id 字面量**（旧地址 shim 等在白名单里，每条都写了理由）。
板块属性一律从 `src/content/repository.ts` 读：

```ts
sectionDefOf(section)      // 完整定义
sectionIsChapter(section)  // 有没有章节
sectionIsMulti(section)    // 控件是否多选
sectionUsesTarget(section) // 有没有「方向」概念
orderedSections()          // 全部板块，按 order
```

> 守护：R14（板块成员资格）、`npm run verify:sections`

## 6. 加一门语言

```bash
cp -r content/languages/_template content/languages/<新语言 id>
```

**① 填 `meta.yaml`**（`id` 必须等于目录名）：

```yaml
id: ruby
name: Ruby
shortName: Rb
aliases: [rb, ruby3]
fileExtension: .rb
comment:
  line: '#'                  # 驱动 @note 标记解析，必须准确
shikiLang: ruby              # Shiki 的高亮语言标识
typing: dynamic
memoryModel: gc
baseline: false              # 是否可当基准候选
```

**② 在 `registry.yaml` 的 `languages` 段登记** `enabled: true`。

**③ 写实现**：`content/languages/<id>/snippets/<topicId>/<NN>-<chapter>.yaml`。

**④ 验证**：

```bash
npm run content:build && npm run verify:ext
```

`verify:ext` 会造一门临时语言，断言 `src/`（不含 `generated/`）里没有任何代码提到它 ——
这就是「加语言只加数据」这句承诺的可执行证明。它同时扫描 `src/` 里写死的语言 id，
以及**面向用户的文案**（i18n 的值、`.vue` 的 `<template>`）里写死的语言**显示名** ——
后者是 2026-10-02 补的：`PitfallCard` 的徽章曾硬编码「JS 开发者必踩」，
于是 Java / Python 基准的页面上也在讲 JS。文案里的语言名一律用 `{baseline}` 之类的占位符。

> 若这门语言要当基准：在 `meta.yaml` 标 `baseline: true`，补一套 `content/topics/basics-<id>/`。
>
> **以 `_` 开头的语言目录是私有目录**，默认不参与构建与校验（脚手架模板、CI 临时语言）。
> 新增真语言不要用下划线前缀。

> 守护：R8、`npm run verify:ext`

## 7. 代码里怎么标记差异：`@note`

差异说明**写在代码里**，不用行号锚定（行号会随编辑静默漂移）。

```js
const user = { name: "Ada" };
user.name = "Grace";   // @note! 允许：const 冻结的是绑定，不是对象内容
```

```python
count = 0            # @note 赋值即声明，没有 let / const 这类关键字
MAX_RETRY = 3        # @note! 全大写只是约定，解释器不会阻止你重新赋值
```

| 写法 | 含义 | 页面上长什么样 |
| --- | --- | --- |
| `@note 说明` | 一般差异 | 说明**留在代码注释里**，贴着那一行读 |
| `@note! 说明` | 高危陷阱 | 同样留在行内，只是说明前多一个 `⚠` |

**两种语气都只在行内出现一次** —— 高危项不再被单独抽到代码块下方，读者不必在代码和说明栏
之间来回跳。抽取时只剥掉 `@note` / `@note!` 标记本身，说明文本原样保留。

标记必须出现在该语言自己的行注释前缀之后（`meta.comment.line`），位置不限：

```js
let x = 1;        // @note 说明                        ← 标记后就是说明
Boolean([]);      // true —— @note! 空数组是真值         ← 注释有正文，标记追加说明
```

上面两行渲染到页面上分别是：

```js
let x = 1;        // 说明
Boolean([]);      // true —— ⚠ 空数组是真值
```

**什么时候用 `@note!`**：后果是**静默失败**（不报错但结果不对）或**直接报错**的行为差异。
两者都不满足的用普通 `@note`。`⚠` 不加色、也不改注释正文，全靠它在满屏注释里被扫到 ——
标多了会稀释它的警示价值。它属于 `code` 的一部分，**复制代码时会一并带走**。

**基准列不要点名屏幕外的语言**（R12）。基础语法是多选列，勾 Java+Go+Rust 时讲 Python 就是幽灵语言。
要横向对照，写成「本语言自己的行为」，让对比由并排的列去呈现。
**这条同时管列下方的 `body`**，不只是 `@note` —— 说明下沉到每列之后，正文成了差异说明的
主要载体，只查注记会让整段正文溜过去。

**`@note` 与 `body` 的分工**：贴着某一行的注意事项写 `@note`，一列整体上是什么、
和对面差在哪写 `body`。两者重合时以 `@note` 为准。

> 守护：R4/R9（标记前缀与解析）、R11（差异要有说明）、R12（基准列不点名，含 body）、R17（校对记录）

## 8. `equivalence` 四态怎么选

`equivalence` 是「**与本 topic 的基准**是否不同」的唯一判据，不提供相似度百分比
（跨语言 diff 恒在低区间，是伪精度）。

| 值 | 含义 | 界面 |
| --- | --- | --- |
| `identical` | 同构，语义与写法几乎可直接迁移 | `=` 绿 |
| `analogous` | 形似，结构相近但有关键差异 | `≈` 琥珀 |
| `divergent` | 语义不同，看起来像但行为不同（陷阱高发） | `≠` 红 |
| `absent` | 该语言没有这个概念 | `∅` 灰 |

**`analogous` 与 `divergent` 的分界**：问「照着基准的写法直接搬过去，会得到正确结果吗」——
会，但有需要知道的差别 → `analogous`；不会（行为变了）→ `divergent`。

`absent` **可以**给代码，表示「没有等价语法，这是惯用替代写法」，但**必须**用 `body` 说明。

**基准列自己的 `equivalence` 恒为 `identical`** —— 它就是参照系（有测试钉住）。
页面上不渲染这枚徽章：自指、零信息量。

> 守护：R2（absent 需 body）、R11

## 9. 多段代码：`blocks`

一个特性需要「一段或多段对照写法」（如「错误写法 / 正确写法」）时用它。

**单段**继续写 `code`（渲染路径与加 `blocks` 之前完全一致）：

```yaml
  - featureId: js2go/nil-map
    equivalence: divergent
    code: |
      ...
```

**多段**写 `blocks`，每段必须有 `label`：

```yaml
  - featureId: js2go/nil-map
    equivalence: divergent
    blocks:
      - label: 会 panic 的写法
        code: |
          var m map[string]int
          m["a"] = 1
      - label: 正确写法
        code: |
          m := make(map[string]int)
          m["a"] = 1
```

**规则**

- `code` 与 `blocks` **恰好给一个**，不能并存也不能都没有（R16）
- 每段的 `label` 必填、非空 —— 它是并排视图里唯一能说明「第 2 段在跟哪一段比」的东西
- 两侧段数一致时**按序号逐段 diff**；段数不同时界面显示「分段结构不同，未做逐行对照」，
  **不会**降级成一份错位的着色
- `@note` 标记照常可用，注记跟着它所在的那一段

> 守护：R16

## 10. `review` 与 `provenance`

每条实现都要有审阅记录。**同一文件里同批生成的条目通常共用一份，写到文件级即可**：

```yaml
topic: basics-javascript
review:                      # 文件级默认，条目可用自己的 review 覆盖
  state: draft
  provenance:
    origin: llm
    model: claude-code-agent
    promptTemplateId: m1-snippet-v1
    generatedAt: '2026-10-01'
snippets:
  - featureId: basics-javascript/var-declaration
    equivalence: divergent
    code: |
      ...
```

### 三个状态

| state | 含义 |
| --- | --- |
| `draft` | 未经人工校对（默认）。页面显示「未经人工校对」标记 |
| `reviewed` | 已人工校对 |
| `verified` | 已实跑验证 |

**升级 state 必须同时填 `reviewedBy` 与 `reviewedAt`**（R17）—— 否则那个标记失去可追溯性。

### provenance 的两种写法

```yaml
# 模型产出：**刻意不填 license** —— 模型输出不产生可署名许可，
# 强填 MIT / GFDL 是错误陈述，比留空更危险（ADR-08）
provenance:
  origin: llm
  model: ...
  promptTemplateId: ...
  generatedAt: ...

# 原创：填 license
provenance:
  origin: manual
  license: CC-BY-4.0
```

**校对不是走形式**：首轮校对实测在 7 条 LLM 产出里查出 1 处断言完全写反。
方法是**把每条断言的代码真的跑一遍**，而不是重读一遍。

> `origin` 如实标 `llm` —— 校对改的是 `review.state`，不篡改来源。

> 守护：R3（provenance）、R10（许可台账）、R17

## 11. 练习题怎么写

**只用于单列板块**（迁移教程）。多列板块没有「一条共享题面」的位置 —— 那里的说明
属于每一列，题面无处安放（R18/R19 与 `tests/pipeline/content-contract.test.ts` 钉住这条边界）。

`kind: exercise` 的题面写在 `feature.body`，**参考答案**走 snippet 的 `code`：

```yaml
# content/topics/js2python/01-functions.yaml
  - id: js2python/exercise
    kind: exercise
    title: 练习：合并配置对象
    body: |
      把下面这个函数迁到 Python，保持行为完全一致……
      写完对照本页 Python 列的参考实现。
```

```yaml
# content/languages/python/snippets/js2python/01-functions.yaml
  - featureId: js2python/exercise
    equivalence: analogous
    code: |
      def merge(*configs):   # 参考实现
        ...
```

**正文里不要写「下方的参考实现」** —— 它在**另一门语言那一列**，不在正下方。
说清是「本页 Python 列的参考实现」。

> 守护：R2

## 12. 常见错误（会静默失败的那些）

这些都不会让构建失败，但页面会错：

| 症状 | 原因 | 怎么避免 |
| --- | --- | --- |
| 某一格永远空着 | `featureId` 前缀写错，实现挂不上任何 feature | 跑 `content:validate`（R5 会报孤儿 snippet） |
| 内容改了但页面没变 | 没重跑 `content:build` | 改完 `content/` 就跑一次 |
| 整章解析失败 | YAML 普通标量以 `` ` `` 或 `{` 开头 | 加引号：`title: "{x} 是什么"` |
| `aliases: [null]` 变成空值 | 写了裸 `null` | 用 `~` 或加引号 |
| 注记没被抽出来 | 标记没跟在该语言的行注释前缀之后 | 检查 `meta.comment.line` |
| 注记行与代码行对不上 | 抽取只剥标记、整行原地保留，**行数绝不能变** | 不要手动增减注记行 |
| 左栏显示裸 key | 板块名写进了 i18n 而不是注册表 | 板块名声明在 `registry.yaml` 的 `sections` 段 |
| 放开一门语言后构建突然报一片 R2 | **`languages` 里出现一门语言，就要求该 topic 的每条 feature 都有它的实现** | 加语言与补内容必须同批；不要先加再补 |
| 想「暂时不要求覆盖」而写 `languages: []` | **空数组会被当成缺省**，等价于「全部已启用语言」，格子数不减反增 | 明确写出你要覆盖的那几门 |
| 进度条 / 勾选状态莫名清零 | 持久化的 key 用了会变的文案 | 用稳定 id（见 `RoadmapView` 的 `stage.id#序号`） |

**批量给 YAML 标量加引号的脚本会误伤块标量**（`code: |` 内部是代码原文）。改内容请手改。

## 13. 规则总表

| 规则 | 管什么 | 级别 |
| --- | --- | --- |
| R1 | 结构（loader 的 Zod 解析） | error |
| R2 | 覆盖率：适用范围内不能有空洞 | error |
| R3 | provenance 完整性 | error |
| R4/R9 | `@note` 标记的前缀与解析（组合 id，从不单独出现） | error |
| R5 | 引用完整性（孤儿 snippet、未知语言、对级词典只讲本方向两门） | error |
| R6 | 发布门槛（`reviewed-only` 策略下 draft 阻断） | error |
| R7 | URL 白名单（必须 https） | error |
| R8 | 命名与一致性（topic 目录、章节 id 前缀、基准候选） | error |
| R10 | 许可台账 | error |
| R11 | `equivalence` 非 `identical` 却既没有 `@note` 也没有 `body` | **warn** |
| R12 | 基准列的 `@note` 或 `body` 点名了屏幕外的语言 | **warn** |
| R13 | `featureId` 前缀必须等于所属 topicId | error |
| R14 | topic 的 `section` 必须在板块注册表里；`scope: pair` 必须声明 target | error |
| R15 | 覆盖层文件的 `topic` 声明与目录、与每条 `featureId` 前缀一致 | error |
| R16 | `code` 与 `blocks` 二选一；多段每段必须有 `label`。**没有板块级例外** —— 曾评估给「心智模型」加 `codeOptional` 以便只写说明，2026-10 决定不加 | error |
| R17 | 校对状态升级了却没留 `reviewedBy` / `reviewedAt` | **warn** |
| R18 | 多列板块（`columns: multi`）某一列没有 `body` 说明 | **warn**（补完后翻 error） |
| R19 | 多列板块还带着共享说明 `feature.body` | **warn**（补完后翻 error） |

> **R18 / R19 是过渡期规则**：正文按 topic 分批补，补完之前就把构建变红毫无意义 ——
> 那会把「内容还没写完」和「内容写错了」混成同一种信号。两条都**按 `(topic, 列)` 汇总成一条**
> 输出（缺口以百计，逐条会淹没真正要看的 error），逐条待办清单在 `npm run content:report` 里。
> 待补账目归零后，把 `warn(` 改成 `err(` 即可翻级。

**两个可执行断言**（不是规则，是脚本）：

- `npm run verify:ext` —— 加语言只加数据；且文案里没有写死语言名（三门基准权重相同）
- `npm run verify:sections` —— 加板块只加数据；且 `sections.gen.ts` 与 `registry.yaml` 同步
