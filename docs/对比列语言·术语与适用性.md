# 对比列语言 · 术语与适用性

> 这份文档服务于 **S11**（新增 7 门对比列语言，见[台账](项目步骤规划与进度台账.md) §6.7）。
> 它回答三个动笔之后会反复要查的问题：
> ① 这门语言管这个东西叫什么？② 这个知识点在这门语言里到底有没有？③ 样张暴露了哪些结构问题？
>
> **它不是规则** —— 规则在[内容书写标准.md](内容书写标准.md) §5.1。这里只放事实与判断。
> §2 的矩阵是**预判**，不是结论：真正写那一组时要按内容实际形态修正它。

## 1. 术语表

每门语言用它自己官方文档里的叫法，全站统一。**写作时先查这里，不要临时换词** ——
同一门语言在 104 个格子里用同一个词，读者才建立得起映射。

| 概念 | TypeScript | ArkTS | Kotlin | Swift | Dart | C++ | PHP |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 可空类型 | `string \| null` | `string \| null` | `String?` | `String?`（Optional） | `String?` | `std::optional<T>` | `?string` |
| 非空断言 | `!`（后缀） | `!`（后缀） | `!!` | `!`（后缀） | `!`（后缀） | 无对应语法 | 无对应语法 |
| 安全取值 | `?.` | `?.` | `?.` | `?.` | `?.` | `has_value()` / 判空 | `?->` |
| 默认值 | `??` | `??` | `?:`（Elvis） | `??` | `??` | `value_or()` | `??` |
| 不可变绑定 | `const` | `const` | `val` | `let` | `final` | `const` | `const`（仅编译期常量） |
| 编译期常量 | `const enum` | — | `const val` | `let`（全局） | `const` | `constexpr` | `const` |
| 类型判断 | `typeof` / `instanceof` | `typeof` / `instanceof` | `is` | `is` | `is` | `dynamic_cast` / `is_same_v` | `is_int()` 系列 / `instanceof` |
| 收窄 | 类型收窄（narrowing） | 同 TypeScript | 智能转换（smart cast） | 类型转换（`as?` 绑定） | 类型提升（promotion） | 无此概念（用 `variant` / 重载） | 无此概念 |
| 类型断言 | `as`（**不做**运行时检查） | `as`（**做**运行时检查） | `as` / `as?` | `as` / `as!` / `as?` | `as` | `static_cast` 等四种 | `(int)` 强制转换 |
| 数值转换 | `Number()` | 同 TypeScript | `toInt()` / `toByte()` | `Int(x)` 构造器 | `num.toInt()` | `static_cast<int>(x)` | `intval()` / `(int)` |
| 类型系统 | 结构化 | **名义**（禁用结构化） | 名义 | 名义 | 名义 | 名义 | 名义 |
| 接口 / 协议 | `interface` | `interface` | `interface` | `protocol` | 隐式接口 | 抽象类 / `concept` | `interface` / `trait` |

> **最需要盯住的是「类型断言」那一行** —— 同一个 `as` 关键字在这几门语言里语义完全不同：
> TypeScript 的 `as` **不做**任何运行时检查（只是让编译器改主意）；**ArkTS 的 `as` 会**在运行时校验、
> 失败抛异常；Swift 的 `as` 是向上转型（编译期保证）、`as!` 才是会崩的那个；Kotlin 与 Dart 的 `as`
> 失败抛异常，Kotlin 另有一个 `as?` 返回 null。写这几格时一个都别想当然 ——
> 样张第一版就把 ArkTS 照 TypeScript 的行为写成了「运行时不检查」，被这条核实纠正。
>
> **PHP 的 `const` 只是编译期常量**，不是「不可重新赋值的变量」；没有对应概念时用 `readonly`（8.1+）
> 或干脆讲没有。

## 2. 适用性矩阵

22 个存放组 × 7 门语言。「这门语言在这个知识点上有没有东西可写」——
它决定每一格的写法与工时。

| 记号 | 含义 |
| --- | --- |
| ● | 内容充足，是这门语言的强项或标志性特征 |
| ○ | 有内容，常规作答 |
| △ | 内容少、或要绕一下才讲得清（形态差异大） |
| ∅ | 大概率 `absent`：本语言没有这个概念 |
| ? | 拿不准，写到那一组时定 |

| --- | --- | --- | --- | --- | --- | --- | --- |

| toolchain | ○ | ○ | ○ | ○ | ○ | ○ | ○ |
| testing | ○ | ○ | ○ | ○ | ○ | ○ | ○ |

**几处值得先记下来的**：

- **`generics` 对 PHP 是 `∅`** —— PHP 没有泛型，只有文档注解（`@template`）。这一格会是纯粹的 `absent` + 「那你们怎么办」的说明。
- **`memory` 对 TS / ArkTS 是 `∅`** —— 有 GC 但语言层不暴露，写不出与基准的实质差异。而 C++ 与 Swift 在这一组是 ●（手动管理 / ARC），是它们最有价值的格子。
- **`concurrency` 对 PHP 是 `∅`** —— 共享无状态的请求模型，一次请求一个进程，没有语言级并发原语。
- **`meta` 对 ArkTS 可能是 ●** —— 装饰器（`@State` / `@Prop` / `@Link`）是它写 UI 的核心手段，比在 TypeScript 里更中心。
- **C++ 的 ● 密度最高**，且集中在 `model` 与 `mechanism` 两组 —— 它离三个基准都远，可写的东西最多，也最贵。

## 3. 样张暴露的问题

### 3.1 `equivalence` 的口径必须成文（已在 §5.1 补）

写样张时，同一个知识点在不同语言下出现了分歧判断：**`structural-nominal` 这一格，
Kotlin 对 Java 记 `analogous`（两者都是名义类型），而 Go 对 Java 记 `divergent`**。
两者都对 —— 判的是「各自与 Java 的关系」，不是语言的绝对属性。
但边界不写清楚，跨批次就会出现同一格判断不一致。判据已补进 §5.1 第 6 条。

### 3.2 ArkTS 与 TypeScript 的同质化（陪跑样张的结论）

`express/bindings` 陪跑样张的结果：**6 格里有 5 格对 TypeScript 侧的判断是
`identical` 或 `analogous`，真正有差异的是 `hoisting`**（ArkTS 的静态检查直接
否掉了依赖提升的写法）。其余几格的 `vs` 只能落在「ArkTS 的检查更严」这一句上。

这印证了按对比轴配对（轮 ① 把 TS 与 ArkTS 放一起）而非按谱系分的判断：
ArkTS 的价值集中在少数几组（`practice/*`、`mechanism/concurrency`、
`mechanism/meta`、`model/modules`），**其余组应当如实标 `identical` + 一句短说明，
不要为了填满而灌水**。矩阵里 ArkTS 的 △ 就是这些格子。

### 3.3 知识点切分：`types` 组目前不必动

主样张 `mechanism/types` 的 6 格在 7 门语言里都成立，没有出现
「两格在每门语言里说的都是同一句话」的过切分信号。
`static-vs-dynamic` 与 `type-annotation` 相邻但不重复（前者问「什么时候查」，
后者问「怎么写」），`type-narrowing` 与 `type-assertion` 也分得开。
**结论：池不动。**

### 3.4 一处写作纪律（已补进 §5.1 第 3 条）

样张写作中真的踩到了 R25：在 `vs.python` / `vs.java` 里为了做三方对比
把 JavaScript 拉了进来。**一份 `vs` 只许出现两门语言**，这一条在写「A 与 B 差在哪」
时特别容易破 —— 因为解释差异时天然想引第三个参照物。

## 4. 工时账

样张实测（可作为全量的换算基准）：

| 项 | 量 |
| --- | --- |
| 单格 YAML 平均行数 | 约 35–40 行（`code` 8–15 行 + 三份 `vs` 各 4–6 行 + `equivalence`） |
| 样张总量 | 12 格 × 7 门 = 84 格，约 2200 行 |
| 全量换算 | 728 格 ≈ **2.6–2.9 万行 YAML**，是样张的 13.5 倍 |

按每轮 44 个文件（2 门 × 22 组）计，**轮 ① 的粗略体量与现存 5 门语言之一相当**。
真正决定节奏的是 `●` 密度：C++（轮 ③）与 PHP（轮 ④）的格子写法最重，
但 PHP 有大量 `∅`（`generics` / `concurrency` / 部分 `memory`），实际不一定更慢。
